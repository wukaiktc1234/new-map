# UOM Conversion Model (Phase 7 Extension)

## 核心问题：单位转换的精度、舍入与部分消费

> 转换不是简单的乘法，需要考虑精度、舍入策略和部分消费场景。

---

## 1. UOM 转换类型分类

| 转换类型 | 定义 | 示例 | 精度要求 |
|----------|------|------|----------|
| **Same-Dimension** | 同维度单位转换 | 箱→瓶, kg→g | 中等 |
| **Cross-Dimension** | 跨维度单位转换 | kg→ml (需密度) | 高 |
| **Rounding** | 舍入处理 | 0.303瓶→0.31瓶 | 业务决定 |
| **Partial** | 部分消费 | 半瓶可乐 | 高 |

### 2.1 精度问题示例

```

│                 UOM 转换精度问题                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  场景: 100ml 可乐需要从瓶(Stock UOM)扣减                        │
│                                                                 │
│  转换计算:                                                      │
│    100 ml ÷ 330 ml/瓶 = 0.303030303... 瓶 (无限循环小数)       │
│                                                                 │
│  舍入策略选择:                                                  │
│    ┌────────────────┬──────────────┬──────────────┐             │
│    │ 策略           │ 结果         │ 影响         │             │
│    ├────────────────┼──────────────┼──────────────┤             │
│    │ 截断(2位)      │ 0.30 瓶      │ 少扣 0.3ml   │             │
│    │ 四舍五入(2位)  │ 0.30 瓶      │ 少扣 0.3ml   │             │
│    │ 向上取整(2位)  │ 0.31 瓶      │ 多扣 3ml     │             │
│    │ 精确存储       │ 0.3030瓶     │ 需要高精度   │             │
│    └────────────────┴──────────────┴──────────────┘             │
│                                                                 │
│  结论: 无完美方案，需根据业务场景选择                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 推荐的舍入策略配置

```sql
-- 舍入策略配置表
CREATE TABLE uom_rounding_config (
    id                BIGINT PRIMARY KEY,
    material_id       BIGINT,                  -- NULL=全局默认
    uom_usage         VARCHAR(20) NOT NULL,     -- 适用的 UOM 类型
    rounding_mode     VARCHAR(20) NOT NULL,     -- TRUNCATE/ROUND_UP/ROUND_DOWN/ROUND_HALF_UP
    decimal_places    INT NOT NULL DEFAULT 2,   -- 小数位数
    min_quantity      DECIMAL(12,4),            -- 最小可操作数量
    is_active         BOOLEAN DEFAULT TRUE,
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    UNIQUE (material_id, uom_usage)
);

-- 示例配置
INSERT INTO uom_rounding_config (material_id, uom_usage, rounding_mode, decimal_places) VALUES
(NULL, 'STOCK',    'ROUND_HALF_UP', 2),   -- 库存数量: 四舍五入到2位
(NULL, 'PURCHASE', 'ROUND_UP',      0),   -- 采购数量: 向上取整到整数
(NULL, 'SALES',    'TRUNCATE',      2),   -- 销售数量: 截断到2位
(NULL, 'RECIPE',   'ROUND_HALF_UP', 4);   -- 配方用量: 四舍五入到4位
```

## 3. Discrete vs Continuous Quantity

### 3.1 离散量 vs 连续量

```
┌─────────────────────────────────────────────────────────────────┐
│              Discrete vs Continuous Quantity                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Discrete Quantity (离散量)                                     │
│  ├── 定义: 只能取整数的量                                       │
│  ├── 示例: 瓶数、袋数、个数                                     │
│  ├── 特性: 不存在 0.5 瓶、1.3 袋                               │
│  └── 存储: INT 或 DECIMAL(整数)                                 │
│                                                                 │
│  Continuous Quantity (连续量)                                   │
│  ├── 定义: 可以取任意实数的量                                   │
│  ├── 示例: 重量(kg)、体积(ml)、长度(m)                         │
│  ├── 特性: 存在 0.303 瓶、1.25 kg                              │
│  └── 存储: DECIMAL(高精度)                                      │
│                                                                 │
│  ⚠️ 问题:                                                       │
│     当库存以"瓶"为单位时，0.303 瓶是否合理？                    │
│     这取决于"瓶"是 Discrete 还是 Continuous                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 餐饮场景的量类型判断

| 物料 | Stock UOM | 量类型 | 说明 |
|------|-----------|--------|------|
| 可乐 | 瓶 | Discrete | 不可能卖出 0.5 瓶 |
| 食用油 | 桶 | Continuous | 可以使用 0.5 桶 |
| 大米 | 袋 | Discrete | 不可能使用 0.3 袋 |
| 面粉 | kg | Continuous | 可以使用 1.5 kg |
| 调料 | ml | Continuous | 可以使用 25 ml |
| 鸡蛋 | 个 | Discrete | 不可能使用 1.5 个 |

## 4. Base UOM Quantity 存储方案

### 4.1 方案比较

```
┌─────────────────────────────────────────────────────────────────┐
│              Base UOM Quantity 存储方案                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  方案 A: 仅存储 Stock UOM                                       │
│  ├── 优点: 简单直观                                             │
│  ├── 缺点: 跨单位转换需要额外计算                               │
│  └── 示例: inventory.current_stock = 100 (瓶)                  │
│                                                                 │
│  方案 B: 仅存储 Base UOM                                        │
│  ├── 优点: 精确，转换简单                                       │
│  ├── 缺点: 显示不直观，需要频繁转换                             │
│  └── 示例: inventory.base_quantity = 33000 (ml)                │
│                                                                 │
│  方案 C: 双存储 (Stock + Base)                                  │
│  ├── 优点: 兼顾精确和直观                                       │
│  ├── 缺点: 存储冗余，需要同步                                   │
│  └── 示例:                                                    │
│       inventory.current_stock = 100 (瓶)                       │
│       inventory.base_quantity = 33000 (ml)                     │
│                                                                 │
│  方案 D: 仅存储 Base UOM + 转换缓存                             │
│  ├── 优点: 单一 Truth，转换按需计算                             │
│  ├── 缺点: 需要频繁转换                                         │
│  └── 示例:                                                    │
│       inventory.base_quantity = 33000 (ml)                     │
│       display_stock = base_quantity / conversion_factor         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 部分消费的处理策略

| 策略 | 适用场景 | 实现方式 | 精度影响 |
|------|----------|----------|----------|
| **精确存储** | 高价值物料 | Base UOM 存储 | 无损失 |
| **最小单位截断** | 低价值物料 | 按最小销售单位截断 | 有损失 |
| **批次管理** | 批次物料 | 按批次扣减 | 中等 |
| **倒冲扣减** | 配方物料 | 成品入库时倒冲 | 中等 |

### 6.1 库存真相应该按哪个单位保存？

```
┌─────────────────────────────────────────────────────────────────┐
│              Canonical Quantity 决策框架                         │
├─────────────────────────────────────────────────────────────────┤

│  决策因素:                                                      │
│  ┌─────────────────┬─────────────────┬─────────────────┐        │
```

## 7. In-transit Quantity (在途库存) 分析

### 7.1 在途库存定义

```
┌─────────────────────────────────────────────────────────────────┐
│                 In-transit Quantity 语义                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  定义: 已下单但尚未入库的物料数量                               │
│                                                                 │
│  来源:                                                          │
│  ├── 采购在途: purchase_order (已下单未收货)                    │
│  ├── 调拨在途: inventory_transfer (已发出未到达)                │
│  └── 退货在途: 退货单 (已发出未确认)                           │
│                                                                 │
│  计算:                                                          │
│    in_transit_qty = SUM(purchase_order.pending_qty)             │
│                   + SUM(transfer.in_transit_qty)                │
│                                                                 │
│  存储: 通常不单独存储，实时计算                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 7.2 在途库存的 UOM 处理

```
在途库存的 UOM 转换：

采购单.quantity = 10, unit = 箱 (Purchase UOM)
    ↓
需要转换为 Stock UOM 存储
    ↓
in_transit_qty = 10 × 24 = 240 瓶

调拨单.quantity = 50, unit = 瓶 (Stock UOM)
    ↓
直接存储，无需转换
    ↓
in_transit_qty = 50 瓶
```

## 8. 总结：库存真相应该用哪个单位？

### 8.1 最终推荐

```
┌─────────────────────────────────────────────────────────────────┐
│              Canonical Quantity 最终推荐                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ✅ 推荐方案: Base UOM 存储 + Stock UOM 展示                   │
│                                                                 │
│  存储层:                                                        │
│    inventory.base_quantity (ml/g/个)  ← 单一 Truth              │
│    inventory.current_stock (瓶/kg/袋) ← Derived 缓存           │
│                                                                 │
│  展示层:                                                        │
│    查询时按需转换: base_quantity → current_stock                │
│    显示时优先使用 Stock UOM (直观)                              │
│                                                                 │
│  转换层:                                                        │
│    uom_conversion 表定义转换系数                                │
│    material_uom 表定义物料的各单位                              │
│                                                                 │
│  精度控制:                                                      │
│    Base UOM 使用高精度 DECIMAL(15,4)                           │
│    舍入策略按业务场景配置                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 8.2 Phase 8 问题的回答

**Q: 库存真相究竟按哪个单位保存？**

**A: 按 Base UOM (基础单位) 保存**

| 物料 | 示例 | Base UOM | Canonical Quantity |
|------|------|----------|-------------------|
| 可乐 | 100 瓶 | ml | 33000 ml |
| 食用油 | 10 桶 | ml | 50000 ml |
| 大米 | 5 袋 | g | 250000 g |
| 调料 | 2 L | ml | 2000 ml |

**理由:**
1. **精确性**: Base UOM 是最小单位，无转换损失
2. **兼容性**: 可以转换为任何业务单位
3. **一致性**: 避免多单位存储导致的同步问题
4. **灵活性**: 支持部分消费、精确配方扣减
