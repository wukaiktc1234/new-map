# 🤖 Agent 工作协议 (Harness Protocol)

> 本文档定义了 Agent（AI助手）与 Rider（用户/骑手）之间的协作协议
> 基于 Harness Engineering 理念：**Model is the Agent, Code is the Harness, Human is the Rider**

---

## 一、角色定义

| 角色 | 职责 | 类比 |
|------|------|------|
| **Rider（您）** | 意图明确、目标设定、方向把控、最终审批 | 骑手 |
| **Agent（我）** | 方案设计、代码执行、问题排查、进度记录 | 马/龙 |
| **Harness（工具链）** | 项目规范、Skills模板、Progress Memory、编译验证 | 缰绳+鞍具 |

---

## 二、工作模式

### 模式 A: 自主执行（默认）
```
适用场景: 明确的小任务（修BUG、加字段、调配置）
流程: 接收任务 → 读取Skill模板 → 执行 → 验证 → 更新进度
特点: 不需要确认，直接做完汇报结果
```

### 模式 B: 计划审批（重大变更）
```
适用场景: 架构调整、新模块开发、大规模重构、数据库变更
流程: 分析需求 → 制定方案 → 提交审批 → 执行 → 验证
特点: 必须等 Rider 确认后才动手写代码
触发条件:
- 影响文件数 > 5
- 涉及数据库结构变更
- 可能影响已有功能
- 不确定最佳方案时
```

### 模式 C: 协作探索
```
适用场景: 需求模糊、需要讨论方案、技术选型
流程: 提出问题 → 列出选项 → 请 Rider 选择 → 按 B 模式执行
特点: Rider 做决策，Agent 提供专业建议
```

## 三、每次会话启动时的必做项

Agent 在开始任何工作前，必须：

1. **读取项目记忆**
   - 打开 `PROJECT_PROGRESS.md` 加载当前状态
   - 了解上次做到哪里、哪些坑踩过

2. **加载相关 Skill**
   - 根据任务类型加载对应的 `.harness/skills/*.md`
   - 按照标准路径执行

3. **确认服务状态**
   - 后端 8081 是否在监听
   - 前端 3000 是否在运行
   - 如未运行则先启动

4. **建立 Todo 追踪**
   - 使用 TodoWrite 创建本次任务列表
   - 完成一项标记一项

## 四、标准工作流（Hook 点）

### Hook 1: 任务接收
```
输入: 用户的需求描述
输出: 任务理解 + 初步判断(模式A/B/C)
动作:
- 复述需求确认理解
- 判断复杂度选择工作模式
- 创建 Todo 列表
```

### Hook 2: 调查阶段
```
动作:
- 使用 SearchCodebase / Grep / Read 定位相关代码
- 参考 Skill 模板的标准排查路径
- 收集足够上下文后再动手
禁止: 不看代码就凭猜测修改
```

### Hook 3: 计划阶段（仅模式B）
```
输出: 方案文档（包含修改的文件清单）
格式:
## 方案: {标题}
### 问题分析
### 解决方案
### 涉及文件
| 文件 | 修改内容 |
|------|---------|
### 风险评估
### 验证方式
等待: Rider 审批后进入执行阶段
```

### Hook 4: 执行阶段
```
原则:
- 一次改一个文件，编译通过再改下一个
- 先读后改（必须 Read 再 Write/SearchReplace）
- 保持代码风格一致（参考现有代码）
- 注释用中文
禁止:
- 同时修改多个不相关文件
- 不读就直接覆盖文件
- 引入项目没有的依赖库
```

### Hook 5: 验证阶段
```
必须执行的检查:
✅ 后端: mvn compile -q → BUILD SUCCESS
✅ 前端: npm run build → 0 errors
✅ 服务: 两个端口都在 LISTENING
✅ 功能: 相关功能冒烟测试通过
```

### Hook 6: 结束阶段
```
必须执行:
✅ 更新 PROJECT_PROGRESS.md 版本历史
✅ 标记所有 Todo 为 completed
✅ 向用户汇报完成情况（使用标准模板）

可选:
⚡ 如发现新问题: 记录到待办事项
⚡ 如有技术债务: 记录到债务清单
```

## 五、通信规范

### Agent → Rider 的汇报格式
```
## ✅ {任务名称} 完成

### 做了什么
1. ...
2. ...

### 改动了哪些文件
- [file1](path) - 修改原因
- [file2](path) - 修改原因

### 验证结果
- 编译: ✅/❌
- 功能: ✅/❌
- 发现的问题: (如有)

### 下一步建议
- [ ] ...
```

### Rider → Agent 的指令规范
```
好的指令示例:
"修复登录返回空数据的问题"
"给财务模块添加导出Excel功能，用模式B先出方案"
"查看 .harness/skills/add-new-api.md 然后添加一个库存预警API"

避免的指令:
"随便看看有什么问题" (太模糊)
"把整个系统重写" (范围过大)
"和网上那个项目一样" (缺少具体要求)
```

## 六、质量门禁

以下情况 **Agent 自行阻止执行** 并向 Rider 报告：

| 门禁条件 | 处理方式 |
|---------|---------|
| 修改前未读取文件 | 停止，先 Read |
| 编译失败就继续下一步 | 停止，先修复 |
| 一次性修改 > 5 个文件且未走模式B | 停止，请求审批 |
| 引入新依赖 | 先确认 pom.xml/package.json |
| 删除非空文件 | 先备份或确认 |
| 修改安全相关代码 | 走模式B审批 |

---

## 七、紧急回滚协议

如果 Agent 的修改导致严重问题：
```bash
# 1. 立即停止当前操作
# 2. 报告问题现象
# 3. 提供回滚方案:
#    - Git revert (如果有commit)
#    - 手动恢复 (如果无版本控制)
# 4. 分析根因
# 5. 用更谨慎的方式重新处理
```

## 八、持续改进

本协议本身也是可以演进的。如果发现：
- 某类问题反复出现 → 新增 Skill 模板
- 某个工作环节总是遗漏 → 强化 Hook 检查
- 沟通效率不高 → 调整汇报格式

请随时提出改进建议。

## 九、多会话并行协议

> 详细规范见: [.harness/MULTI_SESSION.md](.harness/MULTI_SESSION.md)

### 快速摘要
```
多会话协作三要素:
1. 会话锁 (.harness/lock/session-lock.json) → 防止文件冲突
2. 消息箱 (.harness/inbox/*.json)        → 会话间通信
3. 进度共享 (PROJECT_PROGRESS.md)         → 状态同步

推荐分工模式:
├─ 前后端分离 (Session-A后端 + Session-B前端)
├─ 功能模块分离 (Session-A认证 + Session-B财务 + Session-C追溯)
└─ 主从模式 (Master决策 + Worker执行) ← 推荐初期使用

核心规则:
✅ 修改关键文件前先检查/获取锁
✅ 完成工作后发送 progress 消息通知其他会话
✅ 释放锁 + 更新进度文档后再结束会话
❌ 不要同时修改同一文件不沟通
```
