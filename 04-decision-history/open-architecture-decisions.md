## DEC-010: 跨域数据访问模式

| 字段 | 值 |
|------|-----|
| **决策ID** | DEC-010 |
| **决策标题** | 跨域数据访问模式 |
| **状态** | 🟡 OPEN |
| **优先级** | P0 |
| **负责人** | 架构委员会 |
| **截止日期** | 2026-09-30 |
| **技术风险** | 高 — 影响所有域间通信 |

---

### 1. 问题描述

跨域查询应该走 API 契约还是允许直接读副本？当前部分服务直接读其他域的数据库，导致数据所有权边界模糊，数据一致性难以保证，域间耦合度高。需要定义数据所有权边界，统一跨域访问模式。

---

### 2. 当前现实

- 部分服务直接读其他域的数据库（如订单服务直接读用户数据库）
- 数据所有权边界模糊，谁拥有数据不清晰
- 跨域数据同步缺乏统一机制
- 数据一致性问题频发

**当前访问模式**:
```
订单服务 ──直接读取──> 用户数据库（违反数据所有权）
商品服务 ──直接读取──> 库存数据库（违反数据所有权）
营销服务 ──直接读取──> 订单数据库（违反数据所有权）
```

**问题示例**:
```sql
-- 订单服务中直接查询用户信息（应通过 API）
SELECT u.name, u.phone 
FROM users u 
WHERE u.id = ?;  -- 跨域直接访问

-- 库存服务中直接查询商品信息（应通过 API）
SELECT p.name, p.price 
FROM products p 
WHERE p.id = ?;  -- 跨域直接访问
```

---

### 3. 业务需求

| 需求 | 描述 | 优先级 |
|------|------|--------|
| 数据所有权 | 明确每个域的数据所有权边界 | P0 |
| 访问控制 | 统一跨域数据访问机制 | P0 |
| 数据一致性 | 保证跨域数据最终一致性 | P0 |
| 性能保障 | 跨域访问延迟可控 | P1 |
| 可观测性 | 跨域访问可监控、可追踪 | P1 |

---

### 4. 选项分析

#### Option A: API 契约（推荐）

| 维度 | 评估 |
|------|------|
| **描述** | 所有跨域访问必须通过 API 契约，禁止直接数据库访问 |
| **优点** | 数据所有权清晰，访问可控，易于监控 |
| **缺点** | 增加网络调用，可能影响性能 |
| **影响** | 所有跨域访问需重构为 API 调用 |
| **迁移成本** | 高 — 预估 120-180 人天 |
| **风险** | 中 — 迁移期间需保证业务连续性 |
| **性能影响** | ⚠️ 增加 5-20ms 延迟（可通过缓存优化） |

**架构示意**:
```
订单服务 ──API调用──> 用户服务 ──读取──> 用户数据库
商品服务 ──API调用──> 库存服务 ──读取──> 库存数据库
营销服务 ──API调用──> 订单服务 ──读取──> 订单数据库
```

#### Option B: 读副本（CQRS 变体）

| 维度 | 评估 |
|------|------|
| **描述** | 允许跨域读取其他域的只读副本，写操作必须通过 API |
| **优点** | 读性能高，减少 API 调用 |
| **缺点** | 数据所有权边界模糊，数据一致性难以保证 |
| **影响** | 需要维护读副本同步机制 |
| **迁移成本** | 中 — 预估 60-90 人天 |
| **风险** | 高 — 数据一致性问题可能导致业务错误 |
| **性能影响** | ✅ 读性能高（直接访问本地副本） |

**架构示意**:
```
订单服务 ──读取──> 用户只读副本（通过 CDC 同步）
商品服务 ──读取──> 库存只读副本（通过 CDC 同步）
营销服务 ──读取──> 订单只读副本（通过 CDC 同步）
```

#### Option C: 混合模式

| 维度 | 评估 |
|------|------|
| **描述** | 核心域数据通过 API 访问，非核心域数据允许读副本 |
| **优点** | 兼顾性能和一致性 |
| **缺点** | 规则复杂，需要明确哪些是核心域 |
| **影响** | 需要定义核心域/非核心域边界 |
| **迁移成本** | 中 — 预估 80-120 人天 |
| **风险** | 中 — 规则复杂可能导致误用 |
| **性能影响** | ✅ 核心域通过 API，非核心域通过副本 |

**架构示意**:
```
核心域访问：
订单服务 ──API调用──> 用户服务（用户信息为核心）
非核心域访问：
营销服务 ──读取──> 订单只读副本（订单明细为非核心）
```

---

### 5. 推荐方案

**推荐方案**: Option A — API 契约

**推荐理由**:
1. **数据所有权清晰**: 每个域完全拥有自己的数据，访问必须通过 API
2. **访问可控**: 可通过 API 网关统一控制跨域访问权限
3. **易于监控**: 所有跨域访问可追踪、可监控
4. **符合 LOCK-001**: 与事件驱动架构兼容，可通过事件实现数据同步
5. **长期收益**: 虽然迁移成本高，但长期维护成本降低

**实施要点**:
```yaml
# API 契约规范
跨域访问规则:
  - 所有跨域读操作必须通过 GET API
  - 所有跨域写操作必须通过 POST/PUT/DELETE API
  - 禁止直接数据库访问
  
API 设计规范:
  - 每个域提供标准 REST API
  - API 文档使用 OpenAPI 3.0 规范
  - API 版本管理采用 URL 路径版本号

性能优化:
  - 使用 Redis 缓存跨域查询结果
  - 设置合理的缓存 TTL
  - 实现缓存预热机制
```

**迁移计划**:
```yaml
阶段 1 (第 1-2 周):
  - 识别所有跨域直接数据库访问
  - 定义 API 契约规范
  - 创建 API 设计模板

阶段 2 (第 3-6 周):
  - 核心域 API 实现（用户、订单、商品）
  - 重构核心域跨域访问
  - 性能测试与优化

阶段 3 (第 7-10 周):
  - 非核心域 API 实现
  - 重构所有剩余跨域访问
  - 全量回归测试

阶段 4 (第 11-12 周):
  - 监控告警完善
  - 文档更新
  - 团队培训
```

## DEC-011: 事件驱动架构适用范围

| 字段 | 值 |
|------|-----|
| **决策ID** | DEC-011 |
| **决策标题** | 事件驱动架构适用范围 |
| **状态** | 🟡 OPEN |
| **优先级** | P0 |
| **负责人** | 架构委员会 |
| **截止日期** | 2026-09-30 |
| **技术风险** | 高 — 影响解耦策略 |

---

### 1. 问题描述

事件溯源是全面采用还是仅在核心域使用？当前部分模块已引入 Event Store，部分仍用传统 CRUD，导致架构风格不统一。需要确定事件驱动的适用范围，明确哪些域必须采用事件驱动，哪些域可以保留传统 CRUD。

---

### 2. 当前现实

- 部分模块已引入 Event Store（如订单域）
- 部分模块仍用传统 CRUD（如用户域）
- 架构风格不统一，维护成本高
- 事件驱动的优势未充分发挥

**当前架构状态**:
```
订单域: ✅ 已采用事件驱动架构
用户域: ❌ 传统 CRUD
商品域: ❌ 传统 CRUD
库存域: 🔄 部分事件驱动
营销域: ❌ 传统 CRUD
```

**LOCK-001 约束**:
- 事件驱动架构作为核心通信模式（已锁定）
- 所有领域事件通过事件总线进行异步传递
- 事件溯源机制已嵌入核心业务流程

---

### 3. 业务需求

| 需求 | 描述 | 优先级 |
|------|------|--------|
| 架构统一 | 统一架构风格，降低维护成本 | P0 |
| 解耦 | 服务间松耦合，支持独立部署 | P0 |
| 可追溯 | 业务状态变更可追溯 | P1 |
| 性能 | 事件驱动不影响系统性能 | P1 |
| 可观测 | 事件流可监控、可追踪 | P1 |

---

### 4. 选项分析

#### Option A: 全面事件驱动

| 维度 | 评估 |
|------|------|
| **描述** | 所有域必须采用事件驱动架构，所有状态变更通过事件记录 |
| **优点** | 架构统一，完全解耦，可追溯性强 |
| **缺点** | 迁移成本高，部分场景过度设计 |
| **影响** | 所有域需重构为事件驱动架构 |
| **迁移成本** | 极高 — 预估 200-300 人天 |
| **风险** | 高 — 迁移期间业务连续性风险 |
| **适用场景** | 核心业务域（订单、库存、支付） |

**架构示意**:
```
所有域 ──事件驱动──> 事件总线
  ├── 订单域: 创建订单、支付、发货
  ├── 用户域: 注册、修改信息、删除
  ├── 商品域: 上架、下架、改价
  ├── 库存域: 入库、出库、盘点
  └── 营销域: 创建活动、发放优惠券
```

#### Option B: 核心域事件驱动（推荐）

| 维度 | 评估 |
|------|------|
| **描述** | 核心域采用事件驱动架构，非核心域保留传统 CRUD |
| **优点** | 平衡解耦和成本，核心域完全解耦，非核心域保持简单 |
| **缺点** | 需要明确核心域/非核心域边界 |
| **影响** | 核心域需重构，非核心域保持现状 |
| **迁移成本** | 中 — 预估 80-120 人天 |
| **风险** | 中 — 需明确定义核心域边界 |
| **适用场景** | 大多数微服务架构 |

**架构示意**:
```
核心域（事件驱动）：
  ├── 订单域: 订单生命周期事件
  ├── 库存域: 库存变更事件
  └── 支付域: 支付状态事件

非核心域（传统 CRUD）：
  ├── 用户域: 用户信息管理
  ├── 商品域: 商品信息管理
  └── 营销域: 营销活动管理
```

#### Option C: 按需事件驱动

| 维度 | 评估 |
|------|------|
| **描述** | 各域自行决定是否采用事件驱动，无强制要求 |
| **优点** | 灵活性高，各域可按需选择 |
| **缺点** | 架构风格不统一，维护成本高 |
| **影响** | 无统一约束，可能导致架构混乱 |
| **迁移成本** | 低 — 预估 20-40 人天 |
| **风险** | 高 — 架构混乱，长期维护成本高 |
| **适用场景** | 不推荐（与 LOCK-001 冲突） |

---

### 5. 推荐方案

**推荐方案**: Option B — 核心域事件驱动

**推荐理由**:
1. **符合 LOCK-001**: 核心域采用事件驱动架构，符合已锁定的架构决策
2. **平衡成本**: 核心域完全解耦，非核心域保持简单，迁移成本可控
3. **风险可控**: 明确核心域边界，避免过度设计
4. **长期收益**: 核心域完全解耦，支持独立部署和扩展

**核心域定义**:
```yaml
核心域（必须事件驱动）:
  - 订单域: 订单创建、支付、发货、退款
  - 库存域: 库存入库、出库、盘点、调拨
  - 支付域: 支付发起、回调、对账

非核心域（可选事件驱动）:
  - 用户域: 用户注册、信息修改（可保留 CRUD）
  - 商品域: 商品上架、下架（可保留 CRUD）
  - 营销域: 活动创建、优惠券发放（可保留 CRUD）
```

**实施要点**:
```yaml
核心域事件定义:
  订单域:
    - order.created: 订单创建事件
    - order.paid: 订单支付事件
    - order.shipped: 订单发货事件
    - order.completed: 订单完成事件
    - order.cancelled: 订单取消事件
  
  库存域:
    - inventory.inbound: 库存入库事件
    - inventory.outbound: 库存出库事件
    - inventory.adjusted: 库存调整事件
  
  支付域:
    - payment.initiated: 支付发起事件
    - payment.completed: 支付完成事件
    - payment.failed: 支付失败事件

事件存储:
  - 使用 EventStoreDB 存储核心域事件
  - 事件保留策略: 热数据 90 天，冷数据 1 年
  - 事件 schema 演进: 采用 Schema Registry 管理
```

## DEC-013: 裸接口权限归属

| 字段 | 值 |
|------|-----|
| **决策ID** | DEC-013 |
| **决策标题** | 裸接口权限归属 |
| **状态** | 🟡 OPEN |
| **优先级** | P1 |
| **负责人** | 安全组 |
| **截止日期** | 2026-10-15 |
| **技术风险** | 中 — 影响安全模型 |

---

### 1. 问题描述

内部微服务间调用是否需要 token 认证？当前部分服务有 mTLS，部分无任何认证，导致内部接口安全性不一致。需要定义内部接口安全基线，明确哪些内部接口需要认证，哪些可以裸调用。

---

### 2. 当前现实

- 部分服务有 mTLS 双向认证
- 部分服务无任何认证（裸接口）
- 内部接口安全性不一致
- 安全审计困难

**当前安全状态**:
```
用户服务: ✅ mTLS + JWT
订单服务: ✅ mTLS + JWT
商品服务: ⚠️ 仅 mTLS
库存服务: ❌ 无认证（裸接口）
营销服务: ❌ 无认证（裸接口）
```

**问题示例**:
```yaml
# 裸接口示例
内部接口:
  - GET /internal/inventory/{id}  # 无认证
  - POST /internal/inventory/adjust  # 无认证
  - GET /internal/marketing/campaigns  # 无认证

# 安全接口示例
内部接口:
  - GET /internal/user/{id}  # mTLS + JWT
  - POST /internal/order/create  # mTLS + JWT
```

### 4. 选项分析

#### Option A: 全面认证（推荐）

| 维度 | 评估 |
|------|------|
| **描述** | 所有内部接口必须通过 mTLS + JWT 认证 |
| **优点** | 安全性高，访问可控，审计完整 |
| **缺点** | 增加运维复杂度，可能影响性能 |
| **影响** | 所有内部接口需添加认证 |
| **迁移成本** | 中 — 预估 40-60 人天 |
| **风险** | 低 — 安全性高，风险可控 |
| **性能影响** | ⚠️ 增加 2-5ms 延迟（可通过缓存优化） |

**安全架构**:
```
内部服务调用:
  服务 A ──mTLS + JWT──> 服务 B
  
认证流程:
  1. 服务 A 向认证中心申请 JWT
  2. 服务 A 携带 JWT 调用服务 B
  3. 服务 B 验证 JWT 有效性
  4. 服务 B 处理请求并返回响应
```

#### Option B: mTLS only

| 维度 | 评估 |
|------|------|
| **描述** | 仅通过 mTLS 认证，不要求 JWT |
| **优点** | 运维简单，性能影响小 |
| **缺点** | 无法细粒度控制访问权限 |
| **影响** | 所有内部接口需配置 mTLS |
| **迁移成本** | 低 — 预估 20-30 人天 |
| **风险** | 中 — 无法细粒度控制权限 |
| **性能影响** | ✅ 性能影响小（仅 TLS 握手） |

**安全架构**:
```
内部服务调用:
  服务 A ──mTLS──> 服务 B
  
认证流程:
  1. 服务 A 与服务 B 建立 mTLS 连接
  2. 服务 B 验证服务 A 的证书
  3. 服务 B 处理请求并返回响应
```

#### Option C: 混合模式

| 维度 | 评估 |
|------|------|
| **描述** | 核心域接口需要 mTLS + JWT，非核心域接口仅需 mTLS |
| **优点** | 平衡安全性和运维复杂度 |
| **缺点** | 规则复杂，需要明确定义核心域/非核心域边界 |
| **影响** | 核心域接口需添加 JWT，非核心域接口仅需 mTLS |
| **迁移成本** | 中 — 预估 30-45 人天 |
| **风险** | 中 — 规则复杂可能导致误用 |
| **性能影响** | ✅ 核心域增加 2-5ms，非核心域无影响 |

**安全架构**:
```
核心域服务调用:
  服务 A ──mTLS + JWT──> 服务 B
  
非核心域服务调用:
  服务 A ──mTLS──> 服务 B
```

### 5. 推荐方案

**推荐方案**: Option A — 全面认证

**推荐理由**:
1. **安全性高**: 所有内部接口必须认证，防止未授权访问
2. **访问可控**: 通过 JWT 可细粒度控制访问权限
3. **审计完整**: 所有内部访问可审计，满足合规要求
4. **符合 LOCK-004**: 与已锁定的 OAuth 2.0 + JWT 认证方案兼容

**实施要点**:
```yaml
认证架构:
  - mTLS: 所有服务间通信必须使用 mTLS
  - JWT: 所有内部接口必须验证 JWT
  
JWT 配置:
  - 有效期: 15 分钟
  - 刷新机制: 服务间自动刷新
  - 签名算法: RS256
  
权限模型:
  - 服务级权限: 每个服务可访问哪些内部接口
  - 接口级权限: 每个接口的访问控制规则
  
审计日志:
  - 记录所有内部接口访问
  - 包含服务名、接口名、时间、结果
  - 日志保留: 90 天
```

## DEC-014: 供应商 H5 认证

| 字段 | 值 |
|------|-----|
| **决策ID** | DEC-014 |
| **决策标题** | 供应商 H5 认证 |
| **状态** | 🟡 OPEN |
| **优先级** | P1 |
| **负责人** | 安全组 |
| **截止日期** | 2026-10-15 |
| **技术风险** | 中 — 影响前端架构 |

---

### 1. 问题描述

供应商 H5 是独立部署还是嵌入主站 iframe？当前两种方案各有原型，需要确定集成架构，明确供应商 H5 的部署方式、认证方式、安全边界。

---

### 2. 当前现实

- 供应商 H5 有两种原型方案
- 独立部署方案：供应商 H5 独立部署，通过 API 与主站交互
- iframe 嵌入方案：供应商 H5 嵌入主站 iframe，通过 postMessage 通信
- 两种方案各有优缺点，尚未最终确定

**当前原型状态**:
```
方案 A: 独立部署
  - 供应商 H5 独立部署
  - 通过 API 与主站交互
  - 独立域名，独立认证

方案 B: iframe 嵌入
  - 供应商 H5 嵌入主站 iframe
  - 通过 postMessage 通信
  - 共享域名，共享认证
```

**安全考量**:
```yaml
独立部署:
  - 优点: 安全边界清晰，隔离性好
  - 缺点: 认证复杂，用户体验可能受影响

iframe 嵌入:
  - 优点: 认证简单，用户体验好
  - 缺点: 安全风险高，需要防范 XSS、CSRF 等攻击
```

---

### 3. 业务需求

| 需求 | 描述 | 优先级 |
|------|------|--------|
| 安全性 | 供应商 H5 与主站安全隔离 | P0 |
| 用户体验 | 供应商操作流畅，无感知切换 | P1 |
| 认证简单 | 认证流程简单，易于集成 | P1 |
| 运维简单 | 部署和运维简单 | P1 |
| 扩展性 | 支持未来供应商扩展 | P1 |

---

### 4. 选项分析

#### Option A: 独立部署

| 维度 | 评估 |
|------|------|
| **描述** | 供应商 H5 独立部署，通过 API 与主站交互 |
| **优点** | 安全边界清晰，隔离性好，易于扩展 |
| **缺点** | 认证复杂，用户体验可能受影响 |
| **影响** | 供应商 H5 需独立部署，独立域名 |
| **迁移成本** | 中 — 预估 30-45 人天 |
| **风险** | 中 — 认证复杂，用户体验可能受影响 |
| **性能影响** | ✅ 无跨域性能影响 |

**架构示意**:
```
主站 ──API调用──> 供应商 H5 后端
  │
  ├── 独立域名: supplier.example.com
  ├── 独立认证: OAuth 2.0 + JWT
  └── 独立部署: 独立 CI/CD 流水线

安全边界:
  - 主站与供应商 H5 完全隔离
  - 通过 API 网关统一管理
  - 跨域请求需 CORS 配置
```

#### Option B: iframe 嵌入（推荐）

| 维度 | 评估 |
|------|------|
| **描述** | 供应商 H5 嵌入主站 iframe，通过 postMessage 通信 |
| **优点** | 认证简单，用户体验好，部署简单 |
| **缺点** | 安全风险高，需要防范 XSS、CSRF 等攻击 |
| **影响** | 供应商 H5 嵌入主站，共享域名 |
| **迁移成本** | 低 — 预估 15-25 人天 |
| **风险** | 中 — 安全风险需通过技术手段控制 |
| **性能影响** | ⚠️ iframe 加载可能影响页面性能 |

**架构示意**:
```
主站 ──iframe──> 供应商 H5
  │
  ├── 共享域名: 主站域名
  ├── 共享认证: 主站认证
  └── 通信方式: postMessage

安全措施:
  - Content Security Policy (CSP)
  - X-Frame-Options: SAMEORIGIN
  - postMessage 消息验证
  - 输入输出过滤
```

#### Option C: 微前端

| 维度 | 评估 |
|------|------|
| **描述** | 采用微前端架构，供应商 H5 作为微应用集成到主站 |
| **优点** | 架构先进，隔离性好，用户体验好 |
| **缺点** | 技术复杂度高，学习曲线陡峭 |
| **影响** | 需要引入微前端框架 |
| **迁移成本** | 高 — 预估 60-90 人天 |
| **风险** | 高 — 技术复杂度高，团队可能不熟悉 |
| **性能影响** | ✅ 无跨域性能影响，资源加载优化 |

**架构示意**:
```
主站 ──微前端──> 供应商 H5 微应用
  │
  ├── 框架: qiankun / single-spa
  ├── 共享依赖: React, 公共组件
  └── 通信方式: 全局状态管理

安全措施:
  - JS Sandbox 隔离
  - CSS 隔离
  - 生命周期管理
  - 依赖共享控制
```

---

### 5. 推荐方案

**推荐方案**: Option B — iframe 嵌入

**推荐理由**:
1. **用户体验好**: 供应商操作在主站内完成，无感知切换
2. **认证简单**: 共享主站认证，无需额外认证流程
3. **部署简单**: 供应商 H5 嵌入主站，无需独立部署
4. **成本最低**: 迁移成本低，快速集成

**安全措施**:
```yaml
Content Security Policy (CSP):
  - default-src 'self'
  - script-src 'self' 'unsafe-inline' 'unsafe-eval'
  - style-src 'self' 'unsafe-inline'
  - img-src 'self' data: https:
  - connect-src 'self' https://api.example.com

X-Frame-Options:
  - SAMEORIGIN

postMessage 安全:
  - 验证消息来源
  - 使用 JSON Schema 验证消息格式
  - 限制消息类型

输入输出过滤:
  - 所有用户输入进行 HTML 实体编码
  - 所有输出进行 XSS 过滤
  - 使用 DOMPurify 库进行净化
```

**实施要点**:
```yaml
iframe 配置:
  - sandbox: allow-scripts allow-same-origin allow-forms
  - allowfullscreen: true
  - allowpaymentrequest: true

通信协议:
  - 消息类型: 枚举定义
  - 消息格式: JSON Schema 验证
  - 错误处理: 超时、重试、降级

性能优化:
  - iframe 预加载
  - 资源缓存
  - 懒加载非关键资源
```
