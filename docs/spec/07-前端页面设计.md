# 前端页面设计规范

## 一、页面设计原则

### 1.1 单一职责

每个页面只负责一个核心功能，避免将多个不相关的业务逻辑混合在同一个页面中。页面级组件仅负责布局和组件组合，不包含具体业务逻辑。

- 页面组件只做布局编排和子组件组合
- 业务逻辑下沉到功能组件或 Composable 中
- 数据管理交给 Pinia Store 或 Composable
- 工具函数提取到 `utils/` 目录

### 1.2 一致性

统一布局结构、统一交互模式、统一视觉风格，确保用户在不同页面间切换时体验连贯。

- 统一布局：所有业务页面使用 `PageHeader + ContentCard` 结构
- 统一交互：相同操作使用相同的交互方式（如新增、编辑、删除）
- 统一视觉：使用 CSS 变量统一样式，支持浅色/深色主题切换
- 统一命名：组件、文件、变量遵循相同的命名规范

### 1.3 响应式

适配不同屏幕尺寸，确保在移动端、平板和桌面设备上均可正常使用。

- 移动端优先的渐进增强策略
- 使用 CSS Grid 和 Flexbox 实现弹性布局
- 关键信息在小屏幕上优先展示
- 复杂表格在移动端提供简化视图或卡片视图

### 1.4 可访问性

支持键盘导航和屏幕阅读器，确保所有用户均可使用系统功能。

- 所有交互元素支持键盘操作（Tab/Enter/Escape）
- 使用语义化 HTML 标签
- 为图标按钮提供 `aria-label` 属性
- 确保颜色对比度符合 WCAG 2.1 AA 标准
- 尊重用户 `prefers-reduced-motion` 偏好设置

## 二、页面布局规范

### 2.1 主布局：MainLayout

主布局是系统所有业务页面的容器，由以下区域组成：

```
+----------------------------------------------------------+
|                        Header                             |
+----------+-----------------------------------------------+
|          |                   TagsBar                      |
| Sidebar  +-----------------------------------------------+
|          |                                               |
|          |                 ContentArea                    |
|          |                                               |
+----------+-----------------------------------------------+
```

| 区域 | 说明 |
|------|------|
| Header | 顶部导航栏，包含 Logo、面包屑、用户信息、主题切换 |
| Sidebar | 侧边菜单栏，支持折叠/展开，展示功能模块导航 |
| TagsBar | 标签页栏，支持多页签切换和关闭 |
| ContentArea | 内容区域，承载具体业务页面 |

### 2.2 内容区布局：PageHeader + ContentCard

所有业务页面统一使用以下布局结构：

```
+----------------------------------------------------------+
|  PageHeader                                               |
|  - 页面标题                                                |
|  - 操作按钮区                                              |
+----------------------------------------------------------+
|  ContentCard                                              |
|  - card-header: 搜索/筛选条件                              |
|  - card-body: 数据表格/内容展示                             |
|  - card-footer: 分页/批量操作                              |
+----------------------------------------------------------+
```

**PageHeader 组件**：

- 展示当前页面标题
- 提供页面级操作按钮（如新增、导出）
- 支持面包屑导航

**ContentCard 组件**：

- 统一的卡片容器样式
- `card-header`：放置搜索条件和筛选器
- `card-body`：放置数据表格或内容区域
- `card-footer`：放置分页组件和批量操作栏

### 2.3 页面级组件职责

页面级组件仅负责以下工作：

- 组合子组件，确定页面布局
- 传递数据和事件给子组件
- 调用 Composable 获取页面数据
- 不包含具体的业务逻辑实现

```vue
<!-- 示例：页面级组件结构 -->
<template>
  <div class="page-container">
    <PageHeader title="产品列表" :actions="headerActions" />
    <ContentCard>
      <ProductSearch :filters="filters" @search="handleSearch" />
      <ProductTable :data="tableData" :loading="loading" />
      <ProductPagination :total="total" @change="handlePageChange" />
    </ContentCard>
  </div>
</template>
```

## 三、路由设计规范

### 3.1 路由模块化

每个业务域一个路由文件，统一放置在 `router/modules/` 目录下：

```
router/
├── index.ts              # 路由入口，合并所有模块
├── guards.ts             # 路由守卫
└── modules/
    ├── public.ts         # 公共路由
    ├── product.ts        # 产品中心
    ├── order.ts          # 订单中心
    ├── store.ts          # 门店运营
    ├── purchase.ts       # 采购管理
    ├── finance.ts        # 财务中心
    ├── hr.ts             # 人事管理
    ├── asset.ts          # 资产管理
    ├── marketing.ts      # 营销增长
    ├── data.ts           # 数据决策
    └── system.ts         # 系统设置
```

### 3.2 路由 meta 规范

每条路由的 `meta` 字段必须包含以下属性：

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| title | string | 是 | 页面标题，用于面包屑和标签页 |
| icon | string | 否 | 菜单图标，使用 Element Plus 图标名 |
| permissions | string[] | 否 | 访问权限标识列表 |
| menuType | number | 是 | 0=目录, 1=菜单, 2=详情页 |
| category | string | 否 | 业务域分类标识 |
| hidden | boolean | 否 | 是否在菜单中隐藏，默认 false |
| keepAlive | boolean | 否 | 是否缓存页面，默认 false |
| activeMenu | string | 否 | 详情页激活的菜单路径 |

**路由定义示例**：

```typescript
const productRoutes: RouteRecordRaw[] = [
  {
    path: '/product',
    component: MainLayout,
    meta: { title: '产品中心', icon: 'Goods', menuType: 0, category: 'product' },
    children: [
      {
        path: 'list',
        name: 'ProductList',
        component: () => import('@/views/Product/ProductList.vue'),
        meta: { title: '产品列表', icon: 'List', menuType: 1, permissions: ['product:list'], category: 'product' }
      },
      {
        path: 'detail/:id',
        name: 'ProductDetail',
        component: () => import('@/views/Product/ProductDetail.vue'),
        meta: { title: '产品详情', menuType: 2, activeMenu: '/product/list', category: 'product' }
      }
    ]
  }
]
```

### 3.3 路由守卫

路由守卫按以下顺序执行：

1. **认证检查**：验证 JWT Token 是否有效，无效则跳转登录页
2. **权限检查**：验证用户是否拥有路由所需的权限标识
3. **功能模块检查**：验证用户企业是否开通了对应的功能模块
4. **页面初始化**：加载页面所需的公共数据（如字典、配置）

```typescript
router.beforeEach(async (to, from, next) => {
  // 1. 认证检查
  if (!isAuthenticated() && !isPublicRoute(to)) {
    return next({ path: '/login', query: { redirect: to.fullPath } })
  }

  // 2. 权限检查
  if (to.meta.permissions && !hasPermission(to.meta.permissions)) {
    return next({ path: '/403' })
  }

  // 3. 功能模块检查
  if (to.meta.category && !hasModule(to.meta.category)) {
    return next({ path: '/404' })
  }

  next()
})
```

### 3.4 公共路由

以下路由不需要认证和权限检查：

| 路径 | 页面 | 说明 |
|------|------|------|
| /login | LoginPage | 登录页 |
| /register | RegisterPage | 注册页 |
| /404 | NotFoundPage | 页面不存在 |
| /403 | ForbiddenPage | 无权限 |
| /system-init | SystemInitWizard | 系统初始化向导 |

### 3.5 业务路由

| 业务域 | 路径前缀 | 说明 |
|--------|---------|------|
| 产品中心 | /product/* | 产品、分类、规格管理 |
| 订单中心 | /order/* | 订单、退款、评价管理 |
| 门店运营 | /store/* | 门店、库存、健康证管理 |
| 采购管理 | /purchase/* | 供应商、采购单、入库管理 |
| 财务中心 | /finance/* | 报表、账单、成本管理 |
| 人事管理 | /hr/* | 员工、部门、考勤管理 |
| 资产管理 | /asset/* | 固定资产、盘点管理 |
| 营销增长 | /marketing/* | 会员、优惠券、活动管理 |
| 数据决策 | /data/* | 数据看板、分析报表 |
| 系统设置 | /system/* | 角色、权限、配置管理 |

## 四、页面组件拆分规范

### 4.1 组件层级划分

| 层级 | 职责 | 示例 |
|------|------|------|
| 页面级组件 | 布局编排和组件组合 | `ProductList.vue` |
| 功能组件 | 实现具体业务功能 | `ProductSearchForm.vue`、`ProductTable.vue` |
| 复用组件 | 通用 UI 元素 | `SearchPanel.vue`、`DataTable.vue` |
| 基础组件 | Element Plus 二次封装 | `EmptyState.vue`、`StatusTag.vue` |

### 4.2 页面级组件

页面级组件仅负责以下工作：

- 确定页面整体布局
- 组合功能子组件
- 通过 Composable 获取和管理页面状态
- 将状态和事件传递给子组件

**禁止事项**：

- 禁止在页面级组件中编写复杂业务逻辑
- 禁止直接操作 DOM
- 禁止在页面级组件中定义大量内部方法

### 4.3 功能组件

功能组件负责实现具体的业务功能，接收父组件传递的数据和事件：

- 表单组件：负责表单渲染、验证和数据收集
- 表格组件：负责数据展示、排序和筛选
- 详情组件：负责数据详情展示
- 操作组件：负责特定业务操作（如审批、导出）

### 4.4 复用组件

复用组件是跨页面通用的 UI 元素，放置在 `components/` 目录下：

- `SearchPanel`：通用搜索面板
- `DataTable`：通用数据表格
- `PageHeader`：页面头部
- `ContentCard`：内容卡片
- `EmptyState`：空状态展示
- `ElMessageBox/ElPopconfirm`：确认操作（Element Plus原生组件）
- `StatusTag`：状态标签
- `FileUpload`：文件上传

### 4.5 状态管理

复杂状态使用 Pinia Store 管理，简单状态使用 Composable：

| 状态复杂度 | 管理方式 | 示例 |
|-----------|---------|------|
| 跨页面共享 | Pinia Store | 用户信息、权限数据 |
| 页面内复杂状态 | Pinia Store | 报表生成进度、多步骤表单 |
| 页面内简单状态 | Composable | 表格筛选、分页状态 |
| 组件内状态 | ref/reactive | 表单输入、弹窗开关 |

### 4.6 文件大小阈值

| 文件类型 | 最大行数 | 超出时处理方式 |
|---------|---------|--------------|
| Vue 组件 | 1000 行 | 拆分为子组件 |
| JavaScript/TypeScript | 800 行 | 提取工具函数或 Composable |
| SCSS/CSS | 600 行 | 提取公共样式 |
| 函数/方法 | 100 行 | 拆分为多个小函数 |

## 六、Composable 设计规范

### 6.1 命名规范

Composable 文件统一使用 `use{Feature}.ts` 命名，放置在 `composables/` 目录下：

```
composables/
├── useCrudTable.ts          # 通用增删改查表格
├── usePermission.ts         # 权限判断
├── useLayout.ts             # 布局控制
├── useThemes.ts             # 主题切换
├── useMenu.ts               # 菜单管理
├── useFinanceReport.ts      # 财务报表
├── useEmployee.ts           # 员工管理
├── useHealthCertificate.ts  # 健康证管理
└── ...
```

### 6.2 核心 Composable

| Composable | 职责 | 返回值 |
|-----------|------|--------|
| useCrudTable | 通用列表页逻辑（分页、搜索、排序） | tableData, loading, pagination, search, refresh |
| usePermission | 权限判断和按钮级权限控制 | hasPermission, hasAnyPermission, hasAllPermissions |
| useLayout | 布局状态控制（侧边栏、标签页） | isCollapsed, toggleSidebar, addTag, removeTag |
| useThemes | 主题切换和持久化 | currentTheme, toggleTheme, isDark |
| useMenu | 菜单数据获取和过滤 | menuList, activeMenu, filterByPermission |

**useCrudTable 示例**：

```typescript
export function useCrudTable<T>(options: CrudTableOptions<T>) {
  const tableData = ref<T[]>([])
  const loading = ref(false)
  const pagination = reactive({
    current: 1,
    size: 20,
    total: 0
  })
  const searchParams = ref<Record<string, unknown>>({})

  async function fetchData() {
    loading.value = true
    try {
      const result = await options.fetchApi({
        ...searchParams.value,
        page: pagination.current,
        size: pagination.size
      })
      tableData.value = result.records
      pagination.total = result.total
    } finally {
      loading.value = false
    }
  }

  function handleSearch(params: Record<string, unknown>) {
    searchParams.value = params
    pagination.current = 1
    fetchData()
  }

  function handlePageChange(page: number) {
    pagination.current = page
    fetchData()
  }

  return {
    tableData,
    loading,
    pagination,
    searchParams,
    fetchData,
    handleSearch,
    handlePageChange
  }
}
```

### 6.3 业务 Composable

业务 Composable 封装特定业务域的逻辑，每个 Composable 只负责一个关注点：

| Composable | 关注点 | 使用页面 |
|-----------|--------|---------|
| useFinanceReport | 报表生成、模板管理、进度跟踪 | 财务报表相关页面 |
| useEmployee | 员工数据获取、状态管理 | 人事管理相关页面 |
| useHealthCertificate | 健康证到期提醒、批量管理 | 门店运营相关页面 |
| useOrderProcess | 订单状态流转、操作记录 | 订单中心相关页面 |
| useInventory | 库存查询、预警计算 | 门店运营、采购管理 |

### 6.4 Composable 设计原则

- **单一关注点**：每个 Composable 只负责一个明确的功能
- **显式参数**：通过参数接收配置，不依赖外部全局状态
- **返回值类型明确**：返回值使用 TypeScript 接口定义类型
- **可组合**：Composable 之间可以相互调用，但避免循环依赖
- **可测试**：逻辑与 UI 解耦，便于单元测试

## 七、Pinia Store 设计规范

### 7.1 命名规范

Store 文件使用 kebab-case 命名，放置在 `stores/` 目录下：

```
stores/
├── auth.ts                  # 认证（根 Store）
├── permission.ts            # 权限
├── menu.ts                  # 菜单
├── hr.ts                    # 人事管理
├── order.ts                 # 订单管理
├── finance-report.ts        # 财务报表
├── finance-summary.ts       # 财务汇总
└── ...
```

### 7.2 核心 Store

核心 Store 之间存在单向依赖关系：

```
auth (根) --> permission --> menu
```

| Store | 职责 | 缓存策略 |
|-------|------|---------|
| auth | 用户认证、Token 管理、登录登出 | sessionStorage |
| permission | 用户权限数据、角色权限映射 | 内存 + sessionStorage |
| menu | 菜单数据、菜单过滤、激活状态 | 内存 |

**auth Store 示例**：

```typescript
export const useAuthStore = defineStore('auth', () => {
  const token = ref<string | null>(localStorage.getItem('token'))
  const userInfo = ref<UserInfo | null>(null)
  const isAuthenticated = computed(() => !!token.value)

  async function login(credentials: LoginParams) {
    const data = await authApi.login(credentials)
    token.value = data.token
    userInfo.value = data.user
    sessionStorage.setItem('token', data.token)
  }

  function logout() {
    token.value = null
    userInfo.value = null
    sessionStorage.removeItem('token')
  }

  return { token, userInfo, isAuthenticated, login, logout }
})
```

### 7.3 业务 Store

| Store | 职责 | 使用页面 |
|-------|------|---------|
| hr | 员工、部门、职位数据管理 | 人事管理相关页面 |
| order | 订单数据、状态流转管理 | 订单中心相关页面 |
| finance-report | 报表生成、模板、进度管理 | 财务报表相关页面 |
| finance-summary | 财务汇总数据、图表数据 | 财务概览相关页面 |
| purchase | 采购单、供应商数据管理 | 采购管理相关页面 |
| marketing | 会员、优惠券、活动数据 | 营销增长相关页面 |

### 7.4 Store 间依赖规则

- **单向依赖**：Store 之间只能单向依赖，禁止循环依赖
- **层级关系**：核心 Store 为底层，业务 Store 可依赖核心 Store，业务 Store 之间不可互相依赖
- **数据流向**：数据从核心 Store 向业务 Store 流动，禁止反向操作

```
依赖层级：
  核心层：auth
    |
    v
  权限层：permission
    |
    v
  展示层：menu
    |
    v
  业务层：hr, order, finance-report, ...
```

### 7.5 缓存策略

| 缓存方式 | 适用场景 | 生命周期 |
|---------|---------|---------|
| 内存 (ref) | 频繁变更的临时数据 | 页面关闭即清除 |
| sessionStorage | 需要跨页面但不需要持久化的数据 | 浏览器标签页关闭即清除 |
| localStorage | 需要持久化的用户偏好数据 | 手动清除或过期 |

**缓存使用原则**：

- Token 使用 localStorage 存储，确保同域多标签页共享登录状态
- 用户偏好（主题、语言）使用 localStorage
- 业务数据默认使用内存缓存，页面刷新后重新获取
- 不在 Store 中缓存大量列表数据，按需从 API 获取

## 八、交互设计规范

### 8.1 表单验证

表单验证采用实时验证与提交验证相结合的策略：

**实时验证**：

- 输入框失焦（blur）时触发验证
- 格式类错误（如邮箱格式、手机号格式）实时提示
- 必填字段在用户开始输入后实时验证

**提交验证**：

- 表单提交前执行完整验证
- 验证未通过时滚动到第一个错误字段
- 验证错误信息显示在对应字段下方

```typescript
const rules: FormRules = {
  productName: [
    { required: true, message: '请输入产品名称', trigger: 'blur' },
    { min: 2, max: 50, message: '长度在 2 到 50 个字符', trigger: 'blur' }
  ],
  price: [
    { required: true, message: '请输入价格', trigger: 'blur' },
    { type: 'number', min: 0, message: '价格不能为负数', trigger: 'blur' }
  ]
}
```

### 8.2 加载状态

根据数据加载的时长和场景，使用不同的加载状态展示：

| 场景 | 组件 | 说明 |
|------|------|------|
| 页面首次加载 | Skeleton 骨架屏 | 模拟页面结构，减少视觉跳动 |
| 数据刷新 | Loading 遮罩 | 在数据区域显示半透明遮罩 |
| 按钮操作 | Button Loading | 按钮内显示 loading 图标，禁用点击 |
| 异步小块内容 | Spinner | 小型旋转图标，适用于局部加载 |

**Skeleton 使用原则**：

- 骨架屏形状应与实际内容结构一致
- 使用动画效果提示加载中状态
- 数据加载完成后平滑过渡到真实内容

### 8.3 空状态

当页面或区域没有数据时，使用 `EmptyState` 组件展示：

- 显示空状态图标和提示文字
- 提供引导操作按钮（如"新增第一条数据"）
- 区分"无数据"和"无权限"两种空状态

```vue
<EmptyState
  description="暂无产品数据"
  action-text="新增产品"
  @action="handleCreate"
/>
```

### 8.4 错误提示

错误提示根据严重程度和场景选择不同的展示方式：

| 错误类型 | 展示方式 | 示例 |
|---------|---------|------|
| 操作失败 | ElMessage.error | 删除失败、保存失败 |
| 表单验证 | 字段下方红色文字 | 必填项为空、格式错误 |
| 页面级错误 | 页面内错误提示区 | 数据加载失败 |
| 网络错误 | ElNotification | 请求超时、网络断开 |
| 系统错误 | 全局错误页面 | 500 错误、服务不可用 |

**错误提示原则**：

- 错误信息使用中文，语言友好，避免技术术语
- 提示用户可采取的后续操作
- 同一错误不重复弹出提示

### 8.5 确认操作

涉及数据变更的操作（删除、批量操作、不可逆操作）必须弹出确认对话框：

```vue
<el-popconfirm
  title="删除后数据将无法恢复，确认要删除该产品吗？"
  confirm-button-text="确认删除"
  cancel-button-text="取消"
  @confirm="handleDelete"
/>
```

**确认对话框使用场景**：

- 删除操作（单条/批量）
- 状态变更（启用/禁用）
- 数据导出（大量数据时确认）
- 不可逆操作

### 8.6 批量操作

列表页支持批量操作时，遵循以下交互规范：

- 表格首列显示复选框，支持全选和单选
- 选中数据后，表格上方或下方显示批量操作栏
- 批量操作栏显示已选数量和可用操作按钮
- 批量操作前弹出确认对话框，显示影响的数据条数
- 操作完成后清除选中状态

```vue
<BatchActionBar
  :selected-count="selectedRows.length"
  :actions="batchActions"
  @action="handleBatchAction"
  @clear="clearSelection"
/>
```

.search-form {

@media (min-width: 1024px) { .show-md { display: block; } }   /* 桌面显示 */

## 十、组件三级分层标准【强制】

### 10.1 分层定义

| 层级 | 目录 | 职责 | 依赖规则 |
|------|------|------|---------|
| core（基础层） | `src/components/core/` | 与业务无关的纯UI组件 | 不依赖任何业务模块 |
| business（业务层） | `src/components/business/` | 跨模块共享的业务组件 | 可依赖core层 |
| modules（模块层） | `src/views/{module}/components/` | 模块专属组件 | 可依赖core和business层 |

### 10.2 core层组件标准

core层组件必须满足：
- 与具体业务无关，可在任何项目中复用
- 通过props接收所有数据，不依赖Store/API
- 不包含业务逻辑，只负责UI展示和交互
- 当前 `src/components/core/` 中的以下组件属于core层：
  - ContentCard, PageHeader, DataTable, SearchPanel, EmptyState, StatCard

### 10.3 business层组件标准

business层组件必须满足：
- 跨2个以上模块共享使用
- 包含特定业务逻辑（如权限判断、数据格式化）
- 可依赖Store/API，但必须通过props或composable注入
- 示例：EmployeeSelector（人事+采购+仓储共用）、DepartmentTree（多模块共用）

### 10.4 modules层组件标准

模块专属组件放在 `src/views/{module}/components/` 目录下：
- 只在本模块内使用
- 可以自由依赖本模块的Store/API
- 如果被其他模块引用，应提升为business层

### 10.5 迁移计划

当前 `src/components/core/` 目录存放基础层组件，`src/components/business/` 目录存放业务层组件：
- 第一阶段：创建 `core/` 和 `business/` 目录，新组件按标准放置
- 第二阶段：将现有 common/ 组件迁移到对应层级
- 第三阶段：删除 common/ 目录
