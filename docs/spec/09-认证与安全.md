# 认证与安全规范

## 一、认证体系

### 1.1 JWT认证

#### 1.1.1 Token结构

```json
{
  "sub": "用户ID",
  "username": "用户名",
  "roles": ["角色编码列表"],
  "permissions": ["权限编码列表"],
  "storeId": "所属门店ID",
  "iat": 签发时间,
  "exp": 过期时间
}
```

#### 1.1.2 签名算法与密钥

| 配置项 | 值 |
|-------|-----|
| 签名算法 | HS512 |
| 密钥长度 | 至少512位（Base64编码） |
| Access Token有效期 | 30分钟 |
| Refresh Token有效期 | 7天 |
| 密钥存储 | 配置文件加密存储，生产环境使用环境变量注入 |

#### 1.1.3 Token黑名单（Redis）

- **用途**：用户主动登出、密码修改、账号禁用时，将未过期的Token加入黑名单
- **存储结构**：

```
键: token:blacklist:{jti}
值: 1
过期时间: Token剩余有效期
```

- **验证流程**：每次请求校验Token时，先检查黑名单，若存在则拒绝访问
- **批量清除**：用户修改密码或被禁用时，清除该用户所有Token

#### 1.1.4 刷新令牌

- **刷新机制**：Access Token过期后，前端使用Refresh Token请求 `/api/v1/auth/refresh` 获取新的Access Token
- **刷新策略**：
  - 每次刷新后生成新的Refresh Token，旧Refresh Token立即失效
  - Refresh Token仅允许使用一次，防止重放攻击
  - 同一用户同时有效的Refresh Token数量限制为5个
- **存储方式**：Refresh Token的jti存储在Redis中，用于校验有效性

#### 1.1.5 None算法攻击防护

- **防护措施**：
  - JWT解析时强制指定签名算法为HS512，禁止从Header中读取算法
  - 拒绝 `alg` 为 `none` 或空的Token
  - 拒绝非对称算法（如RS256）的Token，防止算法混淆攻击
- **代码示例**：

```java
JwtParser parser = Jwts.parserBuilder()
    .setSigningKey(secretKey)
    .build();
// 强制使用HS512，忽略Header中的alg声明
```

### 1.2 MFA多因素认证

#### 1.2.1 TOTP方式

- **算法**：基于时间的一次性密码（TOTP），符合RFC 6238标准
- **参数配置**：

| 配置项 | 值 |
|-------|-----|
| 哈希算法 | HmacSHA1 |
| 时间步长 | 30秒 |
| 验证码位数 | 6位 |
| 允许的时间偏移 | 前后1个时间窗口 |

- **绑定流程**：
  1. 用户请求启用MFA，后端生成密钥（Base32编码）
  2. 后端返回 `otpauth://totp/` 格式的URI
  3. 前端生成二维码，用户使用认证器App扫描
  4. 用户输入验证码完成绑定验证
  5. 生成恢复码（一次性使用），用户妥善保存

- **验证流程**：
  1. 用户输入用户名密码完成第一因素认证
  2. 系统检查用户是否启用MFA
  3. 若已启用，返回 `MFA_REQUIRED` 状态码
  4. 前端展示MFA验证页面
  5. 用户输入TOTP验证码
  6. 后端校验验证码，通过后签发Token

- **恢复码**：
  - 生成10个8位随机恢复码
  - 每个恢复码仅可使用一次
  - 使用后自动标记为已使用
  - 恢复码使用BCrypt加密存储

### 1.3 密码安全

#### 1.3.1 BCrypt加密

- **算法**：BCrypt
- **强度因子**：12（cost = 12）
- **存储格式**：`$2a$12${22字符盐}{31字符哈希}`
- **验证方式**：使用BCrypt的checkpw方法，禁止自行实现比对逻辑

```java
// 加密
String encoded = BCrypt.hashpw(rawPassword, BCrypt.gensalt(12));

// 验证
boolean matched = BCrypt.checkpw(rawPassword, encoded);
```

#### 1.3.2 密码策略

| 策略项 | 规则 |
|-------|------|
| 最小长度 | 8个字符 |
| 最大长度 | 128个字符 |
| 复杂度要求 | 必须包含大写字母、小写字母、数字、特殊字符中的至少3种 |
| 禁止内容 | 不得包含用户名、姓名、手机号 |
| 历史记录 | 新密码不得与最近5次密码相同 |
| 有效期 | 90天（可配置） |
| 提前提醒 | 密码过期前7天提醒 |

- **密码强度评分**：

| 等级 | 条件 |
|------|------|
| 弱 | 长度 < 8 或仅包含1种字符类型 |
| 中 | 长度 >= 8 且包含2种字符类型 |
| 强 | 长度 >= 12 且包含3种字符类型 |
| 非常强 | 长度 >= 16 且包含4种字符类型 |

#### 1.3.3 密码重置流程

1. 用户点击"忘记密码"，输入注册邮箱或手机号
2. 系统生成重置令牌（UUID），有效期30分钟
3. 重置令牌存储在Redis中：`password:reset:{token} -> userId`
4. 系统发送重置链接到邮箱或验证码到手机
5. 用户通过重置链接或验证码验证身份
6. 用户设置新密码，需满足密码策略
7. 重置成功后，清除该用户所有Token，强制重新登录
8. 记录密码重置审计日志

### 1.4 会话管理

#### 1.4.1 UserSession表

| 字段 | 类型 | 说明 |
|------|------|------|
| session_id | VARCHAR(36) | 会话ID（主键） |
| user_id | VARCHAR(36) | 用户ID |
| device_info | VARCHAR(255) | 设备信息 |
| ip_address | VARCHAR(45) | 登录IP地址 |
| login_time | TIMESTAMP | 登录时间 |
| last_access_time | TIMESTAMP | 最后访问时间 |
| expire_time | TIMESTAMP | 过期时间 |
| status | VARCHAR(20) | 会话状态（active/expired/revoked） |
| deleted | INTEGER | 逻辑删除标记 |

#### 1.4.2 并发会话控制

- **最大并发会话数**：同一用户最多允许5个活跃会话
- **策略**：当达到上限时，最早登录的会话被自动踢出
- **通知机制**：被踢出的会话在下次请求时收到 `SESSION_REVOKED` 错误码
- **管理功能**：用户可在个人设置中查看和手动终止其他会话

#### 1.4.3 Token过期自动跳转登录

- **前端处理**：
  - 请求拦截器检测401响应码
  - 尝试使用Refresh Token刷新
  - 刷新失败则清除本地Token，跳转登录页
  - 登录后跳转回原页面（记录 `redirect` 参数）

- **后端处理**：
  - Token过期返回401状态码和 `TOKEN_EXPIRED` 错误码
  - 区分Token过期和Token无效，返回不同的错误码
  - Token过期但Refresh Token有效时，允许刷新

## 二、权限体系（RBAC）

### 2.1 用户-角色-权限三级模型

```
用户(User) --[多对多]--> 角色(Role) --[多对多]--> 权限(Permission)
```

- **用户**：系统使用者，可分配多个角色
- **角色**：权限的集合，代表一类用户的职能
- **权限**：最小授权单元，对应一个具体的操作或资源访问

#### 数据库表设计

| 表名 | 说明 |
|------|------|
| users | 用户表 |
| roles | 角色表 |
| permissions | 权限表 |
| user_roles | 用户-角色关联表 |
| role_permissions | 角色-权限关联表 |

#### 权限编码格式

```
{模块}:{资源}:{操作}
```

示例：

| 权限编码 | 说明 |
|---------|------|
| `trace:food:create` | 创建食品溯源记录 |
| `trace:food:read` | 查看食品溯源记录 |
| `trace:food:update` | 修改食品溯源记录 |
| `trace:food:delete` | 删除食品溯源记录 |
| `trace:food:export` | 导出食品溯源记录 |
| `system:user:manage` | 用户管理 |
| `system:role:manage` | 角色管理 |

### 2.2 角色类型

| 角色编码 | 角色名称 | 说明 |
|---------|---------|------|
| `SUPER_ADMIN` | 超级管理员 | 拥有所有权限，不受数据权限限制 |
| `ADMIN` | 管理员 | 管理公司级别资源和用户 |
| `MANAGER` | 经理 | 管理门店级别资源和员工 |
| `EMPLOYEE` | 员工 | 基本操作权限，仅访问自己创建的数据 |
| `AUDITOR` | 审计员 | 查看审计日志和报表，无修改权限 |
| `VIEWER` | 访客 | 仅查看权限，无任何修改权限 |

### 2.3 数据权限范围（8级）

| 级别 | 编码 | 说明 | 适用角色 |
|------|------|------|---------|
| 1 | `all` | 全部数据 | 超级管理员 |
| 2 | `company` | 本公司数据 | 管理员 |
| 3 | `region` | 本区域数据 | 区域经理 |
| 4 | `stores` | 所属门店数据（多门店） | 多门店经理 |
| 5 | `departments` | 所属部门数据（多部门） | 部门经理 |
| 6 | `store` | 本门店数据 | 门店经理 |
| 7 | `department` | 本部门数据 | 部门主管 |
| 8 | `self` | 仅本人数据 | 普通员工 |

#### 数据权限实现

- 使用 `@RequiresDataScope` 注解标记需要数据权限控制的接口
- 通过MyBatis拦截器自动拼接数据权限SQL条件
- 数据权限范围存储在角色表中，用户继承角色的数据权限范围
- 当用户拥有多个角色时，取最宽的数据权限范围

### 2.4 权限自动分配

- **基于职位角色映射**：创建用户时，根据所选职位自动分配对应角色
- **映射规则**：

| 职位 | 自动分配角色 |
|------|------------|
| 总经理 | ADMIN |
| 区域经理 | MANAGER（数据权限：region） |
| 门店经理 | MANAGER（数据权限：store） |
| 部门主管 | MANAGER（数据权限：department） |
| 普通员工 | EMPLOYEE |

- **变更同步**：用户职位变更时，自动调整角色分配
- **手动覆盖**：管理员可手动调整用户的角色分配，覆盖自动分配结果

### 2.5 权限缓存

#### UserPermissionCacheService

- **缓存结构**：

```
键: user:permissions:{userId}
值: {
  "roles": ["角色编码列表"],
  "permissions": ["权限编码列表"],
  "dataScope": "数据权限范围"
}
过期时间: 1小时
```

- **缓存更新策略**：
  - 用户角色变更时，清除该用户权限缓存
  - 角色权限变更时，清除拥有该角色的所有用户权限缓存
  - 权限变更时，清除所有用户权限缓存
- **缓存击穿防护**：使用互斥锁防止缓存失效时大量请求穿透到数据库

## 三、安全过滤器链

### 3.1 过滤器执行顺序

```
请求 -> RateLimitFilter -> SecurityHeaderFilter -> JwtAuthenticationFilter
     -> MfaAuthenticationFilter -> AnomalyAccessLogFilter -> Controller
```

### 3.2 JwtAuthenticationFilter

- **功能**：JWT Token认证
- **执行逻辑**：
  1. 从请求Header中提取 `Authorization: Bearer {token}`
  2. 解析并验证Token签名和有效期
  3. 检查Token是否在黑名单中
  4. 提取用户信息，构建 `UsernamePasswordAuthenticationToken`
  5. 设置到 `SecurityContextHolder`
- **放行路径**：登录、注册、密码重置、公开API等
- **异常处理**：Token无效返回401，Token过期返回401（附带 `TOKEN_EXPIRED` 错误码）

### 3.3 MfaAuthenticationFilter

- **功能**：MFA多因素认证验证
- **执行逻辑**：
  1. 检查当前用户是否已启用MFA
  2. 若已启用且未完成MFA验证，拦截请求
  3. 返回 `MFA_REQUIRED` 状态码（HTTP 403）
  4. 前端展示MFA验证页面，用户输入验证码后调用MFA验证接口
  5. MFA验证通过后，在Session/Redis中标记MFA已验证
- **放行路径**：MFA验证接口本身、登出接口

### 3.4 RateLimitFilter

- **功能**：API请求限流
- **限流维度**：

| 维度 | 限流规则 | 说明 |
|------|---------|------|
| IP | 100次/分钟 | 单IP全局限流 |
| 用户 | 60次/分钟 | 单用户全局限流 |
| 接口 | 自定义 | 特定接口独立限流 |

- **实现方式**：基于Redis的滑动窗口算法
- **限流响应**：HTTP 429 Too Many Requests
- **特殊接口限流**：

| 接口 | 限流规则 |
|------|---------|
| 登录 | 5次/分钟/IP |
| 密码重置 | 3次/分钟/IP |
| MFA验证 | 10次/分钟/用户 |
| 短信发送 | 1次/分钟/手机号 |

### 3.5 SecurityHeaderFilter

- **功能**：添加安全响应头
- **响应头配置**：

| 响应头 | 值 | 说明 |
|-------|-----|------|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'` | 内容安全策略 |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | HSTS，强制HTTPS |
| `X-Frame-Options` | `DENY` | 禁止iframe嵌入 |
| `X-Content-Type-Options` | `nosniff` | 禁止MIME嗅探 |
| `X-XSS-Protection` | `1; mode=block` | XSS过滤 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Referrer策略 |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | 权限策略 |

### 3.6 AnomalyAccessLogFilter

- **功能**：异常访问检测与记录
- **检测规则**：

| 检测项 | 规则 | 处理方式 |
|-------|------|---------|
| 异常时间段访问 | 非工作时间（0:00-6:00）的敏感操作 | 记录并告警 |
| 短时间多地登录 | 同一用户5分钟内从不同IP登录 | 锁定账号，通知用户 |
| 高频失败请求 | 1分钟内5次以上请求失败 | 临时封禁IP 10分钟 |
| 敏感接口异常调用 | 权限变更、数据导出等接口的异常调用模式 | 记录并告警 |
| 大量数据访问 | 短时间内访问大量不同数据记录 | 记录并告警 |

- **告警机制**：检测到异常时，记录日志并发送告警通知（邮件/短信）

## 四、数据安全

### 4.1 数据脱敏

#### @Desensitize注解

```java
@Desensitize(type = DesensitizeType.NAME)
private String username;
```

#### DesensitizeType枚举

| 类型 | 规则 | 示例 |
|------|------|------|
| `NAME` | 保留姓，名用*替换 | 张** |
| `EMAIL` | 保留首字母和@后域名，其余用*替换 | z***@example.com |
| `PHONE` | 保留前3位和后4位，中间用*替换 | 138****1234 |
| `ID_CARD` | 保留前3位和后4位，中间用*替换 | 110***********1234 |
| `BANK_CARD` | 保留后4位，其余用*替换 | ****1234 |
| `ADDRESS` | 保留省市区，详细地址用*替换 | 北京市朝阳区*** |
| `PASSWORD` | 全部替换为****** | ****** |

#### 脱敏实现

- 使用Jackson自定义序列化器，在DTO序列化时自动脱敏
- 仅在API响应中脱敏，数据库存储原始数据
- 管理员角色可配置是否跳过脱敏

### 4.2 敏感数据加密

#### AesEncryptionUtil

- **算法**：AES-256-GCM
- **密钥管理**：
  - 加密密钥通过配置文件注入，生产环境使用环境变量
  - 密钥定期轮换，旧密钥保留用于解密
  - 密钥版本号附加在密文前，用于识别解密密钥
- **密文格式**：`{版本号}:{IV}:{密文}:{认证标签}`
- **使用场景**：身份证号、银行卡号等高敏感数据

#### @EncryptedString类型处理器

```java
@TableName(autoResultMap = true)
public class Employee {
    @TableField(typeHandler = EncryptedStringTypeHandler.class)
    private String idCard;  // 自动加密存储，自动解密读取
}
```

- MyBatis TypeHandler实现，写入时自动加密，读取时自动解密
- 对应用透明，业务代码无需关心加解密逻辑

### 4.3 敏感操作标记

#### @SensitiveOperation注解

```java
@SensitiveOperation(description = "修改用户密码", riskLevel = RiskLevel.HIGH)
public void changePassword(String userId, String newPassword) {
    // ...
}
```

#### RiskLevel枚举

| 级别 | 说明 | 审计要求 |
|------|------|---------|
| `LOW` | 低风险操作 | 记录操作日志 |
| `MEDIUM` | 中风险操作 | 记录详细日志，含变更前后数据 |
| `HIGH` | 高风险操作 | 记录详细日志，含变更前后数据，发送告警通知 |
| `CRITICAL` | 关键操作 | 记录详细日志，含变更前后数据，发送告警通知，需二次确认 |

- **二次确认机制**：CRITICAL级别操作需前端弹出确认对话框，用户确认后携带确认令牌提交
- **告警通知**：HIGH及以上级别操作触发邮件/站内信通知管理员

### 4.4 XSS防护

#### 后端防护

- **输入过滤**：对所有用户输入进行HTML转义，使用OWASP Java HTML Sanitizer
- **输出编码**：根据输出上下文（HTML/JavaScript/URL/CSS）进行相应编码
- **Content-Type校验**：确保响应的Content-Type正确设置

#### 前端防护（xss-protection.ts工具）

```typescript
/**
 * XSS防护工具
 */

// HTML转义
function escapeHtml(text: string): string

// URL编码
function encodeUrl(url: string): string

// JavaScript字符串编码
function escapeJsString(text: string): string

// 清除HTML标签
function stripHtmlTags(html: string): string

// 安全的HTML渲染（白名单过滤）
function sanitizeHtml(html: string): string
```

- **使用规范**：
  - 所有用户输入在渲染到页面前必须经过转义
  - 禁止使用 `v-html` 渲染用户输入，除非经过sanitize处理
  - URL参数必须经过编码
  - 动态构建的JavaScript字符串必须经过转义

## 五、审计与监控

### 5.1 @AuditLog注解

```java
@AuditLog(
    module = "用户管理",
    action = "修改密码",
    type = AuditType.UPDATE,
    riskLevel = RiskLevel.HIGH
)
public void changePassword(String userId, String newPassword) {
    // ...
}
```

#### AuditType枚举

| 类型 | 说明 |
|------|------|
| `CREATE` | 创建操作 |
| `READ` | 读取操作（仅敏感数据读取） |
| `UPDATE` | 更新操作 |
| `DELETE` | 删除操作 |
| `LOGIN` | 登录操作 |
| `LOGOUT` | 登出操作 |
| `EXPORT` | 数据导出 |
| `IMPORT` | 数据导入 |
| `GRANT` | 权限授予 |
| `REVOKE` | 权限撤销 |

### 5.2 AuditLogAspect切面

- **拦截方式**：AOP环绕通知，拦截所有标注 `@AuditLog` 的方法
- **记录内容**：

| 字段 | 说明 |
|------|------|
| audit_id | 审计日志ID |
| module | 操作模块 |
| action | 操作动作 |
| type | 操作类型 |
| operator_id | 操作人ID |
| operator_name | 操作人姓名 |
| ip_address | 操作IP地址 |
| user_agent | 用户代理 |

## 六、前端安全

### 6.1 Token管理

- **存储位置**：localStorage
- **存储Key**：`token`
- **Token结构**：

```typescript
interface TokenInfo {
  accessToken: string;
  refreshToken: string;
  expiresAt: number;  // 过期时间戳
}
```

- **安全措施**：
  - Token不存储在Cookie中，防止CSRF攻击
  - Token不存储在sessionStorage中，确保同域多标签页共享
  - 登出时清除localStorage中的Token

### 6.2 Token自动刷新

- **刷新时机**：Access Token过期前5分钟主动刷新
- **刷新流程**：
  1. 请求拦截器检查Token是否即将过期
  2. 若即将过期，先发送刷新请求
  3. 刷新成功后更新本地Token，再发送原请求
  4. 刷新失败则跳转登录页
- **并发处理**：多个请求同时触发刷新时，仅发送一次刷新请求，其他请求等待刷新结果
- **刷新失败处理**：清除Token，跳转登录页，提示"登录已过期"

### 6.3 401自动跳转登录

```typescript
// 响应拦截器
responseInterceptor.onError((error) => {
  if (error.response?.status === 401) {
    const errorCode = error.response.data?.code;
    if (errorCode === 'TOKEN_EXPIRED') {
      // 尝试刷新Token
      return refreshTokenAndRetry(error);
    }
    // 刷新失败或Token无效，跳转登录
    clearToken();
    router.push({
      path: '/login',
      query: { redirect: router.currentRoute.value.fullPath }
    });
  }
});
```

