# 编码规范

## 一、通用编码原则

### 1.1 注释规范

- 统一使用中文注释
- 为复杂逻辑和公共接口添加注释
- 注释应简洁明了，避免冗余
- 注释应描述"为什么"而非"是什么"
- 代码变更时同步更新相关注释

### 1.2 代码整洁

- 避免冗余代码，定期清理未使用的导入和变量
- 遵循DRY原则（Don't Repeat Yourself），提取公共逻辑
- 保持函数短小，单一职责
- 避免过深的嵌套，建议不超过3层
- 使用有意义的命名，避免缩写（除广泛认知的缩写外）

### 1.3 版本控制

- 频繁提交，小步前进
- 每次提交只做一件事
- 提交前确保编译通过、测试通过
- 不提交临时文件和调试代码

## 二、Java编码规范

### 2.5 Lombok使用规范

**Lombok已禁用，必须手写getter/setter/toString**

```java
// 禁止使用
@Data
@Getter
@Setter
@ToString
@NoArgsConstructor
@AllArgsConstructor

// 必须手写
public class Employee {
    private String employeeId;
    private String name;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    @Override

        return "Employee{" +
                "employeeId='" + employeeId + '\'' +
                ", name='" + name + '\'' +
```

### 2.6 实体类规范

```java
/**
 * 员工实体类
 */
@TableName("employees")
public class Employee extends BaseEntity {

    /** 员工ID */
    @TableId(value = "employee_id", type = IdType.ASSIGN_ID)
    private String employeeId;

    /** 员工姓名 */
    @TableField("name")
    private String name;

    /** 部门ID */
    @TableField("department_id")
    private String departmentId;

    /** 逻辑删除标记：0-未删除，1-已删除 */
    @TableLogic
    @TableField("deleted")
    private Integer deleted;

    // getter/setter/toString 手写
}
```

实体类要求：

- 继承 `BaseEntity`（包含 `createTime`、`updateTime` 字段）
- 使用 `@TableName` 注解指定表名
- 使用 `@TableId` 注解指定主键，推荐使用 `ASSIGN_ID` 策略
- 使用 `@TableField` 注解指定字段映射
- 使用 `@TableLogic` 注解标记逻辑删除字段
- 主键格式：`{table}_id`，如 `employee_id`


DTO要求：

- 命名格式：`{Entity}CreateDTO`、`{Entity}UpdateDTO`、`{Entity}BasicInfo`
- 使用 `@Valid` 注解配合Spring进行参数校验
- 使用 `@NotBlank`、`@Size`、`@Pattern` 等注解定义校验规则
- DTO与实体类分离，不直接暴露实体类

### 2.8 Service规范

```java
/**
 * 员工服务接口
 */
public interface EmployeeService {
```

Service要求：

- 接口与实现分离
- 使用构造函数注入依赖，禁止使用 `@Autowired` 字段注入

- 只读操作使用 `@Transactional(readOnly = true)`

### 2.9 Controller规范

```java
/**
 * 员工管理控制器
 */
@RestController
@RequestMapping("/api/v1/employees")
@Tag(name = "员工管理", description = "员工增删改查接口")
public class EmployeeController {

    private final EmployeeService employeeService;

    /**
     * 构造函数注入依赖
     */
    public EmployeeController(EmployeeService employeeService) {
        this.employeeService = employeeService;
    }

    /**
     * 创建员工
     */
    @PostMapping
    @Operation(summary = "创建员工")
    public Result<EmployeeBasicInfo> createEmployee(
            @Valid @RequestBody EmployeeCreateDTO dto) {
        EmployeeBasicInfo employee = employeeService.createEmployee(dto);
        return Result.success(employee);
    }

    /**
     * 根据ID查询员工
     */
    @GetMapping("/{employeeId}")
    @Operation(summary = "根据ID查询员工")
    public Result<EmployeeBasicInfo> getEmployeeById(
            @PathVariable String employeeId) {
        EmployeeBasicInfo employee = employeeService.getEmployeeById(employeeId);
        return Result.success(employee);
    }
}
```

Controller要求：

- 使用 `@RestController` 和 `@RequestMapping`
- 使用 `@Operation` 添加API文档注解
- 使用DTO接收请求参数，使用 `@Valid` 验证
- 返回统一的 `Result<T>` 对象
- 禁止在Controller中直接注入Mapper
- 禁止在Controller中编写业务逻辑

### 2.10 数据访问层规范

```java
/**
 * 架构层次
 * Controller -> Service接口 -> ServiceImpl实现 -> Mapper -> 数据库
 */

/**
 * 员工Mapper接口
 */
@Mapper
public interface EmployeeMapper extends BaseMapper<Employee> {

    /**
     * 根据部门ID查询员工列表
     * @param departmentId 部门ID
     * @return 员工列表
     */
    @Select("SELECT * FROM employees WHERE department_id = #{departmentId}")
    List<Employee> selectByDepartmentId(@Param("departmentId") String departmentId);
}
```

数据访问层要求：

- 继承 `BaseMapper<T>`，使用MyBatis Plus提供的CRUD方法
- 复杂查询使用 `@Select` 等注解或XML映射文件
- 禁止在查询条件中手动添加 `deleted = 0`，由 `@TableLogic` 自动处理
- 使用 `@Param` 注解命名参数

### 2.11 Java禁止事项

| 序号 | 禁止事项 | 说明 |
|------|---------|------|
| 1 | 禁止使用物理删除 | 使用逻辑删除，`@TableLogic` 自动处理 |
| 2 | 禁止在查询中手动添加deleted条件 | 由MyBatis Plus `@TableLogic` 自动处理 |
| 3 | 禁止直接返回异常信息给前端 | 使用全局异常处理器，返回统一错误格式 |
| 4 | 禁止在Controller中直接注入Mapper | 必须通过Service层访问数据 |
| 5 | 禁止硬编码业务逻辑 | 使用配置文件或常量管理业务规则 |

## 三、TypeScript编码规范

### 3.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 接口 | PascalCase | `EmployeeFormData`、`TraceQueryResult` |
| 枚举 | PascalCase | `EmployeeStatus`、`TraceType` |
| 类 | PascalCase | `EmployeeDataConverter`、`DateFormatter` |
| 变量 | camelCase | `employeeList`、`totalCount` |
| 函数 | camelCase | `formatDate`、`validateForm` |
| 常量 | UPPER_SNAKE_CASE | `API_BASE_URL`、`MAX_RETRY_COUNT` |
| 文件 | kebab-case | `employee-api.ts`、`date-utils.ts` |
| 类型文件 | 与内容一致 | `api.ts`（类型定义集中管理） |

### 3.2 类型定义规范

**禁止使用any类型，必须定义明确类型**

```typescript
// 禁止
const data: any = response;
function process(item: any): any { }

// 正确 - 使用具体类型
const data: EmployeeBasicInfo = response;
function process(item: EmployeeFormData): EmployeeBasicInfo { }

// 当类型不确定时，使用unknown替代any
function processUnknown(value: unknown): string {
    if (typeof value === 'string') {
        return value.toUpperCase();
    }
    return String(value);
}
```

### 3.3 类型定义管理

类型定义统一管理在 `types/` 目录：

```typescript
// types/api.ts - 统一API响应类型
/** 统一API响应结构 */
interface ApiResponse<T> {
    code: number;
    message: string;
    data: T;
}

/** 分页响应结构 */
interface PageResponse<T> {
    records: T[];
    total: number;
    current: number;
    size: number;
    pages: number;
}

// types/employee.ts - 员工相关类型
/** 员工表单数据 */
interface EmployeeFormData {
    name: string;
    departmentId: string;
    phone: string;
    status: EmployeeStatus;
}

/** 员工查询表单 */
interface EmployeeQueryForm {
    keyword?: string;
    departmentId?: string;
    status?: EmployeeStatus;
    page: number;
    size: number;
}

/** 员工状态枚举 */
enum EmployeeStatus {
    ACTIVE = 'active',
    INACTIVE = 'inactive',
    PROBATION = 'probation'
}
```

### 3.4 接口优先原则

**优先使用interface而非type**

```typescript
// 推荐 - 使用interface
interface EmployeeBasicInfo {
    employeeId: string;
    name: string;
    departmentName: string;
}

// 不推荐 - 使用type（除非需要联合类型、交叉类型等高级特性）
type EmployeeBasicInfo = {
    employeeId: string;
    name: string;
    departmentName: string;
}

// type适用场景：联合类型、工具类型
type Status = 'active' | 'inactive' | 'probation';
type Nullable<T> = T | null;
```

|------|---------|------|

## 四、Vue组件编码规范

### 4.1 组件命名

- 组件名使用PascalCase：`FinanceReportHeader`
- 文件名与组件名一致：`FinanceReportHeader.vue`
- 页面级组件放在 `views/` 目录
- 功能组件放在 `components/` 目录
- core层组件放在 `components/core/` 目录，business层组件放在 `components/business/` 目录

### 4.2 组件结构

```vue
<!-- 1. script setup 部分 -->
<script setup lang="ts">
import { ref, computed, onMounted } from 'vue';
import type { FormInstance } from 'element-plus';
import EmployeeForm from './EmployeeForm.vue';
import { employeeApi } from '@/api/employee-api';
import type { EmployeeFormData, EmployeeBasicInfo } from '@/types/employee';

/** 组件属性定义 */
const props = defineProps<{
    departmentId: string;
    readonly?: boolean;
}>();

/** 组件事件定义 */
const emit = defineEmits<{
    (e: 'submit', data: EmployeeFormData): void;
    (e: 'cancel'): void;
}>();

/** 响应式数据 */
const loading = ref<boolean>(false);
const employeeList = ref<EmployeeBasicInfo[]>([]);

/** 计算属性 */
const totalCount = computed<number>(() => employeeList.value.length);

/** 方法 */
async function fetchEmployees(): Promise<void> {
    loading.value = true;
    try {
        const response = await employeeApi.getList({
            departmentId: props.departmentId,
            page: 1,
            size: 20
        });
        employeeList.value = response?.records || [];
    } catch (error: unknown) {
        if (error instanceof Error) {
            console.error('获取员工列表失败:', error.message);
        }
    } finally {
        loading.value = false;
    }
}

/** 生命周期 */
onMounted(() => {
    fetchEmployees();
});
</script>

<!-- 2. template 部分 -->
<template>
    <div class="employee-list">
        <div class="employee-list__header">
            <h3>员工列表</h3>
            <span class="employee-list__count">共 {{ totalCount }} 人</span>
        </div>
        <el-table :data="employeeList" v-loading="loading">
            <el-table-column prop="name" label="姓名" />
            <el-table-column prop="departmentName" label="部门" />
        </el-table>
    </div>
</template>

<!-- 3. style 部分 -->
<style scoped>
.employee-list {
    padding: 16px;
}

.employee-list__header {
    display: flex;
    justify-content: space-between;
    align-items: center;
    margin-bottom: 16px;
}

.employee-list__count {
    color: var(--fts-text-secondary);
    font-size: 14px;
}
</style>
```

### 4.3 组件顺序

Vue单文件组件中各部分的顺序：

1. `<script setup>` - 逻辑部分
2. `<template>` - 模板部分
3. `<style scoped>` - 样式部分

### 4.4 Props定义

使用 `defineProps` 配合TypeScript类型定义：

```typescript
// 推荐 - 使用TypeScript类型声明
const props = defineProps<{
    employeeId: string;
    mode: 'create' | 'edit' | 'view';
    loading?: boolean;
}>();

// 带默认值
const props = withDefaults(defineProps<{
    employeeId: string;
    mode?: 'create' | 'edit' | 'view';
    loading?: boolean;
}>(), {
    mode: 'create',
    loading: false
});
```

### 4.5 Emits定义

使用 `defineEmits` 配合TypeScript类型定义：

```typescript
// 推荐 - 使用TypeScript类型声明
const emit = defineEmits<{
    (e: 'submit', data: EmployeeFormData): void;
    (e: 'cancel'): void;
    (e: 'delete', id: string): void;
}>();
```

### 4.6 组件样式

- 所有组件样式必须使用 `scoped` 属性
- 使用BEM命名规范：`block__element--modifier`
- 使用CSS变量引用主题色和通用样式
- 组件文件不超过1000行

### 4.7 组件拆分规则

| 组件类型 | 职责 | 位置 |
|---------|------|------|
| 页面级组件 | 整体布局和组件组合 | `views/` |
| 功能组件 | 独立的功能模块 | `components/` |
| core层组件 | 纯UI组件 | `components/core/` |
| business层组件 | 跨模块业务组件 | `components/business/` |
| 布局组件 | 页面布局结构 | `layouts/` |

拆分原则：

- 单个组件不超过1000行
- 页面级组件仅负责布局和组件组合，不包含具体业务逻辑
- 复杂功能拆分为独立子组件
- 复杂状态使用Pinia store管理

## 六、数据库编码规范

### 6.1 表命名规范

- 表名使用小写+下划线：`employees`、`food_trace`
- 关联表命名：`{table1}_{table2}`，如 `employee_role`
- 禁止使用数据库保留字作为表名

### 6.2 字段命名规范

- 字段名使用下划线命名（数据库层）：`create_time`、`department_id`
- 主键格式：`{table}_id`，如 `employee_id`
- 外键格式：`{referenced_table}_id`，如 `department_id`
- 时间字段格式：`{action}_time`，如 `create_time`、`update_time`
- 布尔字段格式：`is_{description}`，如 `is_active`
- 禁止使用数据库保留字作为字段名

### 6.3 必要字段

每张表必须包含以下字段：

```sql
CREATE TABLE example (
    example_id    VARCHAR(32)   NOT NULL,
    -- 业务字段 ...
    create_time   TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted       INTEGER       NOT NULL DEFAULT 0,
    CONSTRAINT example_pkey PRIMARY KEY (example_id)
);
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `{table}_id` | VARCHAR(32) / SERIAL | 主键 |
| `create_time` | TIMESTAMP | 创建时间 |
| `update_time` | TIMESTAMP | 更新时间 |
| `deleted` | INTEGER | 逻辑删除标记：0-未删除，1-已删除 |

### 6.4 索引规范

| 索引类型 | 命名格式 | 示例 |
|---------|---------|------|
| 主键索引 | `{table}_pkey` | `employees_pkey` |
| 唯一索引 | `uk_{table}_{field}` | `uk_employees_phone` |
| 普通索引 | `idx_{table}_{field}` | `idx_employees_department_id` |
| 组合索引 | `idx_{table}_{field1}_{field2}` | `idx_employees_dept_status` |

索引原则：

- 禁止创建冗余索引
- 频繁查询的字段建立索引
- 外键字段建立索引
- 组合索引遵循最左前缀原则
- 避免在低基数列上创建索引

### 6.5 字段类型映射

| PostgreSQL | Java | 前端TypeScript |
|------------|------|---------------|
| VARCHAR | String | string |
| INTEGER | Integer | number |
| BIGINT | Long | number |
| DECIMAL/NUMERIC | BigDecimal | number |
| TIMESTAMP | LocalDateTime | string (ISO 8601) |
| DATE | LocalDate | string (YYYY-MM-DD) |
| BOOLEAN | Boolean | boolean |
| JSONB | String/Object | object |

### 6.6 数据库禁止事项

| 序号 | 禁止事项 | 说明 |
|------|---------|------|
| 1 | 禁止创建冗余索引 | 避免影响写入性能和增加存储开销 |
| 2 | 禁止使用保留字作为表名/字段名 | 避免SQL语法冲突 |
| 3 | 禁止缺少必要的时间字段 | 每张表必须有 `create_time`、`update_time` |
| 4 | 禁止缺少deleted字段 | 每张表必须有 `deleted` 字段用于逻辑删除 |

## 十、代码审查流程【强制】

### 10.1 审查角色

| 角色 | 职责 |
|------|------|
| 提交者 | 编写代码、自测、提交PR |
| 审查者 | 审查代码质量、规范合规性 |
| 合并者 | 确认审查通过后合并代码 |

### 10.2 审查触发条件

- 所有非main分支的合并请求必须经过审查
- 单次PR变更超过500行需指定2名审查者
- 涉及安全/权限相关代码需安全审查者参与

### 10.3 审查流程

1. 提交者创建PR，填写变更说明
2. 自动化门禁检查（CI）通过
3. 审查者按审查清单逐项检查
4. 审查结果：通过 / 需修改 / 驳回
5. 需修改：提交者修改后重新提交审查
6. 通过：合并者合并代码

### 10.4 审查SLA

| PR变更行数 | 审查响应时间 |
|-----------|------------|
| < 100行 | 4小时内 |
| 100-500行 | 8小时内 |
| > 500行 | 24小时内 |

### 10.5 审查指标

- 审查覆盖率：目标100%
- 平均审查时长：目标<8小时
- 驳回率：目标<20%
