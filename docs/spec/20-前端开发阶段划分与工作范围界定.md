## 六、✅ 技术决策记录（Phase 0固化）

> 以下决策已在Phase 0期间明确，后续开发必须严格遵守。如需变更，需通过正式流程审批。

### 决策1：图表库选型
| 项目 | 决策 | 理由 | 生效时间 |
|------|------|------|---------|
| **当前方案** | **纯CSS模拟**（FinancePage柱状图） | Phase 0/1无需真实图表；CSS模拟足够展示布局标准 | ✅ 当前 |
| **P2引入方案** | ECharts 5.x（按需加载） | 功能强大、社区活跃、支持深色模式；通过import()动态导入避免增大Bundle | 🔜 Phase 2 |
| **否决方案** | Chart.js、D3.js、纯手写Canvas | Chart.js功能不足；D3.js学习成本高；手写不维护 | ❌ 不采用 |

### 决策2：表单验证方案
| 项目 | 决策 | 理由 |
|------|------|------|
| **基础验证** | **Element Plus内置Form Rules** | 与UI框架一致，减少依赖，学习成本低 |
| **复杂验证** | **Zod（TypeScript优先）** | 类型安全，与TS生态完美集成，可生成类型定义 |
| **特殊验证** | 自定义Validator函数（如工号唯一性） | 业务逻辑无法通用化 |

### 决策3：状态管理架构
| 项目 | 决策 | 说明 |
|------|------|------|
| **全局Store** | **layoutStore.ts（已存在）** | 侧边栏折叠、主题切换等全局状态 |
| **模块Store** | **按业务模块拆分**（如employeeStore, financeStore） | 每个Demo页面或业务模块独立store |
| **组件内状态** | **ref/reactive为主** | 组件内部临时状态不需要提升到store |
| **持久化策略** | **localStorage仅用于token和主题偏好** | 其他数据从API获取，不本地缓存 |

### 决策4：Mock数据管理策略
| 项目 | 决策 | 生效时间 |
|------|------|---------|
| **当前方案** | **内置Mock数据（组件内部硬编码）** | ✅ Phase 0-1 |
| **P2方案** | **统一`src/mock/`目录 + Mock API层** | 🔜 Phase 2 |
| **P3方案** | **MSW (Service Worker) 拦截API请求** | ⏳ Phase 3（如需要） |
| **否决方案** | JSON Server（需额外进程）、MSW过早引入（增加复杂度） | ❌ 不采用 |

### 决策5：TypeScript严格度
| 项目 | 决策 |
|------|------|
| strict模式 | ✅ **保持开启** (noImplicitAny=true, strictNullChecks=true) |
| any使用 | ⚠️ **允许但必须注释说明原因**（第三方库类型缺失等特殊情况） |
| 类型定义位置 | ✅ **统一在 `src/types/` 目录** |
| 接口优先 | ✅ **优先使用interface**（对象结构）；type用于联合/交叉类型 |

### 决策6：组件库选型
| 层级 | 方案 | 说明 |
|------|------|------|
| L3-Core基础组件 | **自研 + Element Plus封装** | PageHeader/StatCard/StatusTag等为自研；DataTable基于el-table封装 |
| L3-Business业务组件 | **按需自研** | 食品溯源特有组件（溯源链/二维码）在Phase 3开发 |
| 通用UI组件 | **直接使用 Element Plus** | Button/Input/Select/Dialog等直接使用，不做二次封装 |
| 图标库 | **@element-plus/icons-vue** | 统一使用Element Plus图标集 |

### 决策7：深色模式触发机制
| 项目 | 决策 | 实现时机 |
|------|------|---------|
| **触发方式** | **JavaScript动态切换 `document.documentElement.classList.toggle('dark')`** | Phase 1 |
| **持久化** | **localStorage key: 'theme-preference'** | Phase 1 |
| **跟随系统** | **可选：监听 `prefers-color-scheme` 媒体查询** | Phase 2 |
| **UI入口** | **PageHeader区域或设置抽屉中的主题切换按钮** | Phase 1 |
| **CSS变量覆盖** | **_dark-mode.scss 已完整实现990行** | ✅ 已完成 |

### 决策8：路由规范（预留）
| 项目 | 决策 | 说明 |
|------|------|------|
| 路由文件位置 | `src/router/index.ts` | 集中管理 |
| 路由命名 | kebab-case（如 `/employee-management`） | URL友好 |
| 懒加载 | ✅ **所有页面级路由使用 `() => import()`** | 性能优化 |
| 路由守卫 | ⏳ **待实现（Phase 3）** | 权限控制 |
| 布局嵌套 | MainLayout → router-view | 单层布局 |

### 决策9：API调用规范（已确定）
| 项目 | 决策 | 文件位置 |
|------|------|---------|
| 请求实例 | **必须使用 `src/api/request.ts` 导出的request实例** | 禁止直接axios/fetch |
| 参数传递 | GET用params对象；POST用data对象 | 禁止{ params: { } }嵌套 |
| Token处理 | 请求拦截器自动添加 | 禁止手动添加Authorization |
| 响应处理 | 响应拦截器已提取.data | 禁止再访问.data属性 |

## 八、FAQ：常见疑问解答

### Q1: 为什么现在不修复ModernEmployee的空壳CRUD？
**A**: 因为CRUD属于"页面具体内容和交互细节"，按照"先框架后内容"的原则，应放在Phase 2。现在修复会导致：
- 分散对"框架标准"的注意力
- 可能引入未经标准化的临时方案
- 浪费时间在可能被重构的代码上

### Q2: 为什么不现在引入ECharts？
**A**: 图表库选型属于"技术决策"，应在Phase 1的组件建设中评估。现在引入会：
- 增加Bundle Size（影响性能预算评估）
- 引入额外的学习成本和维护负担
- 可能与未来的图表组件标准化冲突

### Q3: Phase 0完成后，我们会有什么？
**A**: 一套**完整的、经过验证的、可直接指导开发的**前端标准体系：
- ✅ 所有视觉参数已确定（颜色/字体/间距/圆角...）
- ✅ 所有布局结构已标准化（7层DOM模板）
- ✅ 所有响应式规则已明确（3断点适配）
- ✅ 所有核心组件规格已文档化（5个组件）
- ✅ 所有数据格式已统一（状态/金额/日期/分页）
- ✅ 27项检查清单可供智能体执行
- ✅ 清晰的阶段划分指导后续工作

### Q4: 如果在Phase 0中发现需要调整某个标准怎么办？
**A**: 这是完全正常且预期的！标准的价值在于"被遵守"而非"永不改变"。流程是：
1. 发现需要调整 → 记录在案
2. 评估影响范围（影响多少页面/组件）
3. 同步更新19手册和相关文档
4. 在变更日志中记录原因
5. 通知团队（如有）

## 九、结论

### 当前阶段的唯一聚焦点

> **"建立不可动摇的前端基础设施标准"**
>
> 具体来说就是：
