# 数据库设计规范

## 一、数据库选型决策

### 1.1 环境配置

| 环境 | 数据库 | 说明 |
|------|--------|------|
| 生产环境 | PostgreSQL 18 | 企业级关系型数据库，支持高级特性 |
| 开发环境 | H2内存数据库（MODE=PostgreSQL兼容模式） | 零配置启动，与生产环境语法一致，便于本地开发和自动化测试 |

### 1.2 PostgreSQL选型理由

| 能力维度 | 具体优势 |
|----------|----------|
| JSONB支持 | 原生JSONB类型，支持索引和高效查询，适用于灵活的配置存储和扩展字段 |
| 数组类型 | 原生数组类型支持，避免关联表的过度设计，适用于标签、附件列表等场景 |
| 全文搜索 | 内置全文搜索引擎（tsvector/tsquery），无需引入Elasticsearch即可满足中等规模搜索需求 |
| 事务完整性 | 完整的ACID事务支持、多版本并发控制（MVCC），保障数据一致性 |
| 合规性 | 符合SQL标准，支持行级安全（RLS），满足食品安全溯源的合规审计要求 |
| 扩展生态 | 丰富的扩展生态（pg_trgm、pgcrypto、uuid-ossp等），减少自研成本 |

### 1.3 H2开发环境说明

- 使用PostgreSQL兼容模式，确保SQL语法与生产环境一致
- 开发环境H2用于快速启动和单元测试，不依赖外部数据库服务
- 生产环境必须使用PostgreSQL，H2不保证与PostgreSQL的完全兼容

## 二、表设计规范

### 2.1 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 表名 | 小写+下划线 | `employees`, `food_trace`, `purchase_order` |
| 主键 | `{table}_id`格式 | `employee_id`, `food_id`, `order_id` |
| 外键 | `{referenced_table}_id`格式 | `department_id`, `supplier_id` |
| 时间字段 | `{action}_time`格式 | `create_time`, `update_time`, `delete_time` |
| 状态字段 | 语义化命名 | `order_status`, `payment_status` |
| 布尔字段 | `is_`前缀或语义化 | `is_active`, `deleted` |

### 2.2 主键策略

| 策略 | 适用场景 | 语法 |
|------|----------|------|
| 自增整数 | 内部表、无分布式需求 | `GENERATED ALWAYS AS IDENTITY` |
| VARCHAR雪花算法 | 需要分布式唯一ID、对外暴露的ID | `VARCHAR(32)`，应用层生成 |

```sql
-- 自增主键示例
CREATE TABLE departments (
    department_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    department_name VARCHAR(100) NOT NULL
);

-- 雪花算法主键示例
CREATE TABLE orders (
    order_id VARCHAR(32) PRIMARY KEY,
    order_status VARCHAR(20) NOT NULL
);
```

### 2.3 必备字段

每张业务表必须包含以下三个字段：

| 字段名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `create_time` | TIMESTAMP | `CURRENT_TIMESTAMP` | 记录创建时间 |
| `update_time` | TIMESTAMP | `CURRENT_TIMESTAMP` | 记录更新时间 |
| `deleted` | INTEGER | `0` | 逻辑删除标记，0未删除，1已删除 |

```sql
-- 必备字段定义模板
create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
deleted INTEGER NOT NULL DEFAULT 0
```

### 2.4 字段默认值规范

| 场景 | 规范 | 示例 |
|------|------|------|
| 数值类型 | 明确默认值 | `DEFAULT 0` |
| 字符串类型 | 按需设置 | `DEFAULT ''` 或不设默认值 |
| 布尔类型 | 明确默认值 | `DEFAULT FALSE` |
| 时间类型 | 使用数据库函数 | `DEFAULT CURRENT_TIMESTAMP` |
| 逻辑删除 | 固定默认值 | `DEFAULT 0` |

## 三、字段类型映射

### 3.1 PostgreSQL与Java类型映射

| PostgreSQL类型 | Java类型 | 说明 |
|----------------|----------|------|
| VARCHAR | String | 可变长度字符串 |
| INTEGER | Integer | 4字节整数 |
| BIGINT | Long | 8字节整数 |
| DECIMAL/NUMERIC | BigDecimal | 精确数值，用于金额等 |
| TIMESTAMP | LocalDateTime | 日期时间，不含时区 |
| DATE | LocalDate | 仅日期 |
| BOOLEAN | Boolean | 布尔值，值为TRUE/FALSE |
| JSONB | String/Object | JSON二进制存储，支持索引查询 |
| SERIAL | Long | 4字节自增整数 |
| BIGSERIAL | Long | 8字节自增整数 |
| TEXT | String | 不限长度文本 |
| BYTEA | byte[] | 二进制数据 |

### 3.2 金额字段规范

- 金额字段统一使用`DECIMAL(18,2)`类型
- Java层面使用`BigDecimal`，禁止使用`Double`或`Float`
- 汇率字段使用`DECIMAL(12,6)`

```sql
amount DECIMAL(18,2) NOT NULL DEFAULT 0.00,
exchange_rate DECIMAL(12,6) NOT NULL DEFAULT 1.000000
```

### 3.3 JSONB字段使用规范

- 适用于灵活结构、扩展属性、配置信息等场景
- 不适用于频繁查询和关联的字段
- 查询时使用JSONB操作符：`->`、`->>`、`@>`、`?`

```sql
-- JSONB字段示例
extra_data JSONB DEFAULT '{}',

-- JSONB查询示例
SELECT * FROM sys_config WHERE config_data @> '{"key": "theme"}';
```

## 四、索引命名规范

### 4.1 索引命名规则

| 索引类型 | 命名格式 | 示例 |
|----------|----------|------|
| 主键索引 | `{table}_pkey` | `employees_pkey`（PostgreSQL自动生成） |
| 唯一索引 | `uk_{table}_{field}` | `uk_employees_email` |
| 普通索引 | `idx_{table}_{field}` | `idx_employees_department_id` |
| 组合索引 | `idx_{table}_{field1}_{field2}` | `idx_orders_customer_id_order_status` |

### 4.2 索引设计原则

1. **主键自动创建索引**：PostgreSQL的主键约束自动创建唯一索引
2. **外键字段建索引**：外键字段应建立普通索引，提升JOIN性能
3. **高频查询字段建索引**：根据实际查询模式建立索引，避免过度索引
4. **组合索引遵循最左前缀**：组合索引字段顺序应与查询条件顺序一致
5. **避免冗余索引**：如果已有组合索引`idx_t_a_b`，则不再单独建`idx_t_a`

### 4.3 索引创建示例

```sql
-- 唯一索引
CREATE UNIQUE INDEX uk_employees_email ON employees(email);

-- 普通索引
CREATE INDEX idx_employees_department_id ON employees(department_id);

-- 组合索引
CREATE INDEX idx_orders_customer_id_order_status ON orders(customer_id, order_status);

-- 并发创建索引（生产环境推荐，不锁表）
CREATE INDEX CONCURRENTLY idx_food_trace_trace_code ON food_trace(trace_code);
```

### 4.4 生产环境索引操作规范

- 生产环境创建索引必须使用`CONCURRENTLY`选项，避免锁表
- 删除索引前确认无查询依赖
- 大表索引创建应在低峰期执行

## 五、PostgreSQL特有语法规范

### 5.1 自增主键

```sql
-- 推荐方式（PostgreSQL 10+）
employee_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- 兼容方式
employee_id BIGSERIAL PRIMARY KEY
```

### 5.2 布尔类型

```sql
-- 使用BOOLEAN类型，值为TRUE/FALSE（非1/0）
is_active BOOLEAN NOT NULL DEFAULT TRUE,
deleted INTEGER NOT NULL DEFAULT 0  -- 逻辑删除使用INTEGER，配合MyBatis-Plus
```

### 5.3 JSONB操作

```sql
-- 插入JSON数据
INSERT INTO sys_config (config_key, config_data) VALUES ('theme', '{"mode": "dark", "font": 14}');

-- 查询JSON字段
SELECT config_data->>'mode' AS mode FROM sys_config WHERE config_key = 'theme';

-- 包含查询
SELECT * FROM sys_config WHERE config_data @> '{"mode": "dark"}';

-- 键存在查询
SELECT * FROM sys_config WHERE config_data ? 'font';
```

### 5.4 字符串连接

```sql
-- 使用 || 运算符
SELECT first_name || ' ' || last_name AS full_name FROM employees;

-- 不使用CONCAT函数（虽然PostgreSQL也支持）
```

### 5.5 模式匹配

```sql
-- 正则匹配（区分大小写）
SELECT * FROM employees WHERE employee_name ~ '^张';

-- 正则匹配（不区分大小写）
SELECT * FROM employees WHERE employee_name ~* '^zhang';

-- ILIKE模糊匹配（不区分大小写）
SELECT * FROM employees WHERE email ILIKE '%@example.com';

-- LIKE模糊匹配（区分大小写）
SELECT * FROM employees WHERE employee_name LIKE '张%';
```

### 5.6 数组类型

```sql
-- 定义数组字段
tags VARCHAR(50)[] DEFAULT '{}',

-- 数组查询
SELECT * FROM dishes WHERE tags @> ARRAY['川菜'];

-- 数组包含任一元素
SELECT * FROM dishes WHERE tags && ARRAY['川菜', '湘菜'];
```

## 六、数据库字段命名规范

### 6.1 三层命名规范

| 层面 | 命名风格 | 示例 |
|------|----------|------|
| 数据库层面 | 下划线命名（snake_case） | `product_name`, `create_time`, `order_status` |
| Java实体层面 | 驼峰命名（camelCase） | `productName`, `createTime`, `orderStatus` |
| 前端层面 | 驼峰命名（camelCase） | `productName`, `createTime`, `orderStatus` |

### 6.2 MyBatis-Plus自动映射

```yaml
# application.yml
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true
```

- 开启`map-underscore-to-camel-case`后，MyBatis-Plus自动完成数据库下划线与Java驼峰的映射
- 数据库字段`product_name`自动映射到Java属性`productName`
- 无需手动编写ResultMap映射

### 6.3 命名对照示例

| 数据库字段 | Java属性 | 前端属性 | 说明 |
|-----------|---------|---------|------|
| `employee_id` | `employeeId` | `employeeId` | 主键 |
| `department_id` | `departmentId` | `departmentId` | 外键 |
| `product_name` | `productName` | `productName` | 业务字段 |
| `create_time` | `createTime` | `createTime` | 创建时间 |
| `update_time` | `updateTime` | `updateTime` | 更新时间 |
| `order_status` | `orderStatus` | `orderStatus` | 状态字段 |
| `is_active` | `isActive` | `isActive` | 布尔字段 |

## 九、逻辑删除规范

### 9.1 MyBatis-Plus配置

```yaml
# application.yml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

### 9.2 实体类配置

```java
@TableLogic
@TableField("deleted")
private Integer deleted;
```

### 9.3 操作规范

| 规则 | 说明 |
|------|------|
| 禁止手动添加deleted条件 | 使用`@TableLogic`注解后，MyBatis-Plus自动处理逻辑删除 |
| 禁止使用物理删除 | 所有删除操作使用`removeById()`或`remove()`方法进行逻辑删除 |
| 批量删除使用规范方法 | 使用`removeByIds()`方法进行批量逻辑删除 |
| 查询已删除数据 | 如需查询已删除数据，使用原生SQL或`@SqlParser(filter = true)`注解 |

### 9.4 逻辑删除行为说明

- 执行`removeById()`时，MyBatis-Plus自动生成`UPDATE ... SET deleted = 1 WHERE id = ?`
- 执行`selectList()`时，MyBatis-Plus自动添加`WHERE deleted = 0`条件
- 执行`getById()`时，MyBatis-Plus自动添加`WHERE deleted = 0`条件

## 十、数据迁移规范

### 10.1 迁移工具

使用Flyway管理数据库版本迁移。

### 10.2 迁移脚本命名规范

```
V{version}__{description}.sql
```

| 部分 | 规范 | 示例 |
|------|------|------|
| V | 固定前缀，表示版本迁移 | `V` |
| version | 版本号，使用点号分隔 | `1.0.0`, `1.1.0` |
| __ | 双下划线分隔符 | `__` |
| description | 简短描述，使用下划线连接 | `create_employee_table` |

完整示例：

```
V1.0.0__init_schema.sql
V1.0.1__create_employee_table.sql
V1.1.0__add_food_trace_tables.sql
V1.2.0__add_inventory_tables.sql
V2.0.0__add_finance_module.sql
```

### 10.3 迁移脚本编写规范

1. **每个脚本只做一件事**：一个迁移脚本只包含一个逻辑变更
2. **脚本必须可重复执行**：使用`IF NOT EXISTS`等条件判断
3. **禁止修改已执行的脚本**：已执行的迁移脚本不可修改
4. **新增表必须包含必备字段**：`create_time`, `update_time`, `deleted`
5. **数据迁移与结构迁移分离**：结构变更和数据迁移使用不同的脚本

```sql
-- 迁移脚本示例
-- V1.0.1__create_employee_table.sql

CREATE TABLE IF NOT EXISTS employees (
    employee_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    email VARCHAR(200),
    phone VARCHAR(20),
    department_id BIGINT,
    position_id BIGINT,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_employees_department_id ON employees(department_id);
CREATE INDEX IF NOT EXISTS idx_employees_position_id ON employees(position_id);
```

### 10.4 增量变更执行

- 增量变更通过`DatabaseInitConfig`类执行
- 应用启动时自动检测并执行未执行的迁移脚本
- 迁移执行失败时应用启动中止，需人工介入处理
