# 系统架构

## 一、整体架构

### 1.1 架构全景

食品溯源系统采用前后端分离架构，通过Nginx反向代理实现前后端统一入口，后端服务与数据库、缓存、消息队列协作完成业务处理，同时对接多种硬件设备驱动。

```
+------------------+     +----------------+     +---------------------+
|                  |     |                |     |                     |
|  前端 (Vue3)     | --> |    Nginx       | --> |  后端 (Spring Boot) |
|  localhost:3000  |     |  反向代理/静态  |     |  localhost:8081     |
|                  |     |  资源托管       |     |                     |
+------------------+     +----------------+     +---------------------+
                                                        |
                                          +-------------+-------------+
                                          |             |             |
                                          v             v             v
                                 +-------------+  +----------+  +-----------+
                                 | PostgreSQL  |  |  Redis   |  | RabbitMQ  |
                                 | 生产数据库   |  | 缓存/会话 |  | 异步消息   |
                                 +-------------+  +----------+  +-----------+
                                                                      |
                                                        +-------------+-------------+
                                                        |             |             |
                                                        v             v             v
                                                 +-----------+  +-----------+  +-----------+
                                                 | 溯源记录   |  | 通知推送   |  | 自动记账   |
                                                 | 消费者     |  | 消费者     |  | 消费者     |
                                                 +-----------+  +-----------+  +-----------+

                                                        |
                                                        v
                                               +------------------+
                                               |  设备驱动层       |
                                               |  打印机/扫码枪/   |
                                               |  称重秤/取餐柜    |
                                               +------------------+
```

### 1.2 请求流转路径

```
用户操作 → Vue组件 → Composable → Pinia Store → API(request实例)
    → Nginx(:80) → Spring Boot(:8081) → Controller → Service
    → DataService(缓存优先) → Mapper → PostgreSQL
    → 返回Result<T> → 响应拦截器提取data → Store更新 → 视图刷新
```

### 1.3 异步消息流转路径

```
业务操作 → Service发布消息 → RabbitMQ Exchange → Queue
    → 消费者监听 → 处理业务逻辑 → 更新数据库 → 清除缓存
```

## 二、后端分层架构

### 2.1 分层结构

```
Controller层  →  Service层  →  DataService层(缓存)  →  Mapper层  →  Database
     |              |                |                     |             |
  请求路由        业务逻辑        缓存+DB双读           数据访问       数据存储
  参数校验        事务管理        批量查询优化           CRUD操作
  返回Result      消息发布        缓存更新策略           分页查询
```

### 2.2 Controller层

**职责**：请求路由、参数校验、响应封装

**规范**：
- 使用`@RestController`和`@RequestMapping`注解
- 使用`@Operation`添加OpenAPI文档注解
- 接收DTO参数，使用`@Valid`进行参数校验
- 返回统一的`Result<T>`响应对象
- 不包含业务逻辑，仅做参数转换和结果封装

```java
@RestController
@RequestMapping("/api/v1/food-trace")
@Tag(name = "食品溯源", description = "食品溯源管理接口")
public class FoodTraceController {

    private final FoodTraceService foodTraceService;

    public FoodTraceController(FoodTraceService foodTraceService) {
        this.foodTraceService = foodTraceService;
    }

    @PostMapping
    @Operation(summary = "创建溯源记录")
    public Result<FoodTraceVO> create(
            @Valid @RequestBody FoodTraceCreateDTO dto) {
        return Result.success(foodTraceService.create(dto));
    }
}
```

### 2.3 Service层

**职责**：核心业务逻辑、事务管理、消息发布

**规范**：
- 使用`@Service`注解标注
- 复杂业务使用`@Transactional`管理事务
- 通过DataService层访问数据，不直接注入Mapper
- 异步操作通过RabbitMQ发布消息
- 业务校验在Service层完成

```java
@Service
public class FoodTraceServiceImpl implements FoodTraceService {

    private final FoodTraceDataService foodTraceDataService;
    private final RabbitTemplate rabbitTemplate;

    public FoodTraceServiceImpl(FoodTraceDataService foodTraceDataService, RabbitTemplate rabbitTemplate) {
        this.foodTraceDataService = foodTraceDataService;
        this.rabbitTemplate = rabbitTemplate;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public FoodTraceVO create(FoodTraceCreateDTO dto) {
        // 业务校验
        // 数据操作通过DataService
        // 发布异步消息
        // 清除缓存
    }
}
```

### 2.4 DataService层

**职责**：缓存管理、DB双读、批量查询优化

**规范**：
- 定义`{Entity}DataService`接口和`{Entity}DataServiceImpl`实现
- 缓存优先读取，缓存未命中时查询数据库并回填缓存
- 提供批量查询接口，减少N+1查询问题
- 数据变更时清除对应缓存

```java
public interface FoodTraceDataService {

    /**
     * 批量获取溯源基本信息
     * @param traceIds 溯源ID列表
     * @return 溯源基本信息映射
     */
    Map<String, FoodTraceBasicInfo> batchGetFoodTraceBasicInfo(
            List<String> traceIds);

    /**
     * 获取单条溯源基本信息
     * @param traceId 溯源ID
     * @return 溯源基本信息
     */
    FoodTraceBasicInfo getFoodTraceBasicInfo(String traceId);

    /**
     * 清除指定溯源缓存
     * @param traceId 溯源ID
     */
    void clearFoodTraceCache(String traceId);

    /**
     * 批量清除溯源缓存
     * @param traceIds 溯源ID列表
     */
    void clearFoodTraceBatchCache(List<String> traceIds);

    /**
     * 清除所有溯源缓存
     */
    void clearAllFoodTraceCache();
}
```

### 2.5 Mapper层

**职责**：数据访问，SQL执行

**规范**：
- 继承`BaseMapper<T>`，使用MyBatis Plus通用方法
- 复杂查询使用XML映射文件或`@Select`注解
- 逻辑删除由`@TableLogic`自动处理，禁止手动添加`deleted = 0`条件
- 分页查询使用`IPage`对象

```java
@Mapper
public interface FoodTraceMapper extends BaseMapper<FoodTrace> {
    // 复杂查询可使用XML映射
}
```

### 2.6 Entity层

**职责**：数据库表映射

**规范**：
- 使用`@TableName`映射表名
- 使用`@TableLogic`标注逻辑删除字段
- 使用`@TableField`映射字段名和填充策略
- 主键使用`@TableId(type = IdType.ASSIGN_ID)`雪花算法生成

```java
@TableName("food_trace")
public class FoodTrace extends BaseEntity {

    @TableId(type = IdType.ASSIGN_ID)
    @TableField("trace_id")
    private String traceId;

    @TableField("product_name")
    private String productName;

    @TableField(value = "create_time", fill = FieldFill.INSERT)
    private LocalDateTime createTime;

    @TableField(value = "update_time", fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updateTime;

    @TableLogic
    @TableField("deleted")
    private Integer deleted;
}
```

### 2.7 DTO层

**职责**：请求/响应数据传输

**规范**：
- 创建请求DTO命名：`{Entity}CreateDTO`
- 更新请求DTO命名：`{Entity}UpdateDTO`
- 查询请求DTO命名：`{Entity}QueryDTO`
- 响应VO命名：`{Entity}VO`
- 基本信息DTO命名：`{Entity}BasicInfo`
- 使用`@Valid`注解进行参数校验

## 三、前端分层架构

### 3.1 分层结构

```
View层  →  Composable层  →  Store层(Pinia)  →  API层(request)  →  Backend
  |            |                |                  |                 |
页面布局     业务逻辑复用     全局状态管理      请求封装         后端服务
组件组合     表单验证        数据缓存          错误处理
样式渲染     数据转换        响应式更新        Token管理
```

### 3.2 View层

**职责**：页面布局、组件组合、样式渲染

**规范**：
- 页面级组件仅负责布局和组件组合，不包含具体业务逻辑
- 使用`<script setup lang="ts">`语法
- 按外部依赖、内部组件、工具函数的顺序导入
- 样式使用`scoped`属性，通过CSS变量统一样式
- 单文件不超过1000行，超出时拆分子组件

```vue
<template>
  <div class="page-container">
    <FinanceReportHeader />
    <FinanceReportGenerator @submit="handleSubmit" />
    <FinanceReportList :data="reportList" />
  </div>
</template>

<script setup lang="ts">
import FinanceReportHeader from '@/components/Finance/FinanceReportHeader.vue'
import FinanceReportGenerator from '@/components/Finance/FinanceReportGenerator.vue'
import FinanceReportList from '@/components/Finance/FinanceReportList.vue'
import { useFinanceReport } from '@/composables/useFinanceReport'

const { reportList, handleSubmit } = useFinanceReport()
</script>
```

### 3.3 Composable层

**职责**：业务逻辑复用、表单验证、数据转换

**规范**：
- 使用`use`前缀命名，如`useFinanceReport`
- 封装可复用的业务逻辑，供多个组件共享
- 包含表单验证规则、数据格式转换、业务计算逻辑
- 返回响应式数据和方法供组件使用

```typescript
export function useFinanceReport() {
  const store = useFinanceReportStore()

  const handleSubmit = async (formData: FinanceReportFormData) => {
    // 业务逻辑处理
  }

  return {
    reportList: computed(() => store.reportList),
    handleSubmit
  }
}
```

### 3.4 Store层

**职责**：全局状态管理、数据缓存、响应式更新

**规范**：
- 使用Pinia定义Store，文件命名kebab-case，如`finance-report.ts`
- 按功能模块划分独立Store，避免单一Store过大
- 异步操作在Store中调用API层
- 响应拦截器已自动提取`response.data.data`，Store直接使用返回值

```typescript
export const useFinanceReportStore = defineStore('finance-report', () => {
  const reportList = ref<FinanceReportItem[]>([])

  const fetchList = async (params: FinanceReportQueryForm) => {
    const response = await financeReportApi.getList(params)
    reportList.value = response?.records || []
  }

  return { reportList, fetchList }
})
```

### 3.5 API层

**职责**：HTTP请求封装、错误处理、Token管理

**规范**：
- 必须使用`src/api/request.ts`导出的`request`实例
- 禁止直接使用`axios`或`fetch`
- GET请求直接传params对象，禁止嵌套`{ params }`
- POST/PUT请求直接传data对象
- 按模块在`api/`目录下封装API
- 类型定义集中在`types/`目录

```typescript
import request from './request'

export const foodTraceApi = {
  getList(params: FoodTraceQueryForm): Promise<PageResponse<FoodTraceItem>> {
    return request.get<PageResponse<FoodTraceItem>>('/v1/food-trace', params)
  },

  getById(id: string): Promise<FoodTraceItem> {
    return request.get<FoodTraceItem>(`/v1/food-trace/${id}`)
  },

  create(data: FoodTraceCreateDTO): Promise<FoodTraceItem> {
    return request.post<FoodTraceItem>('/v1/food-trace', data)
  }
}
```

### 3.6 Types层

**职责**：TypeScript类型定义

**规范**：
- 接口使用PascalCase命名，如`EmployeeFormData`
- 枚举使用PascalCase命名，如`EmployeeStatus`
- 表单类型命名：`{Entity}FormData`、`{Entity}QueryForm`
- 响应类型命名：`{Entity}Item`、`PageResponse<T>`
- 禁止使用`any`类型，使用`unknown`或具体类型替代

## 四、安全架构

### 4.1 认证体系

```
用户登录 → 账号密码验证 → MFA二次验证 → JWT令牌签发
    → 前端存储Token(localStorage) → 请求拦截器自动附加Authorization
    → 后端过滤器链验证 → 安全上下文注入 → 业务处理
```

**JWT认证流程**：
- 登录成功后签发Access Token（短有效期）和Refresh Token（长有效期）
- Access Token过期后使用Refresh Token自动续签
- Token黑名单存储在Redis，登出时加入黑名单
- 请求拦截器自动添加Authorization Header，禁止手动添加

**MFA多因素认证**：
- 支持TOTP（基于时间的一次性密码）
- 支持短信验证码
- 敏感操作（如删除溯源记录）需二次验证

### 4.2 授权模型

**RBAC权限模型**：
- 角色（Role）：定义功能权限集合
- 权限（Permission）：最小授权单元，对应API接口
- 用户（User）：关联角色，继承权限

**8级数据范围**：

| 级别 | 名称 | 数据范围 |
|------|------|---------|
| 1 | 全部数据 | 系统内所有数据 |
| 2 | 本公司及下级 | 本公司及下属组织数据 |
| 3 | 本公司 | 本公司数据 |
| 4 | 本部门及下级 | 本部门及下属部门数据 |
| 5 | 本部门 | 本部门数据 |
| 6 | 本班组 | 本班组数据 |
| 7 | 本人及下属 | 本人及直属下级数据 |
| 8 | 仅本人 | 仅本人创建的数据 |

### 4.3 AOP切面

| 切面 | 功能 | 实现方式 |
|------|------|---------|
| 审计日志 | 记录关键操作日志 | `@AuditLog`注解 + AOP拦截 |
| 权限检查 | 方法级权限控制 | `@PreAuthorize` + 自定义权限评估器 |
| 数据脱敏 | 敏感字段自动脱敏 | `@DataMask`注解 + 序列化处理器 |
| 限流 | 接口访问频率限制 | `@RateLimit`注解 + Redis计数器 |

## 五、缓存架构

### 5.1 二级缓存结构

```
请求 → 本地缓存(Caffeine) → Redis缓存 → 数据库
          |                     |
     进程内高速访问          分布式共享缓存
     容量小、速度快          容量大、跨实例共享
```

**L1 本地缓存（Caffeine）**：
- 进程内缓存，访问延迟极低
- 适合存储变更频率低的基础数据
- 容量有限，设置合理的maximumSize
- 过期时间短于L2缓存

**L2 分布式缓存（Redis）**：
- 跨实例共享，保证数据一致性
- 适合存储需要多实例共享的业务数据
- 支持丰富的数据结构（String/Hash/Set/ZSet）
- 持久化机制保障数据安全

### 5.2 缓存键规范

**格式**：`{entity}:basic:{entityId}`

**示例**：
- 员工信息：`employee:basic:1234567890`
- 部门信息：`department:basic:dept001`
- 溯源记录：`foodTrace:basic:trace001`

### 5.3 缓存过期时间

| 数据类型 | 过期时间 | 说明 |
|---------|---------|------|
| 用户信息 | 30分钟 | 变更频率较高 |
| 权限信息 | 1小时 | 角色权限调整时清除 |
| 配置信息 | 24小时 | 变更频率低 |
| 基本信息 | 24小时 | 部门/职位等基础数据 |
| 静态数据 | 7天 | 字典/枚举等极少变更数据 |

### 5.4 缓存更新策略

**写时清除（Write-Through Invalidate）**：
- 数据更新/删除时立即清除对应缓存
- 批量操作时批量清除缓存
- 清除顺序：先清L1本地缓存，再清L2 Redis缓存

```
数据更新 → 清除本地Caffeine缓存 → 清除Redis缓存 → 返回结果
```

**缓存穿透防护**：
- 查询结果为空时缓存空值，设置短过期时间
- 布隆过滤器拦截非法ID查询

**缓存雪崩防护**：
- 过期时间添加随机偏移量，避免同时失效
- 热点数据永不过期，通过更新策略主动刷新

## 六、消息架构

### 6.1 RabbitMQ拓扑

```
Producer → Exchange → Queue → Consumer
              |
              +---> Dead Letter Queue (异常消息)
              |
              +---> Delay Queue (延迟消息)
```

### 6.2 队列命名规范

**格式**：`{module}.{entity}.{action}`

**示例**：
- 溯源创建：`trace.food.create`
- 溯源更新：`trace.food.update`
- 通知推送：`notify.message.send`
- 自动记账：`finance.account.auto`

### 6.3 消息可靠性保障

| 保障机制 | 配置 | 说明 |
|---------|------|------|
| 队列持久化 | durable=true | 队列定义持久化到磁盘 |
| 交换机持久化 | durable=true | 交换机定义持久化到磁盘 |
| 消息持久化 | deliveryMode=PERSISTENT | 消息内容持久化到磁盘 |
| 生产者确认 | publisher-confirm-type=correlated | 消息到达Exchange后回调确认 |
| 消费者确认 | acknowledge-mode=manual | 业务处理完成后手动ACK |
| 死信队列 | x-dead-letter-exchange | 消费失败消息转入死信队列 |

### 6.4 重试策略

| 参数 | 值 | 说明 |
|------|-----|------|
| 最大重试次数 | 3 | 超过次数转入死信队列 |
| 初始重试间隔 | 1000ms | 第一次重试等待时间 |
| 重试间隔倍数 | 2.0 | 指数退避，每次间隔翻倍 |
| 最大重试间隔 | 10000ms | 重试间隔上限 |

### 6.5 消息消费流程

```
消息到达 → 消费者接收 → 业务处理
    |                        |
    |                  +-----+-----+
    |                  |           |
    |                成功         失败
    |                  |           |
    |              手动ACK     重试次数<3?
    |                  |        |        |
    |                  |       是        否
    |                  |     重新入队   拒绝消息
    |                  |                 |
    |                  |           转入死信队列
    |                  |           人工处理/告警
```

## 七、设备架构

### 7.1 设备驱动抽象

```
+------------------+
|   业务层         |  调用统一接口，不关心设备细节
+------------------+
        |
+------------------+
| DeviceDriver     |  统一抽象接口
| Interface        |  connect/disconnect/send/receive
+------------------+
        |
   +----+----+----+----+
   |    |    |    |    |
 打印机 扫码枪 称重秤 取餐柜 ...
```

**DeviceDriver接口定义**：

```java
public interface DeviceDriver {

    /**
     * 连接设备
     * @param config 设备连接配置
     * @return 连接是否成功
     */
    boolean connect(DeviceConfig config);

    /**
     * 断开设备连接
     */
    void disconnect();

    /**
     * 发送指令到设备
     * @param command 设备指令
     * @return 执行结果
     */
    DeviceResult send(DeviceCommand command);

    /**
     * 接收设备数据
     * @return 设备返回数据
     */
    DeviceData receive();

    /**
     * 获取设备状态
     * @return 设备状态信息
     */
    DeviceStatus getStatus();
}
```

### 7.2 设备通信方式

| 设备类型 | 通信协议 | 连接方式 | 数据格式 |
|---------|---------|---------|---------|
| 标签打印机 | TSPL协议 | USB/网络 | TSPL指令集 |
| 扫码枪 | HID/串口 | USB | 字符串（条码内容） |
| 称重秤 | 串口协议 | RS232/USB | 数值（重量+单位） |
| 取餐柜 | Modbus/HTTP | 网络 | 柜门状态+控制指令 |

### 7.3 WebSocket实时通信

```
设备状态变更 → 设备驱动层 → WebSocket推送 → 前端实时更新
                                        |
                                  自动重连机制
                                  心跳保活检测
                                  消息确认机制
```

**WebSocket连接管理**：
- 前端通过WebSocket与后端建立长连接
- 设备状态变更时后端主动推送消息
- 心跳机制检测连接存活状态
- 断线自动重连，指数退避策略

### 7.4 TSPL标签打印协议

**打印流程**：
```
选择溯源记录 → 生成标签数据 → 构建TSPL指令
    → 发送到打印机 → 打印标签 → 粘贴到食品包装
```

**TSPL指令示例**：
```
SIZE 60,40           // 标签尺寸60mm x 40mm
GAP 2,0              // 标签间距2mm
DIRECTION 1          // 打印方向
CODEPAGE UTF-8       // 字符编码
TEXT 10,10,"3",0,1,1,"溯源编号:TR20240101001"   // 文本
BARCODE 10,40,"128",80,1,0,2,2,"TR20240101001"  // 条形码
QRCODE 200,10,"H",4,"A",0,"https://trace.example.com/TR20240101001"  // 二维码
PRINT 1              // 打印1张
```

### 7.5 设备异常处理

| 异常场景 | 处理策略 |
|---------|---------|
| 设备离线 | 前端显示设备离线状态，操作排队等待设备上线 |
| 通信超时 | 重试3次，失败后告警通知运维人员 |
| 数据异常 | 校验设备返回数据格式，异常数据丢弃并记录日志 |
| 设备故障 | 标记设备故障状态，自动切换备用设备（如有） |
