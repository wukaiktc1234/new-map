# 商业模式设计：单店/连锁双模式（菜单路由 + 业务策略 + 数据契约）

> 状态：设计稿（评审中）
> 关联：批 23（业务链对齐权限模板、驳回限制）；本设计在其基础上把"模式"从**权限层**提升到**业务流程策略层**
> 用户决策：门店档案↔组织架构联动为独立任务，**不属于本设计实施范围**（见 §8 挂起项）

---

## 1. 背景与设计原则

### 1.1 用户观点（定案）
- **数据层**：单店/连锁共用同一套数据底座，模式切换后溯源与数据互通不受影响（Odoo 多公司范式）
- **模式层**：两者程度绝对不同
  - **单店**：必须简化（一人身兼多职：老板=运营+采购+财务+店长）
  - **连锁**：权责分离、角色分离、业务链完整（SoD 职责冲突矩阵）
- **单店虽小，商业闭环不能少**：组织→门店→开业准备（设备/原料/租金/装修/证件）→商品建档→菜品明细→POS 销售→日结→成本→追溯
- 模式差异落在**入口组织方式**：连锁=全量专业菜单各司其职；单店=合并入口/向导式引导

### 1.2 设计原则
1. **数据不动、规则分层**：模式差异 = 配置层差异（参数/开关/模板），不建两套系统、不迁移数据
2. **路由与菜单分离**：路由全量注册（深链/刷新/权限后端兜底），菜单树按（角色×模式）过滤——模式切换只重算菜单树
3. **联动走契约不走菜单**：跨模块数据联动（如菜品明细下拉=门店库存）全部经 API 契约 + 后端数据权限（storeId 过滤），与菜单显隐零耦合
4. **能力保全（Capacity Preservation）**：模式切换允许"重组入口"（合并/移动/换名/折叠），**不允许"删除入口"**——每个业务能力（页面/关键操作）在任意激活模式下必须有**至少一个可达入口**（直接菜单 | 替代入口 | 待办直达 | 全局搜索），并配套**静态可达性校验**防止"隐藏后无替代入口"的漏洞

## 2. 行业范式调研结论（2026-08-02）

| 范式 | 出处 | 借鉴点 |
|---|---|---|
| 多公司/共享主数据 | Odoo 多公司模型 | 同一数据库内多实体，产品/供应商主数据共享，单据按实体归属 → "切换后数据互通"的实现方式 |
| 配置优先/参数化 | SAP 系/简道云 ERP | 90% 变化用参数/规则/流程配置解决，10% 动代码；功能开关按组织/时间窗启用 |
| 模块化按需 | 金蝶精斗云/有赞/点单星 | 单店只启用进销存+基础财务+门店开单；扩连锁再加中央厨房/调拨/成本分摊（功能开关而非砍数据） |
| 职责分离 SoD | 简道云/Gartner | 冲突矩阵：建供应商≠下单≠收货≠对账≠付款；**单店=SoD 显式豁免场景**（同人自审合法化） |
| 总部配置下发 | 餐饮 SaaS 通用 | 菜单/价格总部一次配置，门店执行；门店独立核算+总部汇总 |

## 3. 现有架构核实（2026-08-02 实查）

### 3.1 管理端（frontend）菜单/路由
- 路由：`router/index.ts` **全量静态注册**（200+ 条），meta 带 `domain / roles / permissions`，守卫统一检查（admin 全过）
- 菜单：`getVisibleMenus()` 按优先级过滤：① userMenuOverrides ② roleMenuOverrides ③ 模板域矩阵覆盖（domainMatrix→DOMAIN_TO_MENU_GROUP）④ defaultMenuConfig；`MenuGroupConfig.visibleRoles` 控制角色可见性
- 模板：4 种（centralized-single / standard-chain / large-chain / custom），服务端持久化激活模板（批 22），applyTemplate 有链完整性校验（批 23）
- 菜单组注册：各模块 `menu.ts` 启动时 `registerMenuGroup()`（注册后锁定 F-008）

### 3.2 POS 端（frontend-pos）与后厨端（frontend-kitchen）
- **无菜单系统**：固定路由（登录/点餐/支付/桌台/叫号/后厨），收银端"菜单"=菜品分类（产品中心驱动）
- 销售数据互动**已打通且同源**：
  - 产品：`/v1/product-center/foods|combos|categories`（与管理端同一后端）
  - 订单：`/v1/pos/orders/*` → `PosOrderCreateServiceImpl` 直接 `orderMapper.insert` → **同一张 order 表**，同步写 kitchen_order；含 storeId（可空→后端兜底默认门店）、班次（shift）、券核销（/v1/pos/coupons）、YOLO 辅助收银（/v1/pos/yolo）
- 数据权限：`DataPermissionAspect` 按当前用户 storeId 给 queryWrapper 加 `store_id` 过滤（admin 除外）

### 3.3 跨模块数据联动（用户关注点，实查）
| 联动 | 实现 | 与菜单耦合 |
|---|---|---|
| 菜品新增对话框·明细下拉（原料） | FoodManagement.vue → `storeInventoryApi` → `/v1/store-inventory`（后端按当前用户门店过滤） | **零耦合**（API 契约） |
| 采购订单/申请/计划·物料下拉（含最新单价 unit_cost） | PurchasePlan/Request.vue → 同上 | 零耦合 |
| 需求提报·商品单价 | StoreMaterialRequest.vue → 同上 | 零耦合 |
| POS 销售 → 管理端订单/统计/成本 | order 表同源 | 零耦合 |

## 4. 模式模型设计

```
模式 Mode = 权限矩阵(现有) + 业务策略集 biz_policy + 菜单策略 visibleModes
```

### 4.1 数据落地
- **permission_templates 表加 `biz_policy JSONB` 列**（每模板自带）：
  ```json
  {
    "autoApproveSamePerson": true,     // 同人自审自动通过（单店 on / 连锁 off）
    "mergeArrivalReceive": true,       // 到货登记+确认入库合一（单店 on）
    "planStepVisible": false,          // 采购计划步骤（单店隐藏）
    "riskConfirm": true,               // 资金/删除操作二次确认+审计（单店 on）
    "approvalCenterStyle": "todo"      // 审批中心：todo=我的待办（单店）/ full=完整审批中心（连锁）
  }
  ```
- **前端 MenuGroupConfig / SubMenuItem 加 `visibleModes?: ModeCode[]`**（菜单项级模式开关，缺省=所有模式可见）

### 4.2 菜单路由处理规则
| 项 | 处理 |
|---|---|
| 路由表 | **基本不动**；仅为"合并入口"新增少量页面（例：单店"采购收货"合一页），旧页面保留（连锁用） |
| 菜单树 | 模式切换（applyTemplate）时重算：现有机制 + `visibleModes` 过滤；切换=热切换+审计（现有 TEMPLATE_APPLIED） |
| 深链/刷新 | 不受影响（路由全量） |
| 单店菜单示例 | "到货登记"+"确认入库"合并为一个入口；审批中心=我的待办；采购计划步骤折叠 |
| 连锁菜单示例 | 全量展示，各司其职 |
| 能力保全 | 任何 `visibleModes` 隐藏项必须登记**替代入口目标**（replacement），如："到货登记"菜单隐藏 → replacement="采购收货"合一页；无替代入口的能力点禁止隐藏（静态校验拦截，见 §4.4） |
| URL 直达与安全 | **不直接禁用 URL，守卫增加"模式可达性"检查层**（见 §4.5）：菜单隐藏的页面按模式校验，不可达→403/重定向；防"知道 URL 绕过菜单隐藏"。**安全边界仍在后端 API 权限点**，前端守卫与菜单均为 UX+纵深防御 |
| **禁用方案** | `router.addRoute` 动态注册（刷新丢路由、可绕过守卫、难维护）；一刀切禁用 URL 直达（会打断待办直达/替代入口/全局搜索等能力保全兜底） |

### 4.3 其他端影响评估（变更后检查项，非主动改动）
| 端 | 影响 | 需检查 |
|---|---|---|
| POS 端 | 无需菜单调整 | 单店模式下隐藏"门店选择器"（storeId 锁定默认门店，契约已支持可空兜底）；连锁显示 |
| 后厨端 | 无影响 | 订单/叫号契约不变 |
| 小程序/员工端 | 无影响 | 同契约 |

### 4.4 能力保全与入口可达性（漏洞防范）
> 用户质疑（2026-08-02）：菜单入口被隐藏后，用户无法进入页面建商品档案——"菜单隐藏≠功能消失"只对知道 URL 的人成立，对业务操作者=功能不可达。需系统性防漏。

**业务能力点（Capability Point）**：每个可执行业务操作（页面+关键动作）。建立清单，如：
`商品档案-新建 / 采购订单-新建 / 到货登记 / 确认入库 / 门店收货 / 审批处理 / 退款处理 ...`

**可达性判定（任意模式激活时，能力点必须满足其一）**：
1. **直接入口**：该能力点所在菜单项可见（域矩阵开放 且 未按模式隐藏）
2. **替代入口**：隐藏项已登记 replacement 目标（合并页内 Tab/按钮可达）
3. **待办直达**：StorePendingTasks 任务类型映射表可跳转（现有机制，如审批/退款/审核）
4. **全局搜索可达**：TopNavbar 全局搜索弹窗可派发到该页面

**静态校验 `validateMenuReachability`**（与批 23 `validateChainIntegrity` 同机制）：
- 模板应用 / 菜单覆盖保存时执行：遍历全部能力点 × 目标模式 → 四类入口均不可达则**拦截（warn 级）并审计**，提示配置者补 replacement
- 数据源：能力点清单（`capability-registry`，前端静态注册，随菜单注册同步声明）+ 模板菜单配置

**兜底机制（现有，纳入校验）**：全局搜索（TopNavbar）、待办直达（StorePendingTasks 跳转映射表，含审批/退款/审核/维护/证件续期）、详情页内联操作（如证件续期对话框）、admin 角色始终全量可见（现有机制）

**对用户举例的结论**：商品档案（含新建）在单店/连锁模板下**入口均不可隐藏**——它是供应链铁三角（product）与菜品明细下拉、采购明细单价的数据源，属业务链必需能力点；若未来设计将其折叠入他组，必须登记 replacement 并在校验中验证

### 4.5 URL 直达安全（守卫按模式可达性校验）

**现状**（guards.ts）：仅检查 meta.domain（域矩阵级别）/meta.roles/meta.permissions，admin 全豁免；**无"模式可达性"检查**——菜单按模式隐藏后，知道 URL 的用户在域矩阵放行时仍可直达 → 模式隐藏形同虚设（对已知路径者）

**方案（分层防御）**：
| 层 | 职责 | 现状 |
|---|---|---|
| ① 后端 API 权限点 | **最终安全边界**（@PreAuthorize/权限码） | 已有 |
| ② 路由守卫·域/角色检查 | 域矩阵+角色+权限点检查 | 已有（guards.ts:143-177） |
| ③ 路由守卫·**模式可达性检查**（新增） | 目标路由对应能力点在该用户+激活模式下是否可达（四类入口之一） | **缺** |
| ④ 菜单过滤 | UX 层（菜单树过滤） | 已有 |

**③ 的规则**：
- 能力点**可达**（直接入口/替代入口/待办映射/搜索可达）→ 放行（不打断待办直达、替代入口跳转、跨模块联动）
- **不可达但存在 replacement** → 重定向到替代页（如 /purchase/stockin → /purchase/receiving 合一页）
- **不可达且无 replacement**（静态校验已拦截，兜底）→ 403 提示
- admin 保持豁免（既有设计：老板全量可见）
- 执行时机：守卫 beforeEach，复用菜单解析结果，避免性能重复计算

**不采用**：直接禁用 URL 直达——会打断能力保全兜底（待办/替代入口/搜索）并破坏深链/刷新体验

## 5. 数据契约影响评估（哪些变、哪些不变）

### 5.1 不变（已验证）
- POS↔管理端销售链路：产品同步、订单创建/支付/退款、班次、券核销、YOLO —— 零改动
- 跨模块联动：菜品明细下拉/采购明细/需求提报的 `/v1/store-inventory` 契约与数据权限（storeId 过滤）—— **菜单变动不影响**（API 契约 + 后端过滤，与菜单显隐零耦合；store-ops 域在单店/连锁模板均开放）
- 追溯、日结、成本链路

### 5.2 变（配置层，非业务表）
- `permission_templates.biz_policy`（新列，迁移 V20260802_00x）
- 前端菜单定义加 `visibleModes`（菜单配置，纯前端）

### 5.3 变（业务契约，独立任务）
- **门店档案↔组织架构联动**（stores_new 加组织节点关联）—— 用户明确独立于本次（见 §8）
- **开办费承接**（租金/装修/证件/设备购置费用 → 财务成本）—— 待独立排期

### 5.4 能力可达性保障（防"隐藏后无入口"）
- 能力点清单（capability-registry）随菜单注册声明，模板应用时 `validateMenuReachability` 静态校验（见 §4.4）
- 菜单显隐变化**不改变**：API 契约、路由可达性、待办/搜索兜底 → 业务数据仍可建/查/改，仅入口形态变化
- 单店模式下业务链必需能力点（商品档案、采购、门店库存、收货、菜品明细等）**保持入口可见**（其域在单店模板全开放，批 23 已验证）

## 6. 单店 vs 连锁差异化矩阵（菜单/策略落地）

| 维度 | 集中单店 centralized-single | 标准连锁 standard-chain |
|---|---|---|
| 权限 | 一人多角色（admin=老板全管）；角色少 | 角色齐全、SoD 冲突校验 |
| 审批 | 同人自审自动通过 + 审计"自审自动通过" | 完整审批链，申请人≠审批人 |
| 流程 | 到货+入库合一；采购计划步骤折叠 | 申请→审批→订单→到货→质检→入库→应付 全链 |
| 菜单 | 合并入口、审批中心=我的待办 | 全量菜单 |
| 风险 | 资金/删除二次确认（不可撤销弹窗+留痕） | SoD 天然控制 |
| 数据 | 同一套表，门店=默认门店（POS 锁定） | 多门店+组织绑定，POS 可选门店 |

## 7. 实施计划（分批，每批含验证）

> **顺序决策（用户拍板）**：以**标准连锁为超集基线**，先完善连锁的全量菜单与数据契约，再实现单店（=基线裁剪投影 + 简化策略）。
> 行业依据：SAP/金蝶实施范式"先完整蓝图（全功能基线），再按规模裁剪"；避免在混合/不完整菜单上做单店裁剪导致返工。
> 单店开发量小（纯配置 + 少量合一页），主体工作量在连锁基线化。

- **批 C0 连锁基线化（超集）**：梳理标准连锁全量能力点清单（capability-registry）+ 菜单归属 + 数据契约完整性（业务链：组织→门店→开业准备→商品→菜品→POS→日结→成本→追溯）；补齐契约缺口（POS 门店选择器、班次与日结联动确认）；此阶段暂不处理单店差异
- **批 C1 配置层**：模板表加 biz_policy 列 + 迁移；前端 getFallbackTemplates 同步；applyTemplate 下发策略
- **批 C2 菜单策略 + 守卫**：MenuGroupConfig/SubMenuItem 加 visibleModes + capability-registry 声明；`validateMenuReachability` 静态校验（无替代入口禁止隐藏）；守卫增加"模式可达性"检查层（§4.5，不可达→403/重定向，不打断兜底）；单店"合并入口"（到货+入库合一页、采购计划折叠）
- **批 C3 单店裁剪 + 业务策略落地**：visibleModes 减法 + 合并入口；同人自审自动通过（审批入口）、风险二次确认（付款/退款/结算/终止/删除）、biz_policy 开关驱动
- **批 C4 验证**：Playwright 全量回归（模式切换/菜单/联动不破）+ API 契约测试 + **能力点可达性清单检查（每种模式下逐能力点验证四类入口）** + **守卫 URL 直达测试（隐藏页面不可达→403/重定向；待办/替代入口可达）** + 文档更新

### 验证要点（回归不破坏）
- 模式切换后：菜品明细下拉仍可加载门店库存；采购明细仍带出单价；POS 下单→管理端订单可查（order 表同源）
- 深链/刷新路由可达性；守卫拦截不误伤待办直达/替代入口/搜索
- 单店模板下 admin 菜单合并正确、连锁模板全量
- **能力保全：单店模式下逐能力点（商品档案新建、采购订单、到货/入库、门店收货、审批、退款等）验证可达性 ≥1 类入口；无 replacement 的隐藏项被校验拦截**
- **URL 安全：菜单隐藏页面在守卫层被拦（403/重定向），但替代入口/待办/搜索仍可达**

## 8. 挂起项（本次范围外，已登记）

1. **门店档案 ↔ 组织架构联动**（用户巡查发现，独立任务）：组织架构在人事模块、门店档案在运营模块，当前无关联；目标：建组织节点→生成门店草稿/绑定关系。与本设计无依赖，独立排期
2. **开办费承接**：租金/装修/证件办理/开业事务费用 → 财务成本归集（需财务费用类型字典扩展）
