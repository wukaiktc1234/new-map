## 1. 逐漏洞详单（等级 / 代码定位 / 攻击场景 / 修复代码）

### RT-1 [P0] 限流键源可伪造（维度 1+2 交叉）

- **代码定位**：`backend/src/main/java/com/foodtraceability/security/filter/RateLimitFilter.java:126-140`
  ```java
  String ip = request.getHeader("X-Real-IP");      // ← 客户端完全可控
  if (ip != null && !ip.isEmpty() && !"unknown".equalsIgnoreCase(ip)) return ip;
  ```
  注：注释自述「不信任 X-Forwarded-For」，但同类伪造头 `X-Real-IP` 仍被首选。
- **攻击场景（已实测）**：
  - 同源 login 错密码连发：第 1–4 次 200，第 5/6 次 **429**（阈值 5 生效 ✓）；
  - 每次 `X-Real-IP: 10.7.$i.1` 轮换：**8 连发全部 200**——绕过成立（直连 8081，无反代覆写此头）。
  - 影响：撞库/枚举、资金端口（`/pos/orders` 60/min）防护全可被键轮换击穿——1423d62/cd55289 的「限流闭环」在攻击者面前失效。
- **修复代码**：
  ```java
  // 1) 配置面：application.yml 增加 rate-limit.trusted-proxies 列表（CIDR）
  private String resolveClientIp(HttpServletRequest req) {
      String remote = req.getRemoteAddr();                    // socket 真址
      if (!isTrustedProxy(remote)) return remote;             // 直连：绝不读任何头
      String real = req.getHeader("X-Real-IP");               // 可信代理链才解码
      return (real != null && !real.isBlank()) ? real : remote;
  }
  // 2) 内存 Map 每 60s 全量清理「窗口已过期」条目（防 unbounded），
  //    多实例部署切 Caffeine + Redis（tech-debt SEC-1 关闭条件）。
  ```

### RT-2 [P1] RuntimeException→500 的 HTTP 状态未落地（维度 3/4 交叉）

- **代码定位**：`GlobalExceptionHandler.java:341-356`（`handleRuntimeException/handleException` 返回 `Result.error(500,…)`，**无 HTTP 状态设置**）；`62f1eb3` 声称「resolveHttpStatus 400/403/404 真码」，500 类未包含。
- **攻击场景（已实测）**：`cashier POST /v1/appeals/NOPE/process` → **HTTP 200 + body code=500**（R6 时同形态，时至今日未变）——监控按状态码告警仍失效；POS 前端只能靠 body code 兜底。
- **修复代码**：
  ```java
  @ExceptionHandler(RuntimeException.class)
  public ResponseEntity<Result<?>> handleRuntimeException(RuntimeException e) {
      ...
      return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
              .body(Result.error(500, buildUserMessage(traceId)));
  }
  // 或 resolveHttpStatus(500) 统一；并把下列三类 handler 逐一 ResponseEntity 化：
  //   AuthenticationException→401、NullPointer/Exception→500、IllegalArgumentException→400
  ```

### RT-3 [P1] 同单二次 void：幂等冲突 500 + casCancel 谓词不对称（维度 2）

- **代码定位**：
  - `ExceptionOpsMapper.java:52-54` `casCancel WHERE … COALESCE(payment_status,0)<>2 AND deleted=0`（**未像 casMarkPaid 一样补 `order_status=0`**）
  - `PosExceptionTxBean.java:196-199`（casRows==0 只有默认文案；**没有 resolve 已有的 `osNow==3||5` 终态分流**）
  - `PosExceptionOpsAttempt.java:28-31`（NESTED 保存点内 insert 冲突异常直接向调用方传播，无 replay/409 转译）
- **攻击/触发（实测）**：对已作废单 `O1793287678113` 用新 key 二次 void → `casCancel` 依然 rows=1（order_status=3 不被谓词排除）→ `insertWithinSavepoint` 撞 `uk_exception_ops_order` 部分唯一 → 异常穿透 → **HTTP 200 + body 500「系统繁忙」**（追踪ID：596c237f60f7）。
- **后果**：收银员双击/两终端竞态得到 500（体验断头路）；审计记录无第二操作痕迹；`resolve` 与 `void` 语义分叉。
- **修复代码**：
  ```java
  // 1) casCancel 对称化（与 casMarkPaid 同一权威谓词族）
  @Update("UPDATE orders SET order_status=3, update_time=now() WHERE order_id=#{orderId} "
        + "AND COALESCE(order_status,0)=0 AND COALESCE(payment_status,0)<>2 AND deleted=0")
  // 2) void casRows==0 分流（与 resolve 对齐，POSExceptionTxBean）
  Integer os = exceptionOpsMapper.orderStatusOf(orderId);
  if (os != null && (os == 3 || os == 5)) {
      return ResolveResult.fail(Status.ALREADY_HANDLED, "订单已" + (os==3?"取消":"退款") + "，无需再作废");
  }
  // 3) 冲突转译（PosExceptionOpsAttempt 或 txBean 处）
  try { opsAttempt.insertWithinSavepoint(ops); }
  catch (DataIntegrityViolationException e) {
      throw new BusinessException(40902, "该订单已被其它操作处理，请刷新"); // controller 映射 409
  }
  ```

### RT-4 [P1] void 联动缺陷：KO try-warn 吞异常 + 库存回补缺口（维度 3/2）

- **代码定位**：`PosExceptionTxBean.java:216-218`（KO 取消失败仅 warn，void 照常提交）；`:220-224`（`exception_void_inventory_release_skipped` metric 仍在——R6 P1-4 谕示的「复用 TTL 同源 food_id→food_code 回补」**未落地**）。

- **修复代码**：

  // 库存回补直接复用 TTL 关单同源实现（不必等 dish_ingredient 映射）：
  List<Map<String,Object>> items = ttlCloseMapper.findItems(orderId);   // food_id/quantity
