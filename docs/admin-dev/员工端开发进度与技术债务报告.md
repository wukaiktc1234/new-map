### 1.3 管理端权限模板与员工端的对应关系

管理端 [034 可配置权限架构](../034-configurable-permission-architecture/spec.md) 已定义 **4 种预设模板**，每种模板决定了员工端的功能边界：

#### 模板 A：enterprise-chain（大型连锁）

| 维度 | 配置 | 对员工端的影响 |
|------|------|--------------|
| 适用画像 | 5+门店，每店50-200人 | 员工端需支持多门店切换视角 |
| 店长权限 | 拥有 hr 域（人事管理） | 店长可在员工端看到团队考勤/审批 |
| 采购权限 | 门店自治 | 员工端可能需要物品领用功能 |
| 员工数据范围 | store（本门店） | 员工只能看到本门店的数据 |

#### 模板 B：standard-chain（标准连锁）← **目标用户**

| 维度 | 配置 | 对员工端的影响 |
|------|------|--------------|
| 适用画像 | 3-10店，每店15-50人 | **最匹配当前员工端设计** |
| 店长权限 | 无 hr/purchase/finance 域 | 店长在员工端也是"执行者"而非"管理者" |
| 采购权限 | 区域集中 | 员工端不需要采购相关功能 |
| 员工数据范围 | store（本门店） | 同上 |

#### 模板 C：centralized-single（集中式单店）

| 维度 | 配置 | 对员工端的影响 |
|------|------|--------------|
| 适用画像 | 单店，3-20人 | 最简模式，员工端功能最少 |
| 店长权限 | 仅 store-ops + product + order | 纯执行层 |
| 员工数据范围 | store（本门店） | 同上 |

#### 模板 D：custom（完全自定义）

| 维度 | 配置 | 对员工端的影响 |
|------|------|--------------|
| 适用画像 | 特殊业态 | 员工端需动态适配任意配置 |
| 权限 | 逐项配置 | 员工端功能完全由管理端决定 |

## 二、管理端能力调研（员工端可继承什么）

### 2.1 管理端已具备的员工端相关能力

#### 2.1.1 认证体系（员工端可直接复用）

```
登录流程:
  POST /v1/auth/login → token + refreshToken + userInfo
      ↓
  Token 存储: localStorage (token / refresh_token)
      ↓
  路由守卫自动触发:
    ① 检查 token 存在性
    ② 调用 authStore.getUserInfo() 获取 { id, name, roles[], permissions[] }
    ③ 调用 permissionStore.initFromAuthStore() 初始化权限
    ④ 初始化功能模块 (featureModuleStore)
      ↓
  页面渲染（受 DataScope 控制）
```

**关键产出物**（员工端对接时直接使用）：
- `userInfo.roles[]` — 角色代码列表，员工端据此判断 UserLevel
- `userInfo.permissions[]` — 权限码列表，员工端据此控制功能可见性
- `token` / `refreshToken` — 认证凭证，员工端请求拦截器复用相同逻辑

#### 2.1.2 权限模板系统（决定员工端功能边界）

管理端权限中心的 **4 种预设模板** 直接决定了员工端能做什么、不能做什么：

| 模板 | 员工(hr域)是否开放 | 员工能否看到团队数据 | 审批流复杂度 |
|------|:------------------:|:---------------------:|:-----------:|
| enterprise-chain | ✅ 店长有hr权限 | ✅ L3+ 可看团队 | 高（多级审批） |
| standard-chain | ❌ 仅总部hr | ⚠️ 仅本人 | 中 |
| centralized-single | ❌ 仅owner | ⚠️ 仅本人 | 低 |
| custom | 由配置决定 | 由配置决定 | 由配置决定 |

**结论**：员工端无需自己设计"谁能看什么"，全部由管理端模板决定。

#### 2.1.3 9 大业务域（员工端涉及其中 3 个）

| 域编码 | 域名称 | 员工端是否使用 | 说明 |
|--------|--------|:-------------:|------|
| store-ops | 门店运营 | ✅ | 排班查看、日结查看、交接班 |
| hr | 人事管理 | ✅ **核心** | 考勤、薪资、请假、审批、培训 |
| finance | 财务管理 | ⚠️ 部分 | 工资条查看、报销提交 |
| product | 产品管理 | ❌ | 不涉及 |
| order | 订单管理 | ❌ | 不涉及 |
| operations | 运营分析 | ❌ | 不涉及 |
| purchase | 采购管理 | ❌ | 不涉及（除非有物品领用） |
| warehouse | 仓储管理 | ❌ | 不涉及 |
| system | 系统管理 | ❌ | 不涉及 |

#### 2.1.4 DataScope 数据范围（员工端继承 self/store 两级）

管理端定义了 8 级 DataScopeType，但员工端实际只继承其中 2 级：

| DataScope | 员工端是否使用 | 映射到员工端行为 |
|-----------|:-------------:|-----------------|
| all | ❌ | 超管专用 |
| company | ❌ | 总部人员专用 |
| region | ❌ | 区域经理专用 |
| stores | ❌ | 多门店管理员专用 |
| **store** | **✅** | **L3+ 用户查看团队数据的范围** |
| **department** | **✅** | **部门级数据过滤** |
| **self** | **✅** | **L1/L2 用户默认仅看本人数据** |

## 三、兼容性与协同对接分析

### 3.1 架构差异总览（继承前的 Gap）

| 维度 | 管理端（决策方） | 员工端（继承方） | 差异性质 | 如何消除 |
|------|-----------------|-----------------|---------|---------|
| 身份来源 | `roles[]` + `permissions[]` 从 JWT 提取 | `UserLevel` 枚举硬编码 | **需适配** | 从 JWT 的 roles[] 派生 UserLevel |
| 权限粒度 | 150+ 权限码 `{domain}:{resource}:{action}` | 无（Mock 阶段） | **需继承** | 员工端按需检查 permissions[] |
| 数据范围 | 8 级 DataScopeType | 扁平 L1-L5 | **需映射** | DataScope.self → L1/L2, DataScope.store → L3+ |
| 认证流程 | 完整（Login→Token→UserInfo→Perm） | Mock 硬编码 | **需替换** | 复用管理端认证链路 |
| 请求层 | ~700 行生产级 | ~187 行最小实现 | **需升级** | 移植关键能力（取消/重试/CSRF） |
| 菜单/路由 | 动态注册（15模块自注册） | 静态路由 | **正常差异** | 员工端菜单固定，不需动态化 |

### 3.2 关键对接点详解

#### 对接点 1：身份模型适配（Mock → 继承）

**当前（Mock 模式）**：
```typescript
// useAuthContext.ts — 当前硬编码
const _userLevel = ref<UserLevel>(UserLevel.STAFF)  // 写死
const _userRole = ref('store_staff')                 // 写死
```

**目标（继承管理端）**：
```typescript
// useAuthContext.ts — 对接后从 JWT 派生
// 登录成功后，从 authStore.userInfo 派生:
const _userLevel = deriveUserLevel(authStore.userInfo.roles)
// roles: ["store_staff"] → UserLevel.STAFF(1)
// roles: ["team_leader"] → UserLevel.SUPERVISOR(2)
// roles: ["store_manager"] → UserLevel.MANAGER(3)

const _userRole = authStore.userInfo.roles[0] // 取主角色
const _userId = String(authStore.userInfo.id)
const _userName = authStore.userInfo.name
```

**派生规则表**（建议管理端确认或扩展）：

| 管理端角色代码 | 派生为 UserLevel | 审批能力 | 数据范围 |
|--------------|-----------------|---------|---------|
| employee / store_staff | STAFF (1) | 不可审批 | self（仅本人） |
| team_leader / shift_leader / supervisor | SUPERVISOR (2) | 可审批L1 | self |
| store_manager / department_manager | MANAGER (3) | 可审批L1-L2 | store（本门店） |
| region_manager / ops_director | REGION_MANAGER (4) | 可审批L1-L3 | region（本区域） |
| owner / admin / super_admin | STORE_MANAGER (5) | 全部 | company（全公司） |

> **⚠️ 需要管理端配合**：确保角色代码命名规范统一，或在 JWT Payload 中直接返回 `level` 字段。

#### 对接点 2：功能可见性继承（从域权限矩阵）

员工端的功能可见性不应自己判断，而应**继承管理端域权限矩阵的结果**：

```
管理端配置（示例：standard-chain 模板下的 employee 角色）
┌──────────────────────────────────────────────────┐
│ employee 角色的域权限:                            │
│   ✓ store-ops  → 员工端可看排班/日结             │
│   ✗ hr          → 员工端不可看人事管理            │
│   ✗ finance     → 员工端不可看财务管理            │
│   ✗ ...其他域   → 不可见                          │
└──────────────────────────────────────────────────┘
                    ↓ 继承
┌──────────────────────────────────────────────────┐
│ 员工端功能菜单（根据域权限自动显示/隐藏）:         │
│   ✓ 首页工作台    （公共，始终可见）               │
│   ✓ 我的排班     （store-ops 域允许）             │
│   ✓ 我的考勤     （store-ops 域允许）             │
│   ✓ 我的薪资     （hr 域的 salary:view 子权限）   │
│   ✓ 审批管理     （hr 域的 approval:create 子权限）│
│   ✗ 采购管理     （purchase 域不允许 → 整个隐藏）  │
│   ✗ 仓储管理     （warehouse 域不允许 → 整个隐藏） │
└──────────────────────────────────────────────────┘
```

**实现方式建议**：后端提供 `/v1/employee/menu` 接口，返回当前用户在员工端可见的功能列表（已根据域权限矩阵过滤）。员工端启动时拉取一次，据此渲染底部导航。

> **⚠️ 需要管理端配合**：新增员工端专用的聚合接口，返回经过域权限过滤后的功能清单。

#### 对接点 3：审批链路继承（从角色层级）

当前员工端审批链路是硬编码的 `LEVEL_CONFIG_MAP`。对接后应从管理端的角色层级获取：

```
当前（硬编码）:
  LEVEL_CONFIG_MAP[UserLevel.MANAGER].canApproveLevels = [STAFF, SUPERVISOR]

目标（继承管理端）:
  从后端获取当前用户的审批配置:
  GET /v1/employee/approval-config
  → {
      canApprove: true,
      maxAmount: 20000,           // 最大审批金额（分）
      approvableLevels: [1, 2],    // 可审批哪些层级
      chain: [...]                 // 完整审批链路
    }
```

> **⚠️ 需要管理端配合**：新增员工端审批配置接口，或扩展现有 `/v1/approvals/config` 接口支持员工端视角。

### 3.3 管理端缺失项（需要补充以支持员工端协同）

以下事项在管理端现有设计中**未覆盖员工端场景**，需要补充：

| 编号 | 缺失项 | 员工端影响 | 建议管理端补充内容 | 优先级 |
|------|--------|----------|-------------------|--------|
| **G-01** | **无员工端专用 API 网关** | 员工端需调用多个管理端接口聚合数据 | 新增 `/v1/employee/*` 前缀的聚合接口（如 `/employee/dashboard` 一次性返回待办+排班+通知） | **P0** |

## 四、数据库策略

### 4.1 策略决策

**员工端开发过程中不创建任何数据库迁移文件，统一由管理端负责。**

### 4.2 依据

| # | 理由 | 说明 |
|---|------|------|
| 1 | 员工端所需表已全部就绪 | 后端已有 70+ 个迁移文件，覆盖 users/roles/hr/finance/approval/schedule/notification 等 |
| 2 | 共享同一后端实例 | DDL 统一管理避免 Schema 冲突 |
| 3 | 职责分离 | 员工端 = 消费 API，管理端 = 管理资源（含数据库） |
| 4 | 符合继承模型 | 管理端建表 → 定义 API → 员工端调用，单向依赖 |

### 4.3 员工端涉及的表（已在管理端迁移中创建）

| 组织架构 | V1.0.0/V20260319 | stores, departments, positions | 门店/部门/岗位 |

### 4.4 执行规则

- 员工端需新字段/新表 → 提交需求给管理端，由管理端创建迁移
- 员工端 Mock 数据层不受限制（纯前端模拟）
- 后端 API 开发需新表 → 由后端/管理端统一处理

### 7.5 Phase 4 详细设计方案

> 参考来源：CSDN《现代员工管理系统》(2026-05-30) + 知乎《OA系统功能模块深度解析》
>
> 设计原则：前端先行(Mock→API)、管理端为主(知识库CMS)、体验优先(降低管理语言)

#### F-17: 今日考勤快捷卡片

**目标**：HomePage 第 5 张 StatCard，打开即知今日考勤状态。

**数据结构**：
```typescript
interface TodayAttendance {
  status: 'normal' | 'late' | 'early_leave' | 'absent' | 'not_clocked_in' | 'overtime'
  clockInTime: string | null
  clockOutTime: string | null
  currentHours: number
  expectedHours: number
  shiftName: string
  exceptionType?: string
}
```

**交互**：正常→跳转AttendancePage；异常→红色提示+[异常处理]按钮；加班中→绿色高亮。

**文件**：新建 `TodayAttendanceCard.vue` + `api/attendance.ts` Mock 方法

#### F-18: 知识库阅读页面

**架构**：管理端 CMS 创建/发布 → 员工端只读消费。大部分内容通用不分岗位。

**分类**：安全规范 / 服务标准 / 操作手册 / 公司制度（4 类）

**UI**：独立路由 `/knowledge`，搜索+分类筛选+文章列表+Markdown详情页+收藏

**文件**：新建 `KnowledgePage.vue` + `api/knowledge.ts` + `types/knowledge.ts`

#### F-19: 任务管理轻量入口

**方式**：不新增页面，扩展现有 TodoSummaryCard 为审批/指派/考核三合一待办中心。

**视觉区分**：审批(蓝边框) / 指派(橙边框+截止倒计时) / 考核(紫边框)

**文件**：修改 `TodoSummaryCard.vue` + `useHomeData.ts`；新建 `api/task.ts`

#### F-20: 全局文案体验优化

**核心映射**（20项）："审批流"→"我的申请"、"考勤统计"→"我的出勤"、"工资条"→"我的收入"、"待我审批"→"需要我确认"、"确认/驳回"→"同意/有疑问" 等

**实施**：全局 Grep → 逐个替换 → 验证语义一致性
