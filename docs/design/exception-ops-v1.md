# 异常单处理闭环 V1.0 — 后端落地稿（DDL + Resolve 核心实现）

> 约束对齐：金额全 **Fen(bigint)**；写接口必带 `idempotencyKey`；状态变更走 **CAS**；交班前校验 `pendingExceptionCount == 0` → 409。
> 工程约定（本项目实测踩过）：无 Lombok（访问器手写）；主键 `GENERATED BY DEFAULT AS IDENTITY`（`ALWAYS` 会与 MyBatis `ASSIGN_ID` 冲突）；**禁止 `INSERT ... ON CONFLICT`**（唯一键冲突会 abort 整个事务，SQLState 25P02），改用 **保存点(NESTED)**；迁移必须自带 `DO $$ ... RAISE EXCEPTION` 断言。

SELECT 'ROLE_CASHIER', 'PERM_POS_ORDER_VOID', 0, now()

DECLARE bad int;
BEGIN
    -- 表与列
    IF to_regclass('public.exception_ops') IS NULL THEN
        RAISE EXCEPTION '迁移失败：exception_ops 表未创建';

    END IF;
    -- 权限码与授权（本迁移负责的，必须全在）

     WHERE permission_code = 'pos:order:void' AND deleted = 0;
    IF bad = 0 THEN RAISE EXCEPTION '迁移失败：权限码 pos:order:void 未登记'; END IF;

    SELECT count(*) INTO bad FROM role_permissions
     WHERE role_id='ROLE_CASHIER' AND deleted=0
       AND permission_id IN ('PERM_POS_ORDER_PAY','PERM_POS_ORDER_VOID');
    IF bad <> 2 THEN RAISE EXCEPTION '迁移失败：ROLE_CASHIER 应持有 pay+void 两码，实际 %', bad; END IF;
END $$;

## 2. API 契约与状态码

| 场景 | HTTP | body.code | 说明 |
|---|---|---|---|
| 成功 | 200 | 0 | 返回最新 `shiftStats` 全量快照 |
| 金额与应收不符 | **422** | 42201 | `AMOUNT_MISMATCH` |
| 订单已被其他终端处理（CAS 命中 0 行） | **409** | 40901 | `ALREADY_HANDLED` |
| 幂等重放（同 key 已成功） | 200 | 0 | **不再执行任何写操作**，直接返回快照 |
| 交班时存在未处理异常单 | **409** | 40902 | `PENDING_EXCEPTIONS`，body 带 `pendingExceptionCount` |

## 3. Resolve 核心实现

### 3.1 Controller

```java
@RestController
@RequestMapping("/api/v1/pos/exceptions")
public class PosExceptionController {

    private final PosExceptionService service;

    public PosExceptionController(PosExceptionService service) { this.service = service; }

    /** 补收款：POST /api/v1/pos/exceptions/{orderId}/resolve */
    @PostMapping("/{orderId}/resolve")
    @PreAuthorize("hasAuthority('pos:order:pay')")
    public ResponseEntity<Result<ShiftStatsVO>> resolve(@PathVariable String orderId,
                                                        @RequestBody @Valid ResolveExceptionRequest req,
                                                        @RequestHeader(value = "X-Operator-Id", required = false) String operatorId) {
        ResolveResult r = service.resolve(orderId, req, operatorId);
        switch (r.getStatus()) {
            case OK:
            case REPLAY:      // 幂等重放：同一个 key 再来一次，不改数据
                return ResponseEntity.ok(Result.success(r.getShiftStats()));
            case AMOUNT_MISMATCH:
                return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
                        .body(Result.error(42201, r.getMessage()));
            case ALREADY_HANDLED:
                return ResponseEntity.status(HttpStatus.CONFLICT)
                        .body(Result.error(40901, r.getMessage()));
            default:
                return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                        .body(Result.error(500, r.getMessage()));
        }
    }
}
```

> 说明：本项目历史上所有业务异常都包成 HTTP 200 + body.code（反模式），本接口**按契约返回真 409/422**；已在 `tech-debt` 记录为「HTTP 语义分批改造」的第一批。

### 3.2 Service（事务 + CAS + 保存点幂等）

```java
@Service
public class PosExceptionServiceImpl implements PosExceptionService {

    private static final Logger log = LoggerFactory.getLogger(PosExceptionServiceImpl.class);

    private final OrderNewMapper orderNewMapper;
    private final OrderPaymentRecordNewMapper paymentRecordMapper;
    private final FundFlowMapper fundFlowMapper;
    private final ExceptionOpsMapper exceptionOpsMapper;
    private final ShiftStatsService shiftStatsService;   // 复用交班统计（含退款扣减口径）
    private final PosExceptionOpsAttempt opsAttempt;      // 保存点写入器（见 3.3）

    // 构造器注入（项目无 Lombok）

    @Override
    public ResolveResult resolve(String orderId, ResolveExceptionRequest req, String operatorId) {
        // 0) 幂等前置：同 key 已成功 → 直接返回快照（不做任何写）
        ExceptionOps existed = exceptionOpsMapper.selectByKey(req.getIdempotencyKey());
        if (existed != null) {
            if (!orderId.equals(existed.getOrderId())) {
                return ResolveResult.fail(ALREADY_HANDLED, "幂等键已被其它订单占用");
            }
            log.info("[EXC-OPS] 幂等重放 orderId={} key={}", orderId, req.getIdempotencyKey());
            return ResolveResult.replay(shiftStatsService.snapshot(existed.getShiftId()));
        }
        // 关键：真正的写操作必须在事务内 → 这里委托到自调用之外的 Bean（避免 this.xxx() 代理失效）
        return opsAttempt.executeResolve(orderId, req, operatorId);
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public ResolveResult doResolveInTx(String orderId, ResolveExceptionRequest req, String operatorId) {
        // 1) 读订单（锁外读，靠 CAS 兜并发）
        OrderNew order = orderNewMapper.selectByOrderId(orderId);   // WHERE order_id = #{orderId} AND deleted = 0
        if (order == null) {
            return ResolveResult.fail(ALREADY_HANDLED, "订单不存在或已删除：" + orderId);
        }
        if (order.getShiftId() != null) { /* 记录班次，供后续统计 */ }

        // 2) 金额校验：一律用分；应收 = final_amount（分）
        long receivableFen = order.getFinalAmount() == null ? order.getTotalAmount() : order.getFinalAmount();
        if (req.getAmountFen() == null || req.getAmountFen() != receivableFen) {
            return ResolveResult.fail(AMOUNT_MISMATCH,
                    "金额不符：应收 " + receivableFen + " 分，请求 " + req.getAmountFen() + " 分");
        }
        if ("CASH".equals(req.getPayType()) && req.getCashReceivedFen() == null) {
            return ResolveResult.fail(AMOUNT_MISMATCH, "现金支付必须提供 cashReceivedFen");
        }

        // 3) CAS 更新订单：status 必须仍是 pending，否则说明别的终端已处理
        int casRows = orderNewMapper.casMarkPaid(orderId, req.getAmountFen(), req.getPayType());
        if (casRows == 0) {
            log.warn("[EXC-OPS] CAS 未命中（已被其它终端处理） orderId={}", orderId);
            return ResolveResult.fail(ALREADY_HANDLED, "该订单已被其它终端处理，请刷新后重试");
        }

        // 4) 支付流水
        OrderPaymentRecordNew pay = new OrderPaymentRecordNew();
        pay.setOrderId(orderId);
        pay.setPayType(req.getPayType());
        pay.setAmountFen(req.getAmountFen());
        pay.setCashReceivedFen(req.getCashReceivedFen());
        pay.setOperatorId(operatorId);
        pay.setTransactionId(generateTxnNo(req.getPayType()));   // CSH-/WX-/ALI- 前缀（见发现⑤的修复）
        paymentRecordMapper.insert(pay);

        // 5) 资金流水（记负数才是出账，这里是入账 → 正数；方向见 money-unit-boundary.md）
        FundFlow flow = new FundFlow();
        flow.setFlowNo(genFlowNo());
        flow.setOrderId(orderId);
        flow.setAmountFen(req.getAmountFen());
        flow.setFlowCategory("SALE");
        flow.setFlowDirection("IN");
        flow.setPayType(req.getPayType());
        fundFlowMapper.insert(flow);

        // 6) 异常单操作记录（唯一键冲突用保存点兜，禁止 ON CONFLICT）
        ExceptionOps ops = new ExceptionOps();
        ops.setOrderId(orderId);
        ops.setOpType("RESOLVE");
        ops.setIdempotencyKey(req.getIdempotencyKey());
        ops.setAmountFen(req.getAmountFen());
        ops.setPayType(req.getPayType());
        ops.setCashReceivedFen(req.getCashReceivedFen());
        ops.setOperatorId(operatorId);
        ops.setShiftId(order.getShiftId());
        ops.setFlowNo(flow.getFlowNo());
        opsAttempt.insertWithinSavepoint(ops);   // 见 3.3：撞唯一键只回滚保存点，外层事务不中止

        // 7) 返回最新班次快照（全量，含退款扣减口径）
        return ResolveResult.ok(shiftStatsService.snapshot(order.getShiftId()));
    }
}
```

### 3.3 保存点写入器（**这是本项目最关键的坑**）

```java
@Component
public class PosExceptionOpsAttempt {

    private final ExceptionOpsMapper mapper;

    /**
     * ⚠ 为什么不用 INSERT ... ON CONFLICT（请勿「优化」回来）：
     * 唯一键冲突会让 PostgreSQL 把【外层事务】标记为 aborted（SQLState 25P02），
     * 后续任何 SQL 都报 "current transaction is aborted"，接口表现成 500 且数据半写入。
     * 保存点只回滚这一段，外层事务继续可用。
     */
    @Transactional(propagation = Propagation.NESTED, rollbackFor = Exception.class)
    public void insertWithinSavepoint(ExceptionOps ops) {
        mapper.insert(ops);
    }
}
```

### 3.4 CAS 的 Mapper 语句（必须带状态条件）

```xml
<update id="casMarkPaid">
    UPDATE orders
       SET order_status   = 'paid',
           payment_status = 2,
           paid_amount    = #{amountFen},
           payment_method = #{payType},
           update_time    = now()
     WHERE order_id = #{orderId}
       AND order_status = 'pending'      <!-- CAS 条件：只有仍是 pending 才更新 -->
       AND deleted = 0
</update>
```

> 返回影响行数：**0 = 已被别的终端处理 → 409**；**1 = 本次抢到**。这是防「多终端并发双收」的唯一正确做法，不能先 SELECT 再 UPDATE。

## 4. 交班闸（409 PENDING_EXCEPTIONS）

```java
// endShift 内、任何写操作之前
long pending = orderNewMapper.countPendingExceptionOrders(shiftId);
if (pending > 0) {
    throw new BusinessException(40902,
        "本班次还有 " + pending + " 笔待处理异常单，请先处理后再交班", "PENDING_EXCEPTIONS");
}
```

```xml
<select id="countPendingExceptionOrders" resultType="long">
    SELECT count(*)
      FROM orders o
     WHERE o.shift_id = #{shiftId}
       AND o.deleted = 0
       AND o.order_status = 'pending'
       AND COALESCE(o.payment_status, 0) &lt;&gt; 2                    <!-- 未支付 -->
       AND NOT EXISTS (SELECT 1 FROM exception_ops e
                        WHERE e.order_id = o.order_id AND e.deleted = 0)
</select>
```

> **口径说明**：`pendingExceptionCount` = 本班次「仍 pending 且未支付、且尚未有 exception_ops 记录」的订单数。
> 注意 `orders.shift_id` 对历史数据为 NULL（不回溯），故历史班次该值为 0 —— 与「历史账绝不回溯」一致。

## 5. 待产品/需确认的三点（先落代码再定，不阻塞）

1. **`reason` 枚举清单**：VOID 的 `reason` 需给固定枚举（如 `CUSTOMER_CANCEL` / `OUT_OF_STOCK` / `WRONG_ORDER`），我需要产品给全集；
2. **`shiftStats` 全量快照字段**：建议沿用现有交班统计口径（营收 / 退款 / 净额 / 现金 / 非现金），避免出现第二套算法；
3. **`exception_ops.order_id` 唯一** 意味着「一单只能操作一次」。若业务允许「先 VOID 再 RESOLVE」这类组合，需改为 `(order_id, op_type)` 唯一。

## 6. 自测清单（落地后必须逐条给证据）

- [ ] 幂等：同 `idempotencyKey` 连发 2 次 → 第 2 次不改数据（`exception_ops` 仍 1 行、`fund_flows` 不增加），返回同一快照；
- [ ] CAS 并发：两终端同时 resolve 同一单 → **恰好 1 个 200、1 个 409**，`fund_flows` 只 +1；
- [ ] 金额不符：请求 `amountFen` = 应收 −1 → **422**，且 `orders` 状态不变；
- [ ] 交班闸：留 1 笔 pending → `endShift` **409 PENDING_EXCEPTIONS** 且 `pos_shifts` 状态不变；
- [ ] VOID：确认 `fund_flows` **零新增**、`kitchen_order` 变 `cancelled`、`inventory.locked_quantity` 释放；
- [ ] 单位：全链路只用 `*_Fen`，DB 校验 `amount_fen` 为整型分（禁止任何 `numeric` 元）。
