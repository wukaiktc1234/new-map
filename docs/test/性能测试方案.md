# 食品溯源系统管理端 - 性能测试方案

> **文档版本**：v1.0
> **文档日期**：2026-07-01
> **测试范围**：管理端接口响应时间、并发处理、资源占用、缓存命中率
> **适用环境**：开发环境（H2）+ 生产环境模拟（PostgreSQL）

---

## 一、测试概述

### 1.1 测试目标

验证食品溯源系统管理端在预期负载下的性能表现，确保接口响应时间、系统吞吐量、资源占用等指标满足业务需求，识别性能瓶颈并提供优化依据，为生产环境商用上线提供性能保障。

### 1.2 测试环境

| 项目 | 开发环境 | 生产模拟环境 |
|------|---------|------------|
| 后端服务 | http://localhost:8081/api | http://localhost:8081/api |
| 前端服务 | http://localhost:3000 | Nginx 静态部署 |
| 数据库 | H2 内存（MODE=PostgreSQL） | PostgreSQL 18 |
| 缓存 | Redis 单机 | Redis 哨兵集群 |
| 消息队列 | RabbitMQ 单机 | RabbitMQ 镜像队列 |
| JDK | 21 | 21 |
| CPU | 4 核 | 8 核+ |
| 内存 | 8 GB | 16 GB+ |

| 指标 | 阈值 | 告警条件 | 说明 |
|------|------|---------|------|

## 二、性能测试工具

### 2.1 工具推荐

| 工具 | 用途 | 优势 |
|------|------|------|
| **JMeter** | 接口压测、负载测试 | 图形化、协议丰富、插件多 |
| **k6** | 现代化负载测试 | 脚本化（JS）、性能好、CI 友好 |
| **Postman** | 接口调试、简单压测 | 易用、Collection Runner |
| **JProfiler / ARMS** | JVM 监控 | 内存/线程/CPU 分析 |
| **pgBadger** | PostgreSQL 慢查询分析 | 日志分析 |
| **Redis CLI** | 缓存监控 | info / slowlog |

### 2.2 JMeter 测试计划模板

```
Test Plan
├── Thread Group（线程组）
│   ├── HTTP Header Manager（Authorization: Bearer ${token}）
│   ├── HTTP Request Sampler（接口请求）
│   ├── Assertions（响应断言）
│   ├── Timer（思考时间）
│   └── Listener（结果收集）
├── CSV Data Set Config（参数化数据）
├── User Defined Variables（环境变量）
└── Listener（Aggregate Report / Summary Report）
```

### 2.3 k6 脚本示例

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },   // 30 秒内升至 50 并发
    { duration: '1m', target: 50 },    // 维持 50 并发 1 分钟
    { duration: '30s', target: 0 },    // 30 秒内降至 0
  ],
  thresholds: {
    http_req_duration: ['p(95)<3000'], // 95% 请求 < 3s
    http_req_failed: ['rate<0.01'],    // 错误率 < 1%
  },
};

export default function () {
  const params = {
    headers: { Authorization: `Bearer ${__ENV.TOKEN}` },
  };
  const res = http.get('http://localhost:8081/api/v1/foods?page=1&size=20', params);
  check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 3s': (r) => r.timings.duration < 3000,
  });
  sleep(1);
}
```

## 五、性能测试执行流程

### 5.1 测试准备阶段

1. **环境准备**
   - 部署测试环境（接近生产配置）
   - 准备测试数据（按生产规模 1:1 或 1:10）
   - 启动监控工具

2. **脚本准备**
   - 编写 JMeter / k6 测试脚本
   - 准备参数化数据（CSV）
   - 配置断言与监听器

3. **基准测试**
   - 单用户单接口基准
   - 记录基线指标

### 5.2 测试执行阶段

1. **负载测试**
   - 按预期负载执行
   - 阶梯加压（50→100→200）
   - 记录每阶段指标

2. **压力测试**
   - 持续加压至系统崩溃
   - 记录极限值
   - 验证恢复能力

3. **稳定性测试**
   - 长时间运行（8 小时+）
   - 监控内存泄漏
   - 验证性能衰减

### 5.3 结果分析阶段

1. **指标对比**
   - 与基线对比
   - 与阈值对比
   - 识别异常点

2. **瓶颈定位**
   - 数据库慢查询分析
   - JVM 内存/GC 分析
   - 接口耗时分解

3. **优化建议**
   - 索引优化
   - 缓存策略优化
   - 代码优化
   - 资源扩容建议

## 七、性能优化建议（基于已知问题）

### 7.1 已知性能风险

根据项目待修复问题清单（PENDING_ISSUES_BACKLOG.md），以下问题影响性能：

| 问题 | 影响 | 优化建议 |
|------|------|---------|
| 运营中心 KPI 全硬编码 mock | 报表数据不真实 | 接入真实聚合查询，添加缓存 |
| LiveMonitorController 返回空 | 实时监控不可用 | 接入实时查询，使用 SSE 推送 |
| H2 数据库 Flyway 禁用 | 数据初始化混乱 | 启用 Flyway 统一管理 |
| stores_new.manager_id 类型不匹配 | 跨表 JOIN 失败 | 修复类型，添加索引 |

### 7.2 通用优化建议

1. **数据库优化**
   - 添加常用查询字段的组合索引
   - 优化深分页（使用游标或覆盖索引）
   - 避免大事务，拆分长事务
   - 使用读写分离减轻主库压力

2. **缓存优化**
   - 提高基本信息缓存命中率（>80%）
   - 使用本地缓存（Caffeine）+ Redis 二级缓存
   - 缓存预热：启动时加载常用数据
   - 防雪崩：过期时间加随机偏移

3. **接口优化**
   - 列表查询避免 SELECT *
   - 关联查询使用 JOIN 而非 N+1
   - 大数据量使用流式处理
   - 异步导出避免阻塞

4. **前端优化**
   - 路由懒加载
   - 列表虚拟滚动（大数据量）
   - 图片懒加载
   - 接口防抖（搜索框）
