## 二、行业调研

### 2.1 法规要求

#### 2.1.1 《中华人民共和国食品安全法》（2025 年第三次修正）

- **第四十二条**：国家建立食品安全全程追溯制度。食品生产经营者应当依照本法建立食品安全追溯体系，保证食品可追溯。国家鼓励采用信息化手段采集、留存生产经营信息。
- **第四十二条**进一步明确：食品经营企业应当建立食品进货查验记录制度，如实记录食品的名称、规格、数量、生产日期或者生产批号、保质期、进货日期以及供货者名称、地址、联系方式等内容。
- **第五十四条**：食品经营者应当按照保证食品安全的要求贮存食品，定期检查库存食品，及时清理变质或者超过保质期的食品。

**对系统的要求**：必须建立"来源可查、去向可追、责任可究"的全链条追溯体系，记录内容须包含名称、规格、数量、生产日期/批号、保质期、进货日期、供货者信息等关键字段。

#### 2.1.2 《网络餐饮服务经营者落实食品安全主体责任监督管理规定》（2026 年 6 月 1 日施行）

- 市场监管总局令第 123 号，2026 年 1 月 27 日公布。
- 要求入网餐饮服务提供者严格执行进货查验、索证索票和台账记录制度，建立食品原料采购记录档案。
- 订单信息（食品名称、下单时间、配送人员、送达时间、收货地址等）保存时间自交易完成之日起不少于三年。

**对系统的要求**：网络餐饮企业（本项目目标用户为个体餐饮企业，多涉及外卖）必须将订单信息与追溯信息关联并长期保存，订单→菜品→原料批次的全链路关联是合规刚需。

#### 2.1.3 《商品二维码》国家标准（2025 年 7 月实施）

- 新修订国标支持"一码查全"：消费者扫码即可同时获取价格结算、产品溯源、数字标签等信息。
- 国家二维码综合服务平台已开放企业注册，国内外通用，符合 GS1 国际标准。

**对系统的要求**：追溯码应采用符合国标的二维码方案，支持消费者扫码查询，且应考虑未来与国家平台对接的能力。

### 2.2 行业最佳实践

#### 2.2.1 批次管理最佳实践

依据《食品追溯与批次管理程序》（2026 年行业实践）及金蝶云·星空等成熟 ERP 方案：

1. **最小追溯单元设定**：原料、添加剂、包材、半成品、成品和销售均应设定批次识别方式，相邻节点可映射。
2. **批次号跟随制**：生产前为成品分配唯一"生产批次号"，并在生产记录中明确"该批次使用的所有原料批次号"，实现"成品批次→原料批次"的逆向追溯。
3. **双向追溯能力**：
   - **正向追溯**：已知上游批次异常时，按"来源→入库→领料→投料→半成品→成品→库存→客户"路径追查，输出影响批次、库存数量和客户范围。
   - **反向追溯**：已知成品批次异常时，按"成品→生产记录→投料→原辅料→来源→放行→客户"路径倒查。
4. **追溯时限**：常规批次查询在 2 小时内形成初步结论，重大风险事件在 1 小时内完成问题对象锁定和临时控制。
5. **信息化要求**：鼓励通过 ERP/WMS/MES 建立批次映射；电子记录应能追溯到原始单据，并保留导出留痕。

#### 2.2.2 数据流转模式（餐饮场景四环节闭环）

依据 2026 年智慧食堂/餐饮追溯实践，完整链条包含四个核心环节：

| 环节 | 关键动作 | 数据产出 |
|------|---------|---------|
| ① 供应商管理与智能采购 | 供应商资质电子化归档、采购订单线上生成、检疫检验报告随货上传 | 供应商档案、采购单、检验报告（追溯起点） |
| ② 入库赋码与库存管理 | 整批次食材生成唯一追溯二维码/RFID、扫码记录生产日期/保质期/批次号/供应商、先进先出、临期预警 | 原料追溯码、库存批次、效期数据 |
| ③ 生产加工与耗用关联 | 后厨领用扫码出库、标准菜品配方（BOM）、按实际产量反推扣减原料批次库存 | 原料批次↔菜品关联（追溯链核心） |
| ④ 销售记录与溯源查询 | 消费者扫码查询菜品主要原料溯源信息、问题批次一键定位影响范围 | 食品追溯码、消费者扫码记录、召回范围 |

**核心结论**：追溯不是独立功能，而是业务流转的自然结果。数据应在业务发生时自动采集与关联，而非事后补录。

#### 2.2.3 消费者扫码查询体验

依据北京海淀餐饮肉类一码溯源试点（2026 年 2 月）、重庆"渝溯源"、北京朝阳农贸市场溯源等实践：

1. **查询入口**：餐桌二维码、菜单二维码、付款小票二维码、包装二维码。
2. **查询内容**：菜品所用原料的品牌、产地、检疫报告、进货时间、生产日期、保质期、供应商信息、检测合格证明。
3. **查询时长**：整个查询过程应在 30 秒内完成（北京通州试点实测"不到半分钟"）。
4. **查询体验**：页面清晰、信息分层、关键信息（检疫证明、产地）优先展示。
5. **监管协同**：监管部门可通过同一系统核验信息真伪，实现"非现场监管"。

### 2.3 系统对接需求

#### 2.3.1 与采购模块的对接（原料采购→追溯起点）

- 采购入库时自动触发原料追溯码生成。
- 采购订单号、供应商、批次号、检验报告作为追溯起点数据。
- **后端现状**：`MaterialTraceCodeController` 已提供 `/v1/material-trace-code/confirm-stockin`（扫码确认入库）和 `/v1/material-trace-code/stockin/{stockinId}`（按采购入库单查询）接口，`PurchaseStockinController`、`QuickStockInController`、`PurchaseStockinScanController` 已存在。

#### 2.3.2 与仓储模块的对接（入库/出库→批次流转）

- 入库绑定库位、批次、效期；出库按先进先出推荐批次。
- 库存调整、库存盘点、库存预警需与追溯码状态联动。
- **后端现状**：`MaterialTraceCode` 实体已含 `warehouseId`、`warehouseName`、`storageLocation`、`inboundTime`、`shelfLifeDays`、`expiryDate` 字段；`InventoryController`、`StoreInventoryController`、`InventoryWarningController` 等已存在。

#### 2.3.3 与商品模块的对接（菜品→追溯终点）

- 标准菜品配方（BOM）决定原料构成，是"菜品→原料"追溯的基准。
- 菜品销售（订单）关联食品追溯码，形成"订单→菜品→原料批次"闭环。
- **后端现状**：`FoodTraceCode` 实体已含 `dishId`、`dishName`、`orderId`、`orderNumber`、`orderType`、`kitchenOrderId`、`chefId`、`chefName` 字段；`RecipeController`（配方）、`FoodController`（菜品）、`KitchenOrderController`（厨单）、`OrderNewController`（订单）已存在。

#### 2.3.4 与供应商的对接（供应商→追溯源头）

- 供应商资质（营业执照、食品经营许可证、检验报告）电子化管理，与原料批次关联。
- 供应商资质临期自动提醒。
- **后端现状**：`SupplierController`、`SupplierEvaluationController` 已存在；`MaterialTraceCode` 实体已含 `supplierId`、`supplierName` 字段；`TraceCode` 实体已含 `supplierId`。

| 类型定义未复用 | 页面定义了本地简化 interface（如 `FoodTrace`、`TraceRecord`），未使用 `types/` 下的完整类型 |
| 状态映射不规范 | 页面在模板中硬编码状态映射（如 `row.status === 'active' ? '有效' : '已过期'`），未使用类型文件中的 `StatusMap` |
| 数据转换缺失 | 无 DataConverter，未遵循项目规范（金额元分转换、状态字段映射） |

## 四、需求分析

### 4.1 核心功能需求

基于法规要求与行业实践，食品追溯模块应实现以下核心功能：

1. **原料追溯码管理**（追溯起点）
   - 采购入库时自动/手动生成原料追溯码
   - 批次号、供应商、生产日期、保质期、库位、检验报告关联
   - 扫码确认入库、领用、退回、过期标记
   - 临期预警、过期自动标记

2. **食品追溯码管理**（追溯终点）
   - 菜品制作时生成食品追溯码，关联原料追溯码
   - 制作状态流转（待制→制作→完成→已出）
   - 关联订单、厨单、厨师、门店
   - 扫码出餐、打印标签

3. **追溯链展示**
   - 正向追溯：原料批次→入库→领料→投料→成品→销售
   - 反向追溯：成品→生产记录→投料→原料→供应商
   - 可视化流程图/时间轴展示

4. **追溯查询**
   - 按追溯码查询完整链路
   - 按批次号/供应商/物料名反向查询影响范围
   - 消费者扫码查询（H5/小程序入口）

5. **召回管理**
   - 问题批次一键定位影响范围
   - 召回操作执行与记录
   - 风险等级评估

6. **质量与检验管理**
   - 原料验收检测、成品检验记录
   - 检测结果与批次关联
   - 不合格品处理流程

7. **标签模板管理**
   - 标签设计（文本/条码/二维码/线条/矩形框）
   - 数据绑定、打印配置
   - 批量打印

### 4.2 数据流转需求

**核心数据流转链路**（必须实现"活数据"）：

```
采购模块                    仓储模块                    商品/订单模块
   │                          │                          │
   ▼                          ▼                          ▼
采购入库单 ──触发──→ 原料追溯码生成 ──关联──→ 库位/批次/效期
   │                          │                          │
   │                          ▼                          │
   │                    领料出库(扫码)                    │
   │                          │                          │
   │                          ▼                          │
   │                    原料批次 ──关联──→ 菜品配方(BOM)
   │                          │                          │
   │                          ▼                          │
   │                    食品追溯码生成 ←──关联── 厨单/订单/厨师
   │                          │                          │
   │                          ▼                          │
   │                    扫码出餐/打印 ←──关联── 消费者订单
   │                          │                          │
   │                          ▼                          │
   └──供应商────────────→ 消费者扫码查询                  │
                              │                          │
                              ▼                          │
                         召回/反向追溯 ←──触发── 质量问题
```

**数据"活性"要求**：
1. 采购入库 → 自动触发原料追溯码生成（事件驱动，非人工录入）
2. 库存出库 → 自动更新原料追溯码状态（领用/使用）
3. 厨单制作 → 自动生成食品追溯码并关联原料批次
4. 订单完成 → 自动关联食品追溯码与销售记录
5. 统计卡片 → 实时从后端聚合，非硬编码
6. 临期/过期 → 后端定时任务自动标记，前端实时展示预警

### 4.3 用户交互需求

1. **个体餐饮企业操作员**：
   - 扫码枪扫描入库（无需手动录入批次号）
   - 后厨显示屏临期食材看板
   - 一键生成追溯报告应对监管检查
   - 移动端/PDA 领料、报损、盘点

2. **消费者**：
   - 扫描餐桌/菜单/小票二维码查询溯源
   - 30 秒内获取关键信息（产地、检疫证明、保质期）
   - 页面简洁、信息分层

3. **监管人员**：
   - 扫码核验信息真伪
   - 一键导出追溯报表
   - 非现场监管（线上抽查）

import request from '@/api/request'

export const materialTraceCodeApi = {

    return request.get('/v1/material-trace-code/statistics')

## 七、风险与注意事项

### 7.1 技术风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 后端接口与前端类型定义不一致 | 数据对接失败 | 改造前先核对后端 DTO 与前端 types，必要时更新类型定义 |
| 检验记录/质量追溯后端缺失 | 2 个页面无法对接 | 先确认是否复用采购检验模块，若否需新增后端 Controller |
| RabbitMQ 消息消费幂等性 | 数据重复或丢失 | 检查 `TraceMessageConsumer` 的幂等处理逻辑 |
| 追溯链路数据量大 | 查询性能问题 | 采用二级缓存 + 分页查询，避免全量加载 |
| 扫码并发冲突 | 同一批次被多次领用 | 后端需加锁或乐观锁控制 |

### 7.2 业务风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 数据流转断链 | 追溯不完整，合规风险 | 确保采购→入库→领料→制作→出餐全链路事件驱动 |
| 临期/过期未及时预警 | 食材过期误用 | 后端定时任务 + 前端预警看板双重保障 |
| 消费者扫码信息不完整 | 信任度下降 | 扫码页展示关键信息（产地、检疫、保质期） |
| 召回影响范围不准 | 召回不彻底或过度召回 | 反向追溯查询需覆盖所有关联批次和销售记录 |

### 7.3 合规注意事项

1. **订单信息保存 3 年**：依据《网络餐饮服务经营者落实食品安全主体责任监督管理规定》（2026.6.1 施行），订单信息保存时间自交易完成之日起不少于三年。需确认数据库订单表的归档策略。
2. **进货查验记录**：依据《食品安全法》第四十二条，必须记录名称、规格、数量、生产日期/批号、保质期、进货日期、供货者信息。`MaterialTraceCode` 实体已覆盖这些字段，需确保前端录入完整。
3. **追溯码符合国标**：依据《商品二维码》国家标准（2025.7 实施），追溯码应采用符合 GS1 标准的二维码，考虑未来与国家二维码综合服务平台对接。
4. **数据不可篡改**：行业最佳实践建议关键追溯数据上链（区块链）或审计日志严格管控。后端已有 `TraceCodeLog` 实体，需确保所有状态变更有日志记录。

### 7.4 实施注意事项

1. **渐进式改造**：建议按 P0→P1→P2→P3 优先级逐步改造，每个页面改造后立即联调测试，避免一次性大改引入风险。
2. **保留 Mock 降级**：API 调用失败时应有降级处理（如显示空状态），避免页面白屏。
3. **类型定义同步**：改造前端时若发现后端 DTO 字段变化，需同步更新 `types/` 定义。
4. **遵循项目规范**：API 调用必须使用 `request` 实例；状态映射必须使用 DataConverter；统计卡片必须使用后端实时数据；禁止硬编码 Mock 数据提交到代码仓库。

---

## 八、调研结论

### 8.1 核心结论

1. **后端能力充足，前端严重滞后**：后端 traceability 模块已实现完整的 Controller/Service/Entity/Mapper/DTO/消息队列/事件机制，但前端 6 个页面全部硬编码 Mock 数据，`api/traceability/` 目录完全缺失，形成"后端有接口无人调、前端有页面无数据"的断层。

2. **数据流转后端已打通，前端未体现**：后端已通过 `confirm-stockin`（采购入库）、`pick`（领用）、`start-make`/`complete-make`（制作）、`serve`（出餐）等接口实现业务流转，并通过 RabbitMQ 消息驱动，但前端页面未调用这些接口，数据"活性"为零。

3. **类型定义已就绪但未使用**：`types/foodTraceCode.ts`、`types/materialTraceCode.ts`、`types/trace-code.ts`、`types/label-template.ts` 均已完整定义（含数据流转关联字段），但 Vue 页面使用了简化的本地 interface，导致类型安全性和数据完整性受损。

4. **菜单与页面不匹配**：菜单 8 项中 2 项（追溯查询、供应商追溯）复用了产品模块页面，无专属实现。

### 8.2 改造优先级建议

**第一优先级（P0）**：创建 `api/traceability/` 目录，改造 MaterialTraceCode/FoodTraceCode/TraceChainView 三个核心页面对接后端，实现基础数据流转。

**第二优先级（P1）**：改造 LabelTemplate/Inspection/Quality 页面，新增 TraceQuery 专属页面。

**第三优先级（P2）**：新增 SupplierTrace/RecallManagement/ExpiryWarning 页面，追溯链可视化改造。

**第四优先级（P3）**：消费者扫码 H5 页面，数据流转事件驱动联调。

### 8.3 关键成功因素

1. **API 层必须先行**：无 `api/traceability/` 目录则一切改造无从谈起。
2. **事件驱动是数据活性的关键**：充分利用后端已有的 RabbitMQ 消息机制，实现业务流转自动触发追溯数据更新。
3. **类型定义复用**：改造时必须使用 `types/` 下已有定义，避免重复定义和数据流转字段丢失。
4. **合规优先**：确保满足《食品安全法》第四十二条和《网络餐饮服务规定》（2026.6.1）的追溯记录要求。
