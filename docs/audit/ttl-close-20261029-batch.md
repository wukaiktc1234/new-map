## 教训（第 11 次「假设存在」）

写完 `UPDATE orders SET … cancel_time = now()` 直接跑了作业，**没先 `\d orders` 确认列存在** ——
结果 92 笔整批失败。真实 `orders` 只有 `cancel_reason`（text），**没有 `cancel_time`**。
→ 写任何 UPDATE 前先看列清单（见 `Key-Tables-Cheat-Sheet.md`）。

## 夹具清理规范（2026-10-29 踩坑，必须遵守）

```text
❌ 直接 DELETE FROM orders WHERE remark LIKE '%<tag>%'
   → 报外键约束：在 "orders" 上的更新或删除操作违反了在 "order_items" 上的外键约束 "fk_order_items_order_id"
   → 整条语句失败，0 行删除（我第一次就是这样，数据还在）

✅ 正确顺序（先子后父）：
  1) DELETE FROM order_items WHERE order_id IN (SELECT order_id FROM orders WHERE remark LIKE '%<tag>%');
  2) DELETE FROM orders WHERE remark LIKE '%<tag>%';
  3) DELETE FROM pos_shifts WHERE terminal_id LIKE 'T-XXX-%';
  4) SELECT count(*) 复核 left=0（三个表都要查）
```

**禁止**：为了「删得动」而去 `ALTER TABLE ... DROP CONSTRAINT` / `SET session_replication_role` ——
那会绕过外键保护，是真事故的开始。**按依赖顺序删，别动约束。**
