# POS 收银端 · 前端体验评估与优化报告

> 评估对象：`frontend-pos/`（Vue 3 + TypeScript + Element Plus，收银主页 `/views/Home.vue`）
> 评估视角：门店收银员（快餐厅，午晚高峰，单手触屏 + 扫码枪 + 偶尔键盘）
> 方法：全量通读源码并逐条取证 → 静态量化（热区 px / 字号 / 对比度 / 点击次数）→ 与后厨端同仓对照 → 关键链路 Playwright 实测
> 结论口径：每条判断都带 `文件:行号`，未取证不写；「已修」指本次任务一已落地并有测试证据。
> 报告日期：2026-10-28 ｜ 基线：当前工作区快照

## 0. 总评

**4.5 / 10（修复前） → 5.0 / 10（第一轮） → 6.0 / 10（第二轮） → 7.0 / 10（第四轮，2026-10-28）**

> 第二轮闭环 P0：R-1 删除无防呆、R-2 取单静默覆盖、R-4 实收现金/付款码不上送。
> 第四轮：交班财务口径校正（应上交 ≠ 备用金+现金）、非现金独立成块、Emoji 全量换 SVG、
> 深色模式重做（#1E1E20 系）、品牌色与数字字体统一。详见 `docs/POS改造说明-第四轮.md`。

一句话：**这是一套「看起来很像样、用起来不敢快」的收银台。** 视觉有设计感——骨架屏、空态、金额 26/32/48 三级递进都在；但收银员赖以提效的四项硬能力（扫码枪商品码入口、全局快捷键、删除/取单防呆、断网可见性）几乎全缺，并且存在 5 个会直接造成**错金额 / 丢行 / 重复扣款**的 P0 缺陷。

| 维度 | 修复前 | 一轮后 | 二轮后 | 四轮后 | 一句话 |
|---|---|---|---|---|---|
| 1. 快捷键与硬件联动 | **2 / 10** | 3 | 3 | 3 | Enter 双触发已修；扫码枪商品码入口、全局快捷键仍为 0 |
| 2. 容错与防呆 | **3 / 10** | 3.5 | 6 | 6 | 撤销条 / 取单挂起 / 现金字段落库；仅剩折扣重算（R-3） |
| 3. 视觉与热区 | **5 / 10** | 5.5 | 6.5 | **8 / 10** | Emoji 全换 SVG、深色改深灰去白框、品牌色统一、DIN 数字、阴影分层；菜名 11px 与数量热区 24px 仍未动 |

**评分口径**：10 分=行业标杆（如成熟 SaaS 收银台）；7 分=可用且高效；5 分=能用但需要培训；3 分=会出错；1 分=不可用。单项由「能力有无（60%）+ 一致性与兜底（40%）」构成。

## 2. 维度一：快捷键与硬件联动（2 → 3 分）

### 2.1 现状

**① 全局键盘绑定只有 1 条，且只服务支付弹窗**

`views/Home.vue:574-581`（修复前）注册了一个**捕获阶段**的 `keydown` 监听，唯一逻辑是「Enter + 支付弹窗打开 → 确认支付」。全量检索 `keydown|keyup|KeyboardEvent` 的 31 处命中里，收银主页之外再无全局快捷键，其余全是弹窗内局部 `@keyup.enter`。

**② 后厨端有完整快捷键体系，收银端是 0——同仓对照**

`composables/kitchen/useKeyboardShortcuts.ts:56-127` 定义了 13 条快捷键（1~5 选单、Enter 开做、空格完成、Esc 取消、Tab 切栏、F1 刷新、`?` 帮助、Ctrl+A 全选），`:132-177` 统一分发、`:183-209` 随组件生命周期注册注销，还配了 `ShortcutHelp.vue` 帮助面板。**同一批用户，后厨有、收银没有。**

**③ 扫码枪（HID 键盘模拟）商品码录入入口：不存在**

- 菜品区模板 `MenuSection.vue:1-96` 只有分类栏 + 错误态 + 网格 + 骨架屏，**没有一个输入框**。
- 唯一的筛选方式是点分类（`MenuSection.vue:6-14` → `Home.vue:45` 直接赋值 `activeCategory`）。
- 收银员扫一瓶可乐：字符落进 body，被 `Home.vue:574` 的监听器读到，但它只判断 `Enter && showPaymentConfirm`，数字串全部丢弃，**不搜索、不加购、无提示**。

**④ 扫码后焦点归位：无处可归**

没有搜索框，自然没有「扫完回到搜索框」。加购（`useCart.ts:43-71`）、删行、结账成功（`usePayment.ts:131` `clearCart()`）之后**都没有 `focus()` 归位**；全仓唯一的自动聚焦只发生在「弹窗打开时聚焦输入框」。

**⑤ F1 挂单 / F2 结账 / F3 取单 / ESC / Delete：全部缺失**，只能鼠标点顶栏（`PosTopBar.vue:25-35,46-49`）与购物车（`CartSection.vue:132-142`）。

### 3.4 结算数据不上送（对账缺口，P0）

- 组单：`usePayment.ts:88-99` —— items 用**原价**、totalAmount 用**折后价**、`tableNumber: 1` **硬编码**；
- 支付：`:112-116` 只传 orderId / paymentMethod / amount；
- `PaymentConfirmDialog.vue:162` 收集了**实收现金**`cashReceived` 与**付款码**`paymentCode`，`usePayment.ts:158-164` 存进 ref 后**全程没再使用**，`PayRequest`（`posApi.ts:223-230`）也**没有这两个字段**。
- 后果：现金实收/找零不落库、第三方付款码不落库、明细与总额不等、所有订单都是 1 号桌。

## 5. 维度四：高频流转效率（4 → 4.5 分）

### 5.1 点击次数实测

**加菜**：1 次点击（`MenuSection.vue:30-40`）——次数优秀，**但零成功反馈**（无 toast / 无角标 / 无数量浮标；`:374-396` 的 `:active` 只有 `translateY(0)`）。收银员必须再扫一眼购物车确认 → 实际成本 ≈ 2 次交互 + 1 次视觉扫视。

**改数量（3→5）**：点数字（热区 24px）→ 键入 → Enter，或连点「+」两次。

**删一行**：PC 垃圾桶 1 次（须先 hover 才出现）／触摸左滑 2 次／「−」到底 1 次（静默）。

**结账（现金）——最关键的路径**

| 步骤 | 层级 | 点击 |
|---|---|---|
| 购物车底部「现金」 | 1 | 1 |
| 弹窗「确认支付」 | 2 | 1 |
| **ElMessageBox「确认支付 ¥X 元？」（重复确认）** | 3 | 1 |
| 支付成功弹窗「完成」（禁遮罩、禁 ESC，**必须点**） | 4 | 1 |
| **合计** | **3 层弹层 / 2 次「确认支付」** | **4** |

证据：`CartSection.vue:132` → `usePayment.ts:35-56` → `PaymentConfirmDialog.vue:82-90` → `usePayment.ts:58-84`（第 3 步双确认在 `:69-79`）→ `PaymentSuccessDialog.vue:2-11,39-41`。

**阻塞点**：成功弹窗模态、禁点遮罩关闭、禁 ESC，**在点「完成」之前下一单开不了**——每单强制 1 次点击，高峰排队时这是最刺眼的卡点。

## 7. 投入产出比最高的 5 条改进建议

> 工作量口径：一人熟悉本仓库前提下的净编码 + 自测；收益按第 1 节门店参数估算。

### 建议 1｜收银端全局快捷键基座（F1 挂单 / F2 结账 / F3 取单 / Delete 删行 / ESC 关层）

- **改动点**：新增 `composables/pos/usePosShortcuts.ts`，照搬 `kitchen/useKeyboardShortcuts.ts:132-209` 的分发/注册骨架，保留 `:134-142` 的「输入框内不触发」排除；在 `Home.vue` 注册 5 条快捷键；顶栏按钮加 `kbd` 角标做可发现性教学。
- **工作量**：**8 人时**
- **收益**：挂单/取单从「移到顶栏点击」变单键（40 次/天 → 省 80 次点击）；结账路径省 2 次鼠标动作；保守 **省 600 次点击/天**，午高峰 120 单累计省约 2.4 分钟纯操作。
- **验收**：`F2` 在购物车非空时直达现金结账；焦点在输入框时任何快捷键不触发；`?` 弹出快捷键帮助。
- **依赖**：无（纯前端）。

### 建议 2｜结账链路「三层并一层」+ 幂等令牌

- **改动点**：`usePayment.ts:58-84` 去掉 `ElMessageBox.confirm`（`PaymentConfirmDialog` 已是确认层）；`PaymentSuccessDialog.vue` 增加 3s 自动关闭并保留手动「完成」；`createOrder` 带上 `requestId`（时间戳+随机）做**服务端幂等**（需后端支持，前端先传）。
- **工作量**：**5 人时**（+ 后端幂等键 2 人时）
- **收益**：每单 4 次点击 → 2 次，**省 600 次点击/天**；结账 6s → 3.5s，高峰单笔吞吐 +40%；**彻底消除重复扣款风险**（已被本次守卫挡住前端路径，服务端幂等是第二道保险）。
- **验收**：单次回车只产生 1 笔订单（本次已有自动化用例，可直接复用为回归）；成功框 3s 自动关闭后可直接下一单。
- **依赖**：后端 `requestId` 幂等（可选但推荐）。

### 建议 3｜删除类操作改「5 秒撤销条」，取单接上既有护栏

- **改动点**：
  - `useCart.ts:81-87`（减到 0）、`:194-196`（垃圾桶/滑删）改为「先移入 `pendingDelete` + 底部 5s 撤销条」，新增 `components/pos/CartUndoBar.vue`；
  - `useHangingOrder.ts:50-68` 的 `selectHeldOrder` **改为调用同文件已写好的 `quickRestoreHeldOrder`（`:84-95`，会提示「恢复挂单将清空当前购物车」）**——1 行接线，直接消灭 P0-2；
  - 清空购物车保留模态确认（`CartSection.vue:206-217`）。
- **工作量**：**6 人时**（撤销条 5h + 取单护栏 1h）
- **收益**：按 2% 误删率（1500 行/天 → 30 行误删）每次重录 4 次点击 + 8 秒 → **省 120 次点击 + 4 分钟/天**，更重要的是消除「客人面前重新点单」的事故；取单零成本消除丢单。
- **验收**：删除后 5s 内可撤销；取单时若购物车非空必弹覆盖确认。
- **注意**：**不要**用 `ElMessageBox` 做删除确认——高峰期会变成「每删一个菜弹一次窗」的新瓶颈。

### 建议 4｜折扣状态机化 + 抹零/整单折扣入口

- **改动点**：`Home.vue:175-176` 把 `discountAmount` 从 `ref` 改为 `computed`（依据 appliedCoupon + originalTotalAmount，低于 minAmount 自动归零并 toast）；`:437-441` 的门槛校验抽成 `validateCoupon()` 供重算复用；新增 `DiscountDialog.vue`（整单减免 / 抹零 / 折扣率 + 数字键盘 + 二次确认）；`CartSection.vue` 增加「手动折扣」行并标注来源。
- **工作量**：**10 人时**（含 discountAmount 是否落库的后端确认）
- **收益**：直接消灭 R-3 的**错金额 P0**；把「抹零」从「做不到」变成 1 次点击（按 15% 订单需抹零 ≈ 45 单/天）。
- **验收**：应用券后改单，折扣自动失效并提示；抹零后总额变为整数且明细可追溯来源。
- **依赖**：后端是否支持 `discountAmount`/`discountType` 落库需产品+后端确认（**本次未动，符合「不改后端业务逻辑」约束**）。

### 建议 5｜常驻扫码枪商品码输入框 + 全局焦点归位

- **改动点**：`MenuSection.vue` 分类栏右侧插入常驻 `<input class="scan-input">`（autofocus，回车/失焦自动重新聚焦）；新增 `composables/pos/useScanGun.ts`：50ms 内连续字符 + Enter 判定为扫码枪 → 按 `dishCode` 精确匹配（`useMenu.ts:33` 已把 id 设为 dishCode，可直接命中）→ 命中则 `addToCart` + 角标反馈，未命中提示「未找到该商品码」；`Home.vue` 的商品 watch 内加 `nextTick` 焦点归位。
- **工作量**：**12 人时**（含键盘/扫码枪误判调参）
- **收益**：条码商品（约 100 单/天）从「切分类 + 目视找图 + 点击」（≈4 次交互、8 秒）→ **1 次扫码 1.5 秒**：**省约 300 次点击 + 11 分钟/天**，彻底消除「扫了没反应」。
- **验收**：扫 `F001` 直接加购并高亮；人工快速输入不误判；扫完焦点自动回到输入框。

### 建议 6（附加，P1 里最便宜的一项）｜全局离线横幅

- **改动点**：`Home.vue:546-559` 消费 `webSocketService.isConnectedStatus()`（现已实现但无人调用）+ `onConnectionChange`，在顶栏下方显示「网络已断开，正在重连…（数据可能不是最新）」，并禁用「结账」按钮直到恢复。
- **工作量**：**3 人时**
- **收益**：把「界面上什么都没发生」变成明确状态，直接降低「按了结账没反应 → 连按 5 次」造成的重复单风险（与建议 2 互补）。
