## 三、修复的问题清单

本轮冒烟测试期间共修复 4 个阻断性问题，其中前 2 项为数据库 schema 与 Mapper 查询不匹配，第 3 项为 PowerShell 测试工具编码问题，第 4 项为脚本注释编码问题。

### 问题 1：ROLES 表 STATUS 字段类型不匹配

| 项 | 内容 |
|----|------|
| 现象 | `Data conversion error converting "active"; SQL statement: SELECT r.ROLE_CODE FROM ROLES r ... AND r.STATUS IN ('1', 'active') [22018-224]` |
| 根因 | [schema.sql](file:///p:/my-new-project/backend/src/main/resources/db/schema.sql) 中 ROLES 表 `STATUS SMALLINT DEFAULT 1`，但 [UserMapper.java](file:///p:/my-new-project/backend/src/main/java/com/foodtraceability/mapper/UserMapper.java) 行 28 使用 `r.STATUS IN ('1', 'active')` 字符串比较 |
| 修复 | 将 ROLES 表 STATUS 改为 `VARCHAR(20) DEFAULT '1'`，与生产 PostgreSQL schema (V1.0.0.100 行 217) 保持一致 |
| 文件 | [schema.sql](file:///p:/my-new-project/backend/src/main/resources/db/schema.sql) |
| 状态 | ✅ 已修复并验证 |

### 问题 2：PERMISSIONS 表 STATUS 字段类型不匹配

| 项 | 内容 |
|----|------|
| 现象 | `Data conversion error converting "active"; SQL statement: SELECT DISTINCT p.PERMISSION_CODE ... AND p.STATUS IN ('1', 'active') [22018-224]` |
| 根因 | 同问题 1，PERMISSIONS 表 STATUS 为 SMALLINT，但 [UserMapper.xml](file:///p:/my-new-project/backend/src/main/resources/mapper/UserMapper.xml) 行 14、27 使用字符串比较 |
| 修复 | 将 PERMISSIONS 表 STATUS 改为 `VARCHAR(20) DEFAULT '1'` |
| 文件 | [schema.sql](file:///p:/my-new-project/backend/src/main/resources/db/schema.sql) |
| 状态 | ✅ 已修复并验证 |

### 问题 3：PowerShell 5.1 响应体编码问题（关键修复）

| 项 | 内容 |
|----|------|
| 现象 | refresh token 测试报 `code:405, message:"请求方法不允许"`，但手动调用同样 API 返回 `code:0, message:"操作成功"`；响应体中中文显示为乱码 `鎿嶄綔鎴愬姛` |
| 根因 | PowerShell 5.1 在通过 `powershell -File` 启动时，系统默认编码为 gb2312，`Invoke-WebRequest.Content` 以 gb2312 而非响应头中的 charset=UTF-8 解码响应体，导致 `ConvertFrom-Json` 解析失败，`newToken` 返回空 |
| 修复 | 在 [smoke-test-runner.ps1](file:///p:/my-new-project/docs/验收清单/smoke-test-runner.ps1) 的 `Invoke-Api` 函数中，从 `response.RawContentStream` 获取原始字节，用 `[System.Text.Encoding]::UTF8.GetString()` 重新解码 |
| 文件 | [smoke-test-runner.ps1](file:///p:/my-new-project/docs/验收清单/smoke-test-runner.ps1) 行 38-46 |
| 状态 | ✅ 已修复并验证 |

## 四、已知限制与未覆盖项

### 4.1 stockinId 返回值为空

- **现象**：2.6 创建入库单返回 HTTP 200，但响应体中 `stockinId` 为空字符串
- **影响**：导致 2.7 质检、2.8 确认入库两步被测试脚本跳过
- **可能原因**：入库 Service 返回的 Result.data 中未携带 stockinId 字段，或字段名与脚本期望不一致
- **建议**：后续排查 `PurchaseStockinServiceImpl.createStockin` 的返回值构造，与前端 API 约定对齐

### 4.2 traceCode 返回值为空

- **现象**：6.1 查询溯源码返回 HTTP 200，但响应体中 `traceCode` 为空
- **影响**：仅校验了接口可用性，未真正验证溯源码生成链路
- **可能原因**：测试链路未触发完整的溯源码生成流程（需先完成生产→加工→物流→门店全链路）
- **建议**：补充端到端溯源码生成用例，覆盖从原料到成品的完整溯源

### 4.3 schema.sql 中其他表的 STATUS SMALLINT

- **现象**：schema.sql 中共有 11 处使用 `STATUS SMALLINT DEFAULT 1`
- **影响**：目前只有 ROLES 和 PERMISSIONS 触发了类型不匹配；其他表暂未触发问题
- **建议**：后续统一排查，将这些表 STATUS 改为 VARCHAR(20)，与生产 PostgreSQL schema 保持一致

### 4.4 未覆盖模块

本次冒烟测试聚焦 V1 核心链路，以下模块未覆盖：
- 生产加工模块（加工工单、BOM）
- 物流配送模块
