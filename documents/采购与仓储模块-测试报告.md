## 三、问题分类与根因分析

### 3.1 严重问题：权限配置缺失（19个端点）

**现象**：admin 超级管理员访问以下端点返回 403 权限不足。

**影响范围**：
- 采购模块：采购申请统计/待审批、采购计划、供应商分页/统计、物资需求分页/统计（7个）
- 仓储模块：仓库、库存、盘点、调拨、预警、报损、日志、统计预警趋势（12个）

**根因分析**：
- admin 用户的 JWT token 中 permissions 列表未包含 `purchase:request:query`、`warehouse:inventory:query` 等权限码
- 后端 Controller 的权限注解（如 `@PreAuthorize`）校验失败
- 属于 RBAC 权限配置问题，需在角色权限映射表中补充对应权限

**修复建议**：
1. 检查 `role_permissions` 表，确认 admin 角色是否包含所有模块的 `:query`/`:view` 权限
2. 检查后端 Controller 的 `@PreAuthorize` 注解，确认权限码命名是否与数据库一致
3. 临时方案：为 admin 角色添加通配权限 `*:*` 或移除测试环境的权限校验

### 3.2 严重问题：数据库表未初始化（5张表）

**现象**：H2 数据库中缺失以下业务表，导致 6 个端点返回 500。

| 缺失表 | 影响端点 | Mapper 文件 |
|--------|---------|------------|
| material_archives | 商品档案查询 | MaterialArchiveMapper |
| material_categories | 商品分类（3个端点） | MaterialCategoryMapper |
| inventory_warning_rules | 预警规则查询 | InventoryWarningRuleMapper |
| inventory_outbound | 出库查询 | InventoryOutboundMapper |
| inventory_adjust | 调整查询 | InventoryAdjustMapper |

**根因分析**：
- 后端 `DatabaseInitConfig` 初始化器未创建上述 5 张表
- H2 内存数据库每次启动重新建表，缺失的建表 SQL 未被执行
- 实体类 `@TableName` 注解指定的表名与初始化脚本中的建表语句不匹配

**修复建议**：
1. 在 `BaseDatabaseInitializer` 或 `PurchaseDatabaseInitializer` 中补充 `material_archives`、`material_categories` 建表 SQL
2. 在 `InventoryDatabaseInitializer` 中补充 `inventory_warning_rules`、`inventory_outbound`、`inventory_adjust` 建表 SQL
3. 建表语句需包含必备字段：`deleted`、`create_time`、`update_time`

### 3.3 严重问题：数据库列不匹配（1个端点）

**现象**：`GET /v1/inventory/stats/overview` 返回 500，错误 `Column "INVENTORY_ID" not found`。

**根因分析**：
- `Inventory` 实体类字段 `inventoryId` 映射到数据库列 `inventory_id`
- 但 H2 中 `inventory` 表的主键列名实际为 `id` 而非 `inventory_id`
- 实体类 `@TableId` 注解与数据库建表语句不一致

**修复建议**：
1. 统一 `Inventory` 实体主键列名：将建表 SQL 中的 `id` 改为 `inventory_id`，或在实体类 `@TableId(value="id")`
2. 检查所有仓储模块实体类的主键命名一致性

### 3.4 中等问题：API 参数契约不一致（2个端点）

**现象**：`turnover-analysis` 和 `waste-analysis` 接口返回 400 "缺少必填参数：startDate"。

**根因分析**：
- 前端 `inventory-analysis.ts` 中 `getTurnoverAnalysis()` 和 `getWasteAnalysis()` 未传 `startDate` 参数
- 后端 Controller 强制要求 `startDate` 必填
- 前后端 API 契约不一致

**修复建议**：
1. 前端 API 调用补充默认日期范围参数（如近30天）
2. 或后端将 `startDate` 改为可选参数，提供默认值

### 3.5 中等问题：其他服务端错误（2个端点）

| 端点 | 错误 | 分析 |
|------|------|------|
| GET /v1/purchase/requests/page | 500 系统繁忙 | 需查看后端日志定位，可能是 SQL 语法或空指针 |
| GET /v1/suppliers/list | 500 获取供应商列表失败 | 需查看后端日志，可能是表结构或查询逻辑问题 |

2. **补充缺失的数据库表**：影响 6 个端点
   - 位置：后端 `DatabaseInitConfig` 或各模块 Initializer
   - 需建表：material_archives、material_categories、inventory_warning_rules、inventory_outbound、inventory_adjust

3. **修复 Inventory 实体主键列名**：影响库存统计概览
   - 位置：`Inventory.java` 或 inventory 建表 SQL
   - 操作：统一主键列名为 `inventory_id`

### P1 - 重要问题（尽快修复）

4. **修复前后端参数契约**：周转率分析、报损分析缺 startDate
   - 位置：前端 `inventory-analysis.ts` 或后端 Controller
   - 操作：前端补充默认日期参数，或后端设为可选

5. **排查采购申请分页 500 错误**
   - 位置：`PurchaseRequestController` / `PurchaseRequestServiceImpl`
   - 操作：查看后端日志定位具体异常

6. **排查供应商列表 500 错误**
   - 位置：`SupplierController.getList()`
   - 操作：查看后端日志，可能是表结构或查询逻辑问题

### P2 - 改进项（计划修复）

7. **清除前端硬编码颜色**：6 个文件，改用 CSS 变量
8. **清除前端硬编码选项数据**：改为从后端 API 获取

## 七、测试结论

### 7.1 可用功能
- 采购订单/合同/电子合同/收货/结算的列表查询功能正常
- 采购报表与数据分析功能完全正常（8/8）

### 7.2 不可用功能

### 7.3 总体评价
当前采购与仓储模块的**前端代码质量较高**（规范合规性好、core 组件使用正确、teleported 配置正确），但**后端存在严重的权限配置和数据库初始化问题**，导致 60% 的 API 端点不可用。建议优先修复 P0 级别的权限配置和数据库建表问题，使功能链路能够闭环，再进行更细致的功能测试。
