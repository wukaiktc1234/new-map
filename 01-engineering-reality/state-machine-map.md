## 1. 订单状态机（三套并存 = CONFLICT）

5: 全额退款 (Full Refund)
6: 待评价 (Pending Review)

### 1.5 订单状态映射冲突分析

| order_status | payment_status | legacy status | sales_order | 冲突说明 |
|--------------|----------------|---------------|-------------|----------|
| 0:待确认 | 0:未支付 | 0:待支付 | pending | 大致对应 |
| 1:已确认 | 1:部分支付 | -1:支付中 | preparing | 部分对应 |
| 2:已完成 | 2:已支付 | 4:已完成 | completed | 大致对应 |
| 3:已取消 | 3:已退款 | 5:已取消 | - | 无对应 |
| 4:部分退款 | 1:部分支付 | 6:退款中 | - | 语义不同 |
| 5:全额退款 | 3:已退款 | 7:已退款 | - | 大致对应 |
| 6:待评价 | 2:已支付 | 1:已支付 | delivered | 语义不同 |

**关键问题：**
1. `sales_order` 状态与 `order_status` 完全无映射
2. 同一业务含义在不同表中使用不同状态值
3. legacy status 包含支付中、配送中等中间状态，其他表缺少对应状态
4. 退款状态在三个表中表示不一致

## 2. 凭证状态机

### 2.1 后端状态定义

```
状态定义：
0: DRAFT (草稿)
1: APPROVED (已审批)
2: POSTED (已过账)
3: VOID (已作废)

状态转换图：
                    ┌─────────────┐
                    │  0:DRAFT    │
                    └─────────────┘
                            │
                            ▼
                    ┌─────────────┐
                    │ 1:APPROVED  │
                    └─────────────┘
                            │
                            ▼
                    ┌─────────────┐
                    │  2:POSTED   │
                    └─────────────┘
                            │
                            ▼
                    ┌─────────────┐
                    │   3:VOID    │
                    └─────────────┘

特殊转换：POSTED → unpost（反过账）→ 回到 POSTED 之前的状态
```

### 2.2 前端映射错位

| 后端状态码 | 后端状态名 | 前端 VoucherStatusMap | 错位说明 |
|------------|------------|----------------------|----------|
| 0 | DRAFT | 1 | 错位 +1 |
| 1 | APPROVED | 2 | 错位 +1 |
| 2 | POSTED | 3 | 错位 +1 |
| 3 | VOID | 4 | 错位 +1 |

**关键问题：**
1. 前端 VoucherStatusMap 从 1 开始，后端从 0 开始
2. 需要维护映射表处理前后端差异
3. 反过账操作无前端状态对应

## 5. CAS 支付状态机

### 5.1 POS 支付状态

```
状态定义：
0: 待支付 (Pending Payment)
-1: 处理中/冲突 (Processing/Conflict)
1: 已支付 (Paid)

状态转换图：
                    ┌─────────────┐
                    │  0:待支付    │
                    └─────────────┘
                            │
                            ▼
                    ┌─────────────┐
                    │ -1:处理中    │
                    └─────────────┘
                            │
              ┌─────────────┼─────────────┐
              ▼                           ▼
     ┌─────────────┐             ┌─────────────┐
     │  1:已支付    │             │  0:待支付    │
     └─────────────┘             └─────────────┘
      (成功)                      (重试/恢复)

冲突处理：
-1 状态 = 幂等容错机制
- 重试：重新发起支付请求
- 恢复：回滚到待支付状态
```

### 5.2 CAS 支付状态与订单状态映射

| CAS 状态 | order_status | payment_status | legacy status | 映射说明 |
|----------|--------------|----------------|---------------|----------|
| 0:待支付 | 0:待确认 | 0:未支付 | 0:待支付 | 大致对应 |
| -1:处理中 | - | -1:支付中 | - | 仅 legacy 有对应 |
| 1:已支付 | 1:已确认 | 2:已支付 | 1:已支付 | 大致对应 |

**关键问题：**
1. CAS 的 -1 状态在其他状态机中无对应
2. 支付成功后，order_status 从 0→1，payment_status 从 0→2，legacy 从 0→1
3. 状态转换时序可能不一致

## 6. 全局状态机冲突总结

### 6.1 冲突清单

| 冲突类型 | 涉及系统 | 严重程度 | 影响范围 |
|----------|----------|----------|----------|
| 订单状态三表并存 | order_status, payment_status, legacy | 🔴 高 | 订单全流程 |
| sales_order 无映射 | sales_order vs order_status | 🔴 高 | 销售订单 |
| 凭证前后端错位 | 后端 0-3 vs 前端 1-4 | 🟡 中 | 凭证管理 |
| 库存单据风格不一 | 数字/英文/中文混用 | 🟡 中 | 库存管理 |
| CAS -1 状态孤立 | CAS vs 其他状态机 | 🟡 中 | 支付流程 |

### 6.2 建议处理方案

1. **订单状态统一**
   - 建立统一的订单状态枚举
   - 明确各表状态的映射关系
   - 考虑废弃 legacy status 或建立同步机制

2. **凭证状态修复**
   - 统一前后端状态码（建议统一为 0-3）
   - 建立状态转换中间层

3. **库存单据规范化**
   - 统一使用数字状态码
   - 为报损单、出库单定义完整状态机

4. **CAS 状态集成**
   - 将 -1 状态纳入支付状态机管理
   - 建立支付状态与订单状态的同步机制
