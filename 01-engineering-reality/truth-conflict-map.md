## 二、冲突点详解

### 冲突 1: 金额单位双轨 — 分 (新表) vs 元 (legacy/tax_record/account_balance)

| 维度 | 详情 |
|------|------|
| **冲突本质** | 新表统一用「分」存储金额；`tax_record`、`account_balance` 等遗留表仍用「元」 |
| **涉及表** | 新表: `orders`、`finance_records`、`payables`、`receivables` 等<br>遗留: `tax_record`、`account_balance` |
| **风险** | 跨表 JOIN/汇总时单位不一致，导致金额差 100 倍 |
| **裁决** | 新表以「分」为准；读 `tax_record`/`account_balance` 时需显式转换 |
| **状态** | ⚠️ 持续关注 — 需在所有跨表查询处添加单位转换注释 |

---

### 冲突 2: product_id vs material_id — 语义 vs 遗留列名

| 维度 | 详情 |
|------|------|
| **冲突本质** | `material_id` 是真相语义（物料）；`product_id` 是遗留列名（实际指向物料） |
| **涉及表** | `orders`、`order_items` 等多表中存在 `product_id` 列 |
| **风险** | 开发者误以为 `product_id` 指向菜品表 `foods`，实际指向物料 |
| **裁决** | `material_id` 为真相语义；`product_id` 列名暂保留兼容，但代码中应使用 `material_id` 语义 |
| **状态** | ⚠️ 遗留技术债 — 新代码一律使用 `material_id` 语义 |

---

### 冲突 3: 科目余额双轨 — accounting_subjects.balance vs account_balance

| 维度 | 详情 |
|------|------|
| **冲突本质** | `accounting_subjects.balance`（分/自动计算）与 `account_balance`（元/人工维护）并存 |
| **涉及表** | `accounting_subjects` vs `account_balance` |
| **风险** | 两个余额源数据不一致，报表口径混乱 |
| **裁决** | **PD-031 已决**: `accounting_subjects.balance` 为唯一真相源<br>`account_balance` 为历史遗留，仅用于只读查询旧数据 |
| **状态** | ✅ 已裁决 — 新业务只写 `accounting_subjects.balance` |

---

### 冲突 4: stores vs stores_new — 新旧门店表

| 维度 | 详情 |
|------|------|
| **冲突本质** | `stores_new`（新真相）与 `stores`（旧）并存，字段结构不同 |
| **涉及表** | `stores_new` vs `stores` |
| **风险** | 读错表导致门店信息不一致（地址、经营范围、状态等） |
| **裁决** | `stores_new` 为唯一真相源；`stores` 仅用于兼容旧查询 |
| **状态** | ⚠️ 迁移中 — 新代码必须查询 `stores_new` |

---

### 冲突 5: 订单状态机 — 三套并存

| 维度 | 详情 |
|------|------|
| **冲突本质** | `order_status`、`payment_status`、legacy 状态 三套并存 |
| **涉及表** | `orders` 表多个状态字段 |
| **风险** | 状态流转逻辑分散，难以保证一致性 |
| **裁决** | 三套状态机**并存**（PADR 裁决）；每个字段有独立生命周期 |
| **状态** | ✅ 已裁决 — 代码中需明确区分使用哪个状态字段 |

---

### 冲突 6: 凭证状态映射 — 后端 0-3 vs 前端 1-4

| 维度 | 详情 |
|------|------|
| **冲突本质** | 后端存储 0-3（枚举），前端展示 1-4（序号），映射关系固定但不直观 |
| **涉及层** | 后端 `finance_vouchers.status` vs 前端展示 |
| **风险** | 新开发者混淆映射，导致状态显示/操作错误 |
| **裁决** | 后端以 0-3 为准；前端映射层单独处理（已实现） |
| **状态** | ✅ 已解决 — 映射逻辑封装在前端 adapter 层 |

---

### 冲突 7: food + foods 双写 — 下单/退款/超时同时写两表

| 维度 | 详情 |
|------|------|
| **冲突本质** | 下单、退款、超时等操作同时写 `food` 和 `foods` 两表 |
| **涉及表** | `food` vs `foods` |
| **风险** | 双写不一致导致库存/状态错乱；写入顺序依赖 |
| **裁决** | `foods` 为真相源；`food` 写入为兼容旧模块的过渡方案 |
| **状态** | ⚠️ 技术债 — 待旧模块迁移后废弃 `food` 表写入 |

---

### 冲突 8: inventory + store_inventory 双写 — 采购入库/调拨/收货

| 维度 | 详情 |
|------|------|
| **冲突本质** | 采购入库、调拨、收货等操作按类型双写 `inventory` 和 `store_inventory` |
| **涉及表** | `inventory` vs `store_inventory` |
| **风险** | 双写事务边界不一致导致中央仓/门店仓库存不同步 |
| **裁决** | 两表各自独立管理（中央仓 vs 门店仓）；双写必须在同一事务内 |
| **状态** | ⚠️ 持续关注 — 需确保所有双写路径在同一事务中 |

---

### 冲突 9: 成本双写 — persistOrderCost (主事务) + recordOrderCost (异步)

| 维度 | 详情 |
|------|------|
| **冲突本质** | `persistOrderCost` 在主事务中写入；`recordOrderCost` 异步写入 |
| **涉及模块** | 订单成本计算模块 |
| **风险** | 主事务成功但异步失败导致成本记录丢失或不一致 |
| **裁决** | 分口径一致（成本口径：分）；异步失败需有补偿机制 |
| **状态** | ⚠️ 持续关注 — 需监控异步任务成功率 |

---

### 冲突 10: finance_record 口径 — 注释分实元

| 维度 | 详情 |
|------|------|
| **冲突本质** | `finance_records` 表注释中金额单位标注混乱，有标「分」有标「元」 |
| **涉及表** | `finance_records` |
| **风险** | 开发者按注释理解单位，实际存储与注释不符 |
| **裁决** | `finance_records` 存储单位为「分」；注释错误需修正 |
| **状态** | ⚠️ 待修 — 需扫描并修正所有注释中的单位标注 |
