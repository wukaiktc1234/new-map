# H5招聘表单安全架构 - 根本性解决方案

## 🎯 问题本质

**当前架构的根本缺陷**：
```
❌ H5服务器(3003) ──API代理──→ 后端(8081)
        ↑
   攻击者只要突破H5服务器，就能访问后端！
```

**核心矛盾**：既要让求职者提交数据，又要防止他们访问系统。

---

## 💡 三种根本性解决方案

### 方案对比总览

| 维度 | 方案A: 纯静态 | 方案B: 独立微服务 | 方案C: 第三方SaaS |
|------|------------|--------------|----------------|
| **安全性** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **实现难度** | 极低 | 中等 | 极低 |
| **成本** | 零 | 低（需额外服务器） | 免费/低价 |
| **离线支持** | ✅ 完美 | ❌ 需要 | ❌ 不需要 |
| **数据实时性** | 差（需手动同步） | 好 | 实时 |
| **维护复杂度** | 最低 | 中等 | 最低 |
| **推荐场景** | 小型门店 | 中大型企业 | 所有规模 |

### 核心特性

#### 1️⃣ **零后端依赖**
```javascript
// 表单提交时只做一件事：保存到浏览器本地
function saveToLocalStorage(data) {
  let apps = JSON.parse(localStorage.getItem('recruit_apps') || '[]')
  apps.push(data)
  localStorage.setItem('recruit_apps', JSON.stringify(apps))
}
```
- ❌ 无API调用
- ❌ 无网络请求
- ❌ 无服务器交互
- ✅ 数据100%在客户端

#### 2️⃣ **唯一取票码机制**
```
求职者填写表单 → 自动生成号码 → 告知店员 → 店员输入查询
```
- 格式：`FT-{时间戳36进制}{随机4位}`
- 示例：`FT-KL7M9X2P`
- 特点：短小易记、唯一性强、可复制

#### 3️⃣ **完全隔离**
```
攻击者能做什么？
✅ 访问 :3003 的HTML文件 → 只能看到空白表单
✅ 尝试调用API → 404（根本没有API）
✅ 尝试SQL注入 → 不可能（无数据库连接）
✅ 尝试XSS攻击 → CSP策略防护
❌ 无法获取任何敏感数据
❌ 无法影响主系统
❌ 即使控制3003端口也毫无意义
```

### 优缺点分析

**优势** ✅
- 安全性最高（物理隔离）
- 实现最简单（纯前端代码）
- 成本最低（无需额外资源）
- 离线可用（无网络也能填）
- 攻击面为零（无可攻击的点）

**劣势** ❌
- 数据不同步（需要手动导入）
- 依赖LocalStorage（清除浏览器数据会丢失）
- 不适合大量数据（通常<1000条没问题）
- 店员需要额外操作（输入取票码）

**适用场景**
- ✅ 小型门店（日招聘量 < 50人）
- ✅ 临时性/季节性招聘
- ✅ 对安全性要求极高的场景
- ✅ 网络不稳定的环境

## 🔧 方案B：独立微服务 + 物理隔离

### 架构设计

```
┌─────────────────────────────────────────────────────┐
│                   公网 / DMZ区                        │
│                                                     │
│  ┌─────────────────┐                               │
│  │ 接收服务 :4000   │  ← 独立的极简服务              │
│  │                 │  ← 只接收POST /submit          │
│  │ • Node.js/Go    │  ← 存储到独立SQLite数据库      │
│  │ • SQLite       │  ← 与主系统零网络连接            │
│  │ • 10MB内存占用  │                               │
│  └────────┬────────┘                               │
│           │                                        │
│           ▼ 存储到独立DB                            │
│  ┌─────────────────┐                               │
│  │ recruit_data.db │  ← 定期导出为JSON/CSV         │
│  └─────────────────┘                               │
│                                                     │
│  ════════════════════════════════════════════════    │
│              防火墙 / VLAN隔离                       │
│  ════════════════════════════════════════════════    │
│                                                     │
│                   内网 / 受信区                      │
│                                                     │
│  ┌─────────────────┐     ┌─────────────────┐        │
│  │ 主系统 :8081     │ ←──│ 导入JSON文件     │        │
│  │ (Spring Boot)   │     │ 同步到PostgreSQL │        │
│  └─────────────────┘     └─────────────────┘        │
└─────────────────────────────────────────────────────┘
```

### 核心代码示例

```javascript
// receiver.js - 独立数据接收服务（约100行代码）
const express = require('express')
const sqlite3 = require('sqlite3')
const app = express()

app.use(express.json({ limit: '1mb' }))

// 唯一接口：接收应聘数据
app.post('/api/submit', (req, res) => {
  const { name, phone, position, ...data } = req.body

  // 基础验证
  if (!name || !phone) {
    return res.status(400).json({ error: '姓名和电话必填' })
  }

  // 插入独立数据库
  db.run(
    `INSERT INTO applications (name, phone, position, data, created_at)
     VALUES (?, ?, ?, ?, datetime('now'))`,
    [name, phone, position, JSON.stringify(data), new Date().toISOString()],
    function(err) {
      if (err) return res.status(500).json({ error: err.message })

      res.json({
        success: true,
        ticketCode: `RC${this.lastID.toString(36).padStart(6, '0')}`
      })
    }
  )
})

app.listen(4000, () => console.log('✅ 接收服务运行在 :4000'))
```

### 部署架构

```yaml
# docker-compose.yml
version: '3'
services:
  # 独立接收服务（可部署在任何云服务器上）
  recruit-receiver:
    image: node:18-alpine
    working_dir: /app
    volumes:
      - ./receiver.js:/app/receiver.js
      - ./data:/app/data  # SQLite数据库持久化
    ports:
      - "4000:4000"
    command: ["node", "receiver.js"]
    restart: unless-stopped
    resources:
      limits:
        memory: 50M  # 内存限制50MB
        cpus: '0.1'  # CPU限制10%
```

### 优缺点

**优势** ✅
- 物理隔离（即使被攻破也不影响主系统）
- 可独立部署在云端
- 数据自动存储（不需手动同步）
- 支持大量并发（轻量级服务）

**劣势** ❌
- 需要额外的服务器/容器
- 数据有延迟（需要定期同步）
- 运维成本增加
- 需要处理数据一致性

**适用场景**
- ✅ 中型企业（日招聘量 50-500人）
- ✅ 需要自动化的流程
- ✅ 有独立的运维能力
- ✅ 多门店连锁经营

## 📊 安全等级对比

| 攻击向量 | 当前方案（API代理） | 方案A（纯静态） | 提升 |
|---------|------------------|---------------|------|
| SQL注入 | ⚠️ 有风险 | ✅ 不可能 | +∞ |
| XSS攻击 | ⚠️ 需要防护 | ✅ CSP天然防护 | +++++ |
| API滥用 | ⚠️ 白名单可能绕过 | ✅ 无API | +∞ |
| DDoS攻击 | ⚠️ 频率限制 | ✅ 静态文件抗打 | +++++ |
| 数据泄露 | ⚠️ 代理层风险 | ✅ 数据在本地 | +∞ |
| 横向渗透 | ⚠️ 同网段可访问 | ✅ 物理隔离 | +++++ |

## 📝 总结

**当前方案的问题**：试图在"开放访问"和"安全防护"之间找平衡，但本质上这是矛盾的。

**方案A的思路**：彻底放弃"实时同步"，采用"异步+人工确认"模式，从根本上消除了安全风险。

**类比**：
- 当前方案 = 在城墙上开个门，然后派兵守门（总有疏漏的可能）
- 方案A = 把城门焊死，改用信鸽传递消息（虽然慢一点，但绝对安全）
