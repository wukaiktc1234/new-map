## 1. 概述

### 1.1 系统定位

采购管理系统是食品溯源系统的核心业务模块之一，负责从供应商管理到采购结算的全流程管理。本系统需要与财务、仓储、溯源、人事等外部系统进行数据交互。

### 1.2 当前状态

| 项目 | 状态 | 说明 |
|------|------|------|
| 前端 API | Mock 数据 | 所有 API 返回模拟数据，尚未对接真实后端 |
| ID 生成 | `Date.now()` 时间戳 | 后端对接时需替换为雪花算法 |
| 供应商编码 | 用户输入 + 自动生成双模式 | 用户可手动输入编码，留空则自动生成 |
| 合同模板 | 统一到 `mockData.ts` 管理 | 后端需提供模板管理接口 |
| 金额单位 | 前端元（浮点），后端分（整数） | 通过 DataConverter 在 API 边界转换 |

### 1.3 技术栈

- **后端**: Spring Boot 3.2.0 + MyBatis Plus 3.5.5 + PostgreSQL 18
- **前端**: Vue.js 3.5.x + TypeScript 5.2.2
- **消息队列**: RabbitMQ（跨系统异步通信）
- **缓存**: Redis + Caffeine 二级缓存

## 2. 通用规范

### 2.1 统一响应格式

```json
{
  "code": 0,
  "message": "操作成功",
  "data": {},
  "timestamp": 1712345678901
}
```

- `code=0` 表示成功，非 0 表示失败（业务状态码，与 HTTP 状态码无关）
- 前端响应拦截器已自动提取 `response.data.data`，直接使用返回值即可

### 2.2 分页响应格式

```json
{
  "records": [],
  "total": 100,
  "current": 1,
  "size": 10,
  "pages": 10
}
```

### 2.3 金额转换规则

| 层面 | 单位 | 类型 | 示例 |
|------|------|------|------|
| 前端展示 | 元 | 浮点字符串 | `"1590.00"` |
| API 传输 | 分 | 整数 | `159000` |
| 数据库存储 | 分 | BIGINT | `159000` |

转换公式：
- 元转分：`Math.round(yuan * 100)`
- 分转元：`(fen / 100).toFixed(2)`

### 2.4 状态字段转换规则

前端使用语义化字符串，后端和数据库使用数字编码：

| 业务含义 | 前端值 | 后端值 | 数据库值 |
|---------|-------|-------|---------|
| 启用/正常 | `'active'` | `1` | `1` |
| 禁用/停用 | `'inactive'` | `0` | `0` |
| 试用/审核 | `'probation'` | `2` | `2` |

通过 `DataConverter` 在 API 边界处完成转换，禁止在组件中直接做状态映射。

### 2.5 日期时间格式

| 场景 | 格式 | 示例 |
|------|------|------|
| 前端显示 | `YYYY-MM-DD HH:mm:ss` | `2026-06-01 09:00:00` |
| API 传输 | ISO 8601 | `2026-06-01T09:00:00` |
| 数据库存储 | TIMESTAMP | `2026-06-01 09:00:00` |
| 日期字段 | `YYYY-MM-DD` | `2026-06-01` |

### 2.6 命名规范

| 层面 | 风格 | 示例 |
|------|------|------|
| 数据库字段 | snake_case | `supplier_name`, `create_time` |
| Java 实体 | camelCase | `supplierName`, `createTime` |
| 前端字段 | camelCase | `supplierName`, `createTime` |
| API 路径 | kebab-case | `/v1/purchase/e-contracts` |
| 主键格式 | `{实体缩写}{雪花ID}` | `SUP1234567890`, `PO1234567890` |

### 2.7 逻辑删除

- 业务核心数据必须逻辑删除（`deleted` 字段，0 未删除，1 已删除）
- 临时/日志/缓存类数据可物理删除
- MyBatis-Plus `@TableLogic` 自动处理，查询时无需手动添加 `deleted = 0`

## 4. API 接口规范

### 4.1 通用请求规范

- **基础路径**: `http://localhost:8081/api`

## 5. 核心业务流转链路

### 5.1 主流程

```
供应商管理 → 商品分类 → 商品档案
     │                        │
     ▼                        ▼
采购计划 → 采购申请 → 采购订单 → 采购收货 → 采购结算
                     │              │
                     ▼              ▼
               采购合同(可选)    仓储系统(入库)
                     │
                     ▼
               电子合同(签署)
```

### 5.2 状态流转详解

#### 采购计划 → 采购申请 → 采购订单

```
采购计划: draft → pending → approved → executing → completed
                                              ↓
采购申请: draft → pending → approved ──────→ 生成订单
                                              ↓
采购订单: draft → pending → approved → ordered → shipped → received → completed
```

#### 采购订单 → 采购收货 → 采购结算

```
采购订单: ordered → shipped → received/partial_received
                                    ↓
采购收货: pending → inspecting → qualified/partial → completed
                                    ↓
采购结算: pending → partial → finance_reviewing → completed
```

#### 采购合同 → 电子合同

```
采购合同: draft → pending → active → expired/terminated
                                  ↓
电子合同: draft → pending_sign → signed → expired/cancelled
```

### 5.3 关键业务规则

| 规则 | 说明 |
|------|------|
| 供应商状态校验 | 供应商必须为 `active` 状态才能下单/签约 |
| 申请审批前置 | 采购申请必须 `approved` 才能生成订单 |
| 订单收货前置 | 订单必须 `approved` 或 `ordered` 状态才能收货 |
| 合同关联 | 订单可选择性关联合同，合同终止时关联订单需批量更新状态 |
| 金额一致性 | 订单金额 = 明细行金额之和；结算金额 ≤ 订单金额 |
| 数量一致性 | 收货数量 ≤ 订单数量；所有明细行收货完成时订单状态自动流转 |

## 7. 数据回流更新机制

### 7.1 回流数据汇总

| 回流数据 | 来源 | 目标实体.字段 | 触发条件 | 更新机制 |
|---------|------|-------------|---------|---------|
| 已收货数量 | 仓储系统 | `PurchaseOrderItem.receivedQuantity` | 每次收货确认 | 累加更新 |
| 订单状态→已收货 | 仓储系统 | `PurchaseOrder.status` | 所有明细行 `receivedQuantity >= quantity` | 批量判断 |
| 已付款金额 | 财务系统 | `PurchaseOrder.paidAmount` | 每次付款 | 累加更新 |
| 付款状态 | 财务系统 | `PurchaseOrder.paymentStatus` | `paidAmount` 变化时 | 判断更新 |
| 合同终止→订单状态 | 采购系统 | `PurchaseOrder.status` | 合同终止时 | 批量更新 |
| 供应商评分 | 质量系统 | `Supplier.qualityScore` 等 | 定期评估 | 覆盖更新 |
| 库存数量 | 仓储系统 | `MaterialArchive`（库存） | 每次入库 | 累加更新 |
| 预算占用/释放 | 财务系统 | `PurchaseOrder.budgetStatus` | 订单创建/完成/取消 | 状态同步 |

### 7.2 更新策略说明

- **累加更新**: 在现有值基础上增加/减少，适用于数量、金额类字段
- **覆盖更新**: 直接替换为新值，适用于评分、状态类字段
- **判断更新**: 根据业务规则计算后更新，适用于状态流转
- **批量更新**: 一次操作影响多条记录，如合同终止时更新所有关联订单

### 7.3 幂等性保证

所有回流消息必须携带唯一 `eventId`，消费端需实现幂等校验：

```java
/**
 * 幂等消费示例
 */
if (processedEventIds.contains(eventId)) {
    // 已处理，直接确认
    return;
}
// 执行业务逻辑
processEvent(event);
// 记录已处理
processedEventIds.add(eventId);
```

### 7.4 消息可靠性保障

| 保障机制 | 配置 | 说明 |
|---------|------|------|
| 队列持久化 | `durable=true` | 队列不会因 RabbitMQ 重启丢失 |
| 消息持久化 | `deliveryMode=PERSISTENT` | 消息写入磁盘 |
| 生产者确认 | `publisher-confirm-type=correlated` | 确认消息到达交换机 |
| 消费者手动确认 | `acknowledge-mode=manual` | 处理成功后才确认 |
| 死信队列 | `x-dead-letter-exchange` | 消费失败转入死信队列 |
| 重试策略 | 3次，指数退避 | 初始1s，倍数2.0，最大10s |

## 8. 数据一致性校验

### 8.1 金额一致性

| 校验规则 | 公式 | 校验时机 |
|---------|------|---------|
| 订单金额 = 明细行金额之和 | `order.totalAmount = Σ(item.amount)` | 创建/更新订单时 |
| 结算金额 ≤ 订单金额 | `settlement.totalAmount ≤ order.totalAmount` | 创建结算时 |
| 已付金额一致性 | `order.paidAmount = Σ(关联Settlement的paidAmount)` | 付款确认时 |

### 8.2 数量一致性

| 校验规则 | 公式 | 校验时机 |
|---------|------|---------|
| 收货数量 ≤ 订单数量 | `item.receivedQuantity ≤ item.quantity` | 收货确认时 |
| 合格+不合格 = 收货数量 | `qualifiedQty + unqualifiedQty = quantity` | 检验提交时 |

### 8.3 时间一致性

| 校验规则 | 公式 | 校验时机 |
|---------|------|---------|
| 合同有效期 | `endDate > startDate` | 创建/更新合同时 |
| 期望到货日期 | `expectedDate >= orderDate` | 创建订单时 |

### 8.4 状态前置校验

| 校验规则 | 说明 | 校验时机 |
|---------|------|---------|
| 供应商状态 | 供应商必须为 `active` 才能下单/签约 | 创建订单/合同时 |
| 申请审批 | 采购申请必须 `approved` 才能生成订单 | 生成订单时 |
| 订单状态 | 订单必须 `approved`/`ordered` 才能收货 | 创建收货单时 |
| 合同状态 | 合同必须 `active` 才能关联订单 | 关联合同时 |

### 8.5 对账校验

建议每日凌晨执行定时对账任务：

| 对账项 | 数据源A | 数据源B | 容差 |
|-------|--------|--------|------|
| 订单金额 vs 明细金额 | `purchase_order.total_amount` | `purchase_order_item.amount` 之和 | 0 |
| 已付金额 vs 结算金额 | `purchase_order.paid_amount` | `purchase_settlement.paid_amount` 之和 | 0 |
| 收货数量 vs 订单数量 | `purchase_stockin_item.qualified_quantity` | `purchase_order_item.received_quantity` | 0 |

### 10.4 注意事项

1. **ID 替换**: 当前前端 Mock 使用 `Date.now()` 生成 ID，对接后端后需替换为雪花算法生成的 ID
2. **金额精度**: 所有金额后端以分为单位存储（BIGINT），前端以元为单位展示，转换时使用 `Math.round(yuan * 100)` 避免浮点精度问题
3. **状态映射**: 前端使用语义化字符串（如 `active`），后端使用数字编码（如 `1`），通过 DataConverter 在 API 边界转换
4. **冗余字段**: 供应商名称、部门名称等在订单/合同等实体中冗余存储，更新时需同步
5. **合同模板**: 当前模板在 `mockData.ts` 中管理，后端需提供模板管理接口
6. **供应商编码**: 支持用户手动输入和自动生成双模式，自动生成格式为 `SUP-{时间戳36进制}`
7. **审批流程**: 当前为简单审批，后续需对接工作流引擎
8. **权限控制**: 所有 API 需添加权限注解（`@RequiresPermission`），按 RBAC 模型控制
9. **审计日志**: 所有数据变更需记录审计日志，仅允许 INSERT，禁止 UPDATE 和 DELETE
10. **消息幂等**: 跨系统消息消费必须实现幂等校验，避免重复处理
